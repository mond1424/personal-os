# 밤 실측 — 자는 동안 알람이 뜨는가

**한 번도 안 해 봤다.** 7월 말 Guard v1이 선 뒤로 계속 밀렸다.

---

## 무엇을 확인하나

**Doze 상태에서 `setAlarmClock`이 실제로 기기를 깨우는가.**

그리고 이제 **하룻밤에 셋이 걸린다** — T-28·T-29가 붙었다:

```
01:30  Level 3 이 떴는가              Doze 통과          ← 이 밤의 과녁
02:00~ 격상이 기록됐는가              T-28 · level4State
       오늘 칸이 흐려지는가           T-29 · 날짜 게이트
```

**01:30 첫 발동이 Doze 질문의 답 전부다.** 거기까지가 자는 동안이고,
그 뒤로는 깨어 있으니 Doze가 아니다 — 그래서 **02:00부터는 게이트를 봐도 된다.**
둘이 충돌하지 않는다.

Guard의 발동 경로 둘 중 A(시각·보호 규칙)가 그것에 전부 걸려 있다.
낮에는 화면이 켜져 있어 확인이 안 된다 — **Doze는 화면이 꺼지고 움직임이 없어야 들어간다.**

그리고 이 실패는 **아무 오류도 내지 않는다.** 알림이 안 뜨는 것으로만 드러나고,
그때는 이미 그 밤이 지났다. 9~11월 실사용이 §6.5의 전례를 쌓는 기간인데
**그 전제가 바로 이것**이다.

## 하네스로 대체되지 않는다

`dumpsys deviceidle force-idle`은 흉내다. 실제 Doze와 다를 수 있고,
제조사(삼성) 최적화는 그 위에 한 겹 더 있다. **하룻밤이 필요하다.**

---

## 준비 — 자기 전 10분

> **아래 콘솔 명령은 `chrome://inspect`의 DevTools 콘솔에 붙여 넣는다**
> (`GUARD-DEV-LOOP.md` §3과 같은 자리 — 릴리스 빌드도 붙는다).
> **USB가 연결돼 있어야 한다.** ★·①~③은 자기 전에 하고, ④에서 뽑는다
> (**뽑지 않고 유지하는 방법이 ④에 있다** — 무선 adb).

### ★ 모드가 `coach`인가 — 이것부터다

```js
const m = await Api.guardModes();
[m.active.key, m.active.max_level, m.active.ai_daily_cap];   // ["coach", 4, 5]
```

**`secretary`면 그 밤은 통째로 무효다.** `max_level = 2`라 서버 예약이 L2까지만 만들고
(`smoke.ts:499`가 그것을 박아 뒀다) **01:30에 Level 3이 아예 안 난다.**
`ai_daily_cap`도 **0**이라 격상 후보가 생겨도 전부 `cap`으로 막힌다.

**그리고 그 실패는 "Doze가 막았다"와 화면에서 구별되지 않는다** — 둘 다 *아무 일도 안 일어남*이다.
이 밤이 대답해야 할 질문이 정확히 그것이므로, **모드가 틀리면 잰 것이 없다.**

모드는 **Me 탭의 Guard 모드**에서 바꾼다. `secretary → coach`는 상향이라 언제든 되지만,
**보호 구간 안에서는 하향이 막힌다**(ADR-027) — 되돌릴 거면 데드라인 전에.

### ① 발동이 예약되게 만든다

내일 **09:00 일정**을 하나 만들고 보호를 켠다. 기본값이면 자동으로 이렇게 예약된다:

```
데드라인 = 09:00 − 준비 90분 − 수면 360분 = 01:30

01:30      Level 3   "지금 자야 합니다"
02:00~     Level 4   30분 간격 6회 → 마지막이 04:30
```

**04:30은 하루 경계가 아니라 `deadline + 30분 × 6`이다**(`services/guard.ts`의 `push` 루프).
경계는 설정값이라 여기 적지 않는다 — 궁금하면 ②의 응답에 `boundary`가 함께 온다.

**03:00 언저리에 Level 4가 두세 번 온다** — 그것이 이 실측의 과녁이다.

### ② 서버가 예약을 만들었는지 본다

**`Api`에는 `guardSchedule`이 없다** — `/api/guard/schedule`은 프런트가 안 쓰는 유일한 Guard
엔드포인트라 래퍼가 없다(기기가 직접 부른다). 그래서 raw fetch이고, **토큰을 직접 실어야 한다:**

```js
const r = await fetch("/api/guard/schedule", {
  headers: { Authorization: "Bearer " + localStorage.getItem("api_token") },
}).then((x) => x.json());
r.events[0].fires.map((f) => `L${f.level} ${f.at}`);
```

01:30(L3)·02:00~(L4 여섯)이 나와야 한다. **안 나오면 여기서 멈춘다** — 밤을 기다릴 필요가 없다.
`r.events`가 비었으면 보호 규칙이 안 붙은 것이고, `fires`만 비었으면 이미 지난 시각이다.

### ③ 기기가 알람을 걸었는지 본다

```js
const G = Capacitor.Plugins.Guard;
await G.state();
```

권한 넷(`notifications`·`fullScreenIntent`·`overlay`·`batteryUnrestricted`)이 `true`인지
먼저 본다. 하나라도 `false`면 그것부터다(`GUARD-DEV-LOOP.md` §3).

**그다음이 이 절의 핵심이다 — 서버 예약이 기기 알람으로 넘어왔는지 본다:**

```js
await G.sync();          // 하루 1회 자동이지만, 오늘 규칙을 방금 만들었으면 직접 당긴다
await G.listAlarms();    // { alarms: [{level, atLocal, inSeconds, title}], count, canScheduleExact }
```

`count`가 ②의 `fires` 개수와 같아야 하고 `atLocal`이 01:30·02:00…이어야 한다.
**여기가 sync 누락을 잡는 유일한 자리다** — ②가 초록이어도 `sync()`가 안 돌았으면
서버에는 예약이 있고 폰에는 없다. 그 상태로 자면 **아무 일도 안 일어나고, 아무 오류도 안 난다.**
`canScheduleExact`가 `false`면 정확 알람 권한이 없어 Doze가 미룬다.

```cmd
adb shell dumpsys alarm | findstr /i "personalos"
```

`setAlarmClock`으로 걸린 것이 보여야 한다. **`RTC_WAKEUP`이 아니면 Doze가 미룬다.**

### ★ 그날 낮에 `testNotify({level:4})`를 쓰지 않는다

**AI 상한은 귀속일 기준이다**(`guard.ts:568`). 경계가 06:00이므로
**밤 01:30~05:00은 전날 낮과 같은 귀속일**이고, 낮에 상한을 다 쓰면 그 밤의 Level 4가
**전부 `cap`으로 막힌다** — 격상이 없으면 `GuardLevel4.note()`도 없고 날짜 게이트도 안 걸린다.
상한 값은 모드가 정한다 — **`coach`는 5**(★ 참조).

⚠️ **여기 예로 적혀 있던 2026-08-17은 이 경고의 사례가 아니다 (2026-08-20 정정).**
그날의 `13:57:40 L3 unavailable cap`은 **소진이 아니라 모드다** — 활성 모드가 `secretary`였고
`secretary.ai_daily_cap`은 **0**이다(`0010_guard.sql:150`). 판정이 `used >= cap`이라
(`guard.ts:566-569`) **한 번도 안 썼어도 `0 >= 0`이 참이라 `cap`이 나온다.**

**경고 자체는 그대로 옳다** — 상한은 실제로 작동하고 `coach`의 다섯은 실제로 소진된다.
틀린 것은 **예시 하나**다. 그리고 그 오진이 ★(모드 확인)을 준비의 첫 항으로 올린 이유다:
**`cap` 하나로는 소진과 모드를 못 가르고**, 그 구별은 `guardModes()`만 준다.
`T-31`이 이유를 붙여 "네트워크가 없었나"까지는 막았지만, 이유 하나가 **다시 둘을 뜻했다.**

남은 횟수는 이렇게 본다 (**상한이 0이 아닐 때만 뜻이 있다**):

```js
(await Api.guardEvents(20)).filter(e => e.on_date === <오늘 귀속일> && e.ai_used === 1).length
```

### ④ 폰을 두고 잔다

```
□ 충전기를 꽂지 않는다        ← 충전 중이면 Doze가 안 걸린다. 시험이 무의미해진다
□ 화면을 끄고 손대지 않는다   ← 움직이면 Doze에서 나온다
□ 방해 금지를 켜도 된다       ← ADR-026 — 무음을 override하지 않는 것도 함께 확인된다
□ USB를 뽑는다               ← 연결돼 있으면 충전이다
```

**★ 뽑기 전에 무선 adb로 갈아탄다 — 콘솔을 잃지 않고 충전만 끊는 방법이다.**

```cmd
adb tcpip 5555
adb connect <폰IP>:5555      ← 설정 → 연결 → Wi-Fi → 현재 네트워크에서 IP를 본다
adb devices                  ← <폰IP>:5555 가 device 로 보이면 됐다
```

**그다음 USB를 뽑는다.** 충전은 끊기고 `chrome://inspect`·`device.mjs`는 붙어 있다.

**이것이 왜 ★인가**: 지금까지 두 밤 다 **01:30을 Doze에서 관측하지 못했다.**
8/11은 충전 중이었고, **8/18은 콘솔을 유지하려고 01:30까지 USB를 꽂아 두었다가 01:50에 뽑았다** —
과녁 시각이 매번 충전 구간 안에 들어갔다. 무선 adb는 **그 맞바꿈 자체를 없앤다.**

⚠️ **이 기기에서 아직 하룻밤 검증되지 않았다.** `adbd`는 앱이 아니라 시스템 데몬이라 Doze의
앱 네트워크 제한을 안 받는 것이 기대되지만, **삼성 절전이 그 위에 한 겹 더 있다**(§③과 같은 자리).
그러니 **자기 전에 한 번 확인한다**: 화면을 끄고 몇 분 둔 뒤 `adb devices`가 아직 붙어 있는가.
끊기면 그 밤은 8/18과 같은 조건이 되는 것이고, **끊긴 것 자체가 알아 둘 값이다** — 여기 적는다.

⚠️ **붙어 있어도 보기만 한다.** 폰을 만지면 Doze에서 나온다 — 그건 USB든 무선이든 같다.

## 밤에 깼다면 — 02:00 이후에만

**01:30에 깼으면 그냥 반응하고 다시 잔다.** 그때 앱을 열면 게이트는 볼 수 있지만
Level 3이라 아직 안 걸린다 — 볼 것이 없다.

**02:00 이후 Level 4가 뜬 뒤**라면 30분 안에 앱을 연다.

```
□ 캘린더에서 오늘 칸이 흐려져 있다
□ 오늘 칸에 일정을 추가하면 내일로 가고, 왜 그런지 뜬다
□ 대기에 담는 것은 그대로 된다        ← 막지 않았음을 확인하는 짝
```

**USB만 뽑았다면 이 시각에는 콘솔을 쓸 수 없다.** `chrome://inspect`도 `device.mjs`도
adb 연결이 있어야 붙는다. 다시 꽂으면 **충전이 시작돼 Doze가 풀리고 그 밤이 끝난다** —
Doze가 이 실측의 과녁이므로 그걸 깨면서 게이트를 보는 것은 맞바꿈이 아니다.

**④의 무선 adb로 갈아탔다면 콘솔은 살아 있다.** 그때는 **PC에서** 본다 —
폰을 집어 드는 순간 Doze에서 나오므로, 살아 있는 콘솔의 값은 *폰을 안 만지고 본다*는 데 있다.

**그러니 눈으로 보는 것이 전부다.** 위 세 줄이면 충분하다 — 흐려짐·내일로 이동·이유 문구는
전부 화면에 나온다. 기록은 폰 안에 남으므로 **확인은 아침으로 미룬다.**

**안 깼으면 그냥 잔다.** 게이트는 다음 밤으로 넘긴다 — 급하지 않고, 아침에 `guard_events`로
격상이 났는지는 어차피 확인된다.

## 아침에

### 무엇이 남았나

**USB를 다시 꽂고** `chrome://inspect` 콘솔에서:

```js
(await Api.guardEvents()).slice(0, 8)
  .map((e) => [e.fired_at, e.level, e.cause, e.reaction, e.ai_verdict]);
```

`Api.guardEvents`는 **있다**(`api.js`). 데드라인~그 뒤 세 시간 사이 `protect:` 계열이
몇 건 있는지 본다. `level`이 4인 행이 있으면 **T-28의 격상 기록도 함께 확인된 것**이고,
그때 `ai_verdict`가 `approve`(또는 킬 스위치면 비어 있음)다.

밀린 큐가 있으면 아직 서버에 안 올라갔을 수 있다:

```js
await Capacitor.Plugins.Guard.syncStatus();   // queued > 0 이면 아래를 부른다
await Capacitor.Plugins.Guard.flushEvents();
```

### 가르는 표

| 남은 것 | 뜻 | 다음 |
|---|---|---|
| 예약대로 다 있다 | **통과.** Doze를 통과한다 | 9월 준비 끝 |
| 일부만 있다 | Doze가 일부를 미뤘다 | 몇 시 것이 빠졌나 — 깊은 Doze는 시간이 갈수록 창이 넓어진다 |
| 하나도 없다 | 알람이 안 울렸거나 기록이 안 갔다 | 아래 ③으로 |
| 알림은 봤는데 기록이 없다 | 발동은 됐고 **동기화가 실패** | `G.flushEvents()` · 오프라인 큐 |

### ③ 하나도 없을 때

```cmd
adb shell dumpsys deviceidle
adb shell dumpsys alarm | findstr /i "personalos"
```

- `deviceidle`이 `IDLE`까지 갔는가 — 안 갔으면 실험 자체가 성립 안 했다
- 알람이 아직 걸려 있는가, 아니면 사라졌는가
- **삼성 절전**: 설정 → 배터리 → 백그라운드 사용 제한에 앱이 들어갔는지

**폰을 만지기 전에 이 둘을 먼저 뽑는다.** 화면을 켜면 Doze에서 나오고 증거가 흐려진다.

## 기록

결과는 `STATE.md` §미해결이 아니라 **`APP-BUILD.md` 결정 기록**에 남긴다 —
"확인했다"가 아니라 **"어느 조건에서 어떻게 됐다"**를 적는다.
9월에 문제가 나면 그때 이 기록과 비교한다.

실패했다면 **무엇을 바꿔서 다시 잘 것인지**까지 적는다. 한 번 자고 끝날 일이 아닐 수 있다.
