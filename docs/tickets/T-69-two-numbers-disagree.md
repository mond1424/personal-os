# T-69 — 한 문장 안의 두 수가 서로를 반박한다

**발행** Cowork · 2026-09-12 · **담당** Claude Code · **보통**
**근거** 2026-09-10 Fable 검토 ③ · [ADR-026](../../APP-ADR.md#adr-026) *"재확인도 하나의 발동"* ·
**★ APK 필요 · 위임 금지(`guard/`) · 마이그레이션 없음 · 서버 무관**

---

## 무엇이 어긋났나 — T-68이 넣은 수가 옆의 수를 드러냈다

```
"오늘 밤 3번째예요. 취침 창(00:30~06:00) 안에서 15분째 화면을 보고 있어요."
       └ 재확인·경로 A 를 안 센다        └ 창 안 연속이 아니라 마지막 화면 닫힘 이후
```

**3번째면 창 안에서 최소 45분은 지났다.** 두 수가 한 문장에서 서로를 반박한다.

```
"N번째"   K_NIGHT_N — watch:bedtime 만 센다
          9/9 의 01:13 은 사용자에게 다섯 번째인데 문구는 "3번째" 였을 것이다
"N분째"   GuardActivityLog:91 — intervene_off 이후부터 다시 센다
          개입 화면이 닫힐 때마다 0 이 되므로 두 번째 L3 부터는 세 시간을 써도 "15분째"
```

⚠️ **`usedMin`은 T-68 전에도 틀렸고 아무도 몰랐다.** `n`이 옆에 서면서 드러났다 —
**틀린 사실은 명령보다 빨리 신뢰를 깎는다**(ADR-047 §정정).

## ★ 둘의 뿌리가 같다 — 한 값이 두 일을 한다

```
K_NIGHT_N      ①  밤 상한(watchMaxPerNight)이 쓴다      ← 동작
               ②  문구의 "N번째"가 쓴다                  ← 말
continuousMin  ①  발동 조건(watchMinutes)이 쓴다         ← 동작
               ②  문구의 "N분째"가 쓴다                  ← 말
```

**말을 고치려고 값을 바꾸면 동작이 따라 바뀐다.** 그것이 이 티켓의 함정이고,
**⚠️ 이 티켓은 동작을 한 톨도 바꾸지 않는다.**

## 할 일 — 재는 것을 둘로 가른다

### ① "N번째"가 그 밤의 모든 개입을 센다

**ADR-026이 *"재확인도 하나의 발동"* 이라 정의했고, 사용자가 겪는 것은 *"몇 번 방해받았나"* 다.**

```
지금   K_NIGHT_N          watch:bedtime 만          상한과 문구가 같이 쓴다
바꿈   K_NIGHT_N          ★ 그대로 — 상한이 쓴다     동작 불변
       새 계수            ★ 그 밤의 모든 개입        문구가 쓴다
```

⚠️ **`K_NIGHT_N`을 확장하지 마라.** `watchMaxPerNight`가 그것을 읽으므로
**재확인까지 세면 감시 발동이 줄어든다 — 동작 변경이다.**

⚠️ **이것은 두 벌이 아니다 — 세는 것이 다르다.** 이름이 그 차이를 말해야 한다
(`K_NIGHT_N`은 *"감시가 몇 번 발동했나"*, 새 계수는 *"오늘 밤 몇 번 방해받았나"*).
**★ 둘의 뜻을 각각 한 문장씩 주석에 적어라** — 안 적으면 다음 사람이 합친다(함정 15).

⚠️ **무엇이 "개입"에 드는지 담당이 정하고 근거를 적는다.** 감시 발동·재확인·경로 A 알람 셋이
후보다. **기기가 발동 경로에서 아는 것만** 셀 수 있다(ADR-021 — 서버를 안 부른다).
**셀 수 없는 것이 있으면 그 사실을 §보고에 적어라** — 조용히 빼지 마라.

### ② "N분째"가 취침 창 안의 연속을 말한다

```
지금   마지막 intervene_off 이후          개입 화면이 닫힐 때마다 0
바꿈   ★ 창에 들어온 뒤 화면이 켜져 있던 시간
```

⚠️ **발동 조건(`watchMinutes`)이 읽는 값을 바꾸지 마라.** 그것은
*"방금 N분 연속으로 보고 있다"* 를 재는 것이 맞고, **개입 뒤 0으로 돌아가는 것이 그 뜻이다.**
**문구가 읽을 값을 따로 만든다.**

⚠️ **문구를 이 티켓에 적지 않는다** — 담당이 쓰고 §보고에 적는다.
**다만 두 수가 서로 모순되지 않아야 한다** — 그것이 이 티켓의 유일한 계약이다.

### ③ ★ 재확인 문구의 거짓 하나 — 같이 고친다

```
지금   "5분 전 [알겠습니다]를 선택했지만…"
L2 의 버튼은 "확인" 이다 (GuardAlertActivity.kt:133)
```

**L2를 수락한 뒤의 재확인 문구가 없는 버튼 이름을 말한다.** 한 줄이고 같은 부류다
(문구가 사실과 다르다). ⚠️ **재확인의 조건·상한은 건드리지 마라 — 문구만.**

## 범위

```
android/.../guard/GuardWatch.kt          문구 조립 · 계수 · ★ 위임 금지 영역
android/.../guard/GuardActivityLog.kt    창 안 연속을 따로 낸다
android/.../guard/GuardRecheck.kt        ③의 한 줄
test/smoke.ts 또는 test/front.mjs        검사 (스캐너 층이 될 가능성이 높다)
```

**마이그레이션 없음 · 서버 무변경 · ★ APK 필요.**

⚠️ **`guard/`는 위임 금지 영역**(`AGENT-CHAIN` §4). 직접 한다.
⚠️ **`watchMaxPerNight`·`watchMinutes`·`refireMinutes`·`MAX_PER_DAY`를 한 글자도 만지지 마라.**
⚠️ **L2 게이트(T-60)·수락 버튼(ADR-049 ②)을 건드리지 마라.**
⚠️ **T-70이 넣은 `asked`·`unasked` 경로를 건드리지 마라** — 다른 티켓의 땅이다.

## 금지

| 하지 말 것 | 왜 |
|---|---|
| `K_NIGHT_N`을 확장 | **밤 상한이 그것을 읽는다.** 감시 발동이 줄어든다 — 동작 변경 |
| 발동 조건이 읽는 연속 값을 바꾸기 | 같은 이유. *"방금 N분"* 은 개입 뒤 0이 되는 것이 맞다 |
| 두 계수의 뜻을 주석에 안 적기 | 다음 사람이 합친다(함정 15) |
| 셀 수 없는 것을 센 척하기 | 기기가 아는 것만 센다. 모르면 §보고에 적는다 |
| 상한을 문구에 싣기 | 도구가 카운트다운이 된다(ADR-049 ②) |
| 재확인의 조건·상한 손대기 | ③은 문구 한 줄이다 |
| 발동 경로에서 서버 조회 | ADR-021 |

**검사**

```
1  ★ 문구의 "N번째"가 재확인·경로 A 를 포함해 센다
2  ★ 밤 상한이 세는 수는 안 바뀐다 (감시 발동만)          ← 1의 짝. ★ 동작 불변의 증거
3  ★ 문구의 "N분째"가 창에 들어온 뒤의 연속을 말한다
4  ★ 발동 조건이 읽는 연속 값은 안 바뀐다                 ← 3의 짝. ★ 동작 불변의 증거
5  ★ 한 문장 안의 두 수가 서로 모순되지 않는다            ← 본체
6  재확인 문구가 그 레벨의 실제 버튼 이름을 말한다
7  두 계수가 서로 다른 이름을 갖고 각각 뜻이 적혀 있다 (스캐너)
```

**5가 본체이고 2·4가 이 티켓을 안전하게 만든다** — *"문구만 고친다"* 가 약속이므로
**동작이 안 바뀌었다는 것이 세어져야** 한다.

⚠️ **5를 "두 수가 같다"로 세지 마라** — 다른 것을 세는 수라 같을 리가 없다.
**세야 하는 것은 *"N번째가 k면 N분째가 최소 (k−1)×재발동간격 이상"* 같은 관계**다.
**관계를 어떻게 잴지는 담당이 정하고 근거를 적는다.**

⚠️ **개수를 세지 말고 자리를 세라**(`AGENT-CHAIN` §8) — *"문구에 n이 몇 번 나오나"* 는
이웃 변이와 함께 움직인다(T-68이 그것으로 좁혔다).
⚠️ **fixture 에 고정 시각을 쓰지 마라**(함정 12).
⚠️ **Kotlin 쪽은 jsdom이 못 본다** — 진짜 판정은 밤 실측이다.

**변이**
- 문구가 `K_NIGHT_N`을 그대로 쓴다 → **1만** 죽는다
- `K_NIGHT_N`을 확장한다 → **2만** 죽는다
- 문구가 옛 연속 값을 쓴다 → **3만** 죽는다
- 발동 조건을 새 값으로 바꾼다 → **4만** 죽는다
- 두 수가 모순되게 만든다 → **5만** 죽는다
- 재확인 문구를 되돌린다 → **6만** 죽는다
- 두 계수에 같은 이름을 준다 → **7만** 죽는다

## 확인 절차 (사용자) — APK 설치 후

**밤 실측이다. T-68·T-70과 한 APK로 묶인다.**

```
□ ★ 문구의 두 수가 서로 말이 된다 ("3번째 … 15분째" 같은 모순이 없다)
□ ★★ 그 밤의 발동 횟수·시각이 전과 같다        ← 동작이 안 바뀌었는가
```

**★★ 둘째 줄이 판정이다** — *"문구만 고친다"* 가 지켜졌는가.
⚠️ **발동이 줄거나 늘었으면 이 티켓이 동작을 건드린 것이다.** 그때는 되돌린다.

### ① 무엇이 "개입"인가 — **`fire()`를 지나는, 창 안의, 닿은 발동**

**세는 자리를 `GuardNotifications.fire()` 하나에 두었다.** 티켓이 후보로 든 셋(감시·재확인·
경로 A 알람)이 **전부 그 함수를 지난다** — 경로마다 세면 **넷째 경로가 생겼을 때 조용히 빠진다.**
T-70이 `markAsked`를 발동 경로가 아니라 화면으로 옮긴 것과 같은 이유다:
**자리가 늘어나는 곳과 값을 내는 곳이 같아야 안 갈라진다.**

계수는 새 파일 `GuardNight`의 `night_interrupt_count`이고, 상한이 읽는
`GuardWatch.K_NIGHT_N`(`watch_night_count`)은 **한 글자도 안 건드렸다.**

**⚠️ 세는 것과 안 세는 것을 조용히 두지 않는다:**

| | 센다 | 왜 |
|---|---|---|
| 감시 발동 · 재확인 · 경로 A 알람 | ✅ | ADR-026 *"재확인도 하나의 발동"* · 사용자가 겪는 것은 *"몇 번 방해받았나"* |
| **취침 창 밖의 발동** | ❌ | 문구가 *"오늘 밤"* 과 *"취침 창"* 을 **함께** 말한다. 두 수가 같은 틀을 써야 한 문장에 선다 |
| **닿지 않은 발동**(권한 없어 알림도 화면도 못 냄) | ❌ | 아무도 안 봤다. 그걸 *"방해"* 로 세면 **T-70이 없앤 거짓과 같은 모양**이다 |
| **진단 발동**(`GuardPlugin.testNotify`) | ✅ | ⚠️ **티켓이 안 센 넷째다.** 그것도 Guard가 사용자 앞에 선 것이라 거짓이 아니지만, **밤 실측에서 테스트를 쏘면 그 수가 오른다** — 아래 §남긴 것 2 |

★ **`fire()`가 예측하지 않는다.** 증가는 `posted || shown`이 정해진 **뒤**에 일어나고,
문구는 발동 **전**에 `count + 1`을 읽는다. 이번 발동이 안 닿으면 계수가 안 올라 **다음 발동이
같은 수를 말한다** — 그게 맞다.

### ② 두 수가 같은 틀을 쓴다 — 그것이 이 티켓의 계약

**문구:** *"오늘 밤 3번째예요. 취침 창(00:30~06:00)에 들어온 뒤 66분 화면을 켜 두셨어요."*

`GuardActivityLog.screenOnMinSince(ctx, GuardNight.windowStartMs(…))`가 재는 것은
**창 시작 이후 화면이 켜져 있던 시간의 합에서 Guard 자신이 붙잡은 몫을 뺀 값**이다.

- **왜 합인가.** 합은 **밤 동안 줄지 않는다.** 방해 횟수도 줄지 않는다.
  ★ **둘 다 단조라서 서로를 반박할 수 없다** — 그것이 티켓이 요구한 *"관계"* 이고, 검사 5가 세는 것이다.
- **왜 Guard 몫을 빼는가.** 개입 화면은 `FLAG_KEEP_SCREEN_ON`으로 화면을 붙잡는다(T-30).
  안 빼면 **Guard가 자기 개입 시간을 사용자 사용으로 청구한다.** T-31이 *"원본엔 더해서 남기고
  읽는 쪽이 뺀다"* 고 적어 둔 그 자리다.
- **⚠️ 문구를 바꿨다.** *"N분째 보고 있어요"* → *"들어온 뒤 N분 켜 두셨어요"*.
  **합에 *"째"* 를 붙이면 연속이라는 거짓이 된다** — 화면을 껐다 켠 밤에 바로 틀린다.

★ **경계 판정이 한 곳이다.** `inWindow`·`key`·`windowStartMs`가 `GuardNight`의 같은 `startCal`을
쓴다(`GuardWatch`에서 옮겼다). 셋이 각자 판단하면 **자정 근처에서 두 수가 다른 밤을 말한다.**

### ③ 재확인 문구 — 거짓이 **둘**이었다

```
전  "5분 전 [알겠습니다]를 선택했지만 …"
후  "7분 전 [확인]을 선택했지만 …"            ← Level 2 의 실제 버튼
```

- **버튼 이름**의 주인을 `GuardAlertActivity.acceptLabel(level)` 하나로 두었다.
  Level 3+ 값은 **레이아웃의 `android:text`와 같아야 하고 검사 6이 그 둘을 맞춰 본다** —
  주석으로 적는 대신 세게 했다(함정 15).
  ⚠️ **수락 버튼은 안 건드렸다**(티켓 §범위). Kotlin이 **이미 쓰고 있던** `level < 3` 가지의
  리터럴만 그 함수 호출로 바꿨다 — 렌더되는 글자는 전과 같다.
- **조사도 재료가 된다** — `[확인]을` · `[알겠습니다]를`. 이름만 맞고 문장이 틀리면 같은 부류의 결함이다.
- **⚠️ *"5분"* 도 고쳤다.** 그건 `RECHECK_MS`의 복사본이라 그 상수를 만지면 문구만 옛말이 된다.
  **실제 경과**를 쓴다 — 티켓이 든 것은 버튼 이름 하나지만 **같은 줄의 같은 부류**다.

### 검사 — 셋은 스캐너가 아니다

티켓이 *"관계를 재라"* 고 했고 **관계는 정규식으로 못 잰다.** 그래서 `GuardActivityLog`의 두 함수를
**Kotlin 본문 그대로 JS로 옮겨 한 밤을 돌린다**(T-68이 문구에 쓴 방식의 한 단계 아래).
규칙을 검사에 다시 적지 않으므로 **구현이 틀리면 검사가 함께 틀리는 일**이 없다(함정 15).

```
창 10분 전부터 화면 켜짐 · 창 안 25·50·75분에 개입 셋(각 2분 점유)
게이트  [35, 23, 23]   개입마다 0에서 다시 센다        ← 안 바뀌었다 (검사 4)
문구    [25, 48, 71]   창 시작부터, 개입이 안 되돌린다  ← 바뀐 것 (검사 3·5)
```

**옛 규칙을 그대로 넣으면 `[35, 23, 23]`이고 *"3번째인데 23분째"*** 가 된다 — `5의 짝`이 그것을 센다.
⚠️ **옮기기가 실패하면 셋이 함께 빨간불**이다. 조용히 통과하지 않는다.

**⚠️ T-68의 검사 3·4를 고쳤다 — 옛 동작을 검사하고 있었다**(CLAUDE.md §기준선).
T-69가 문구의 계수를 옮겼으므로 *"문구가 읽는 계수"* 의 주소가 바뀌었다. **주장은 한 글자도 안 바꿨고**
사는 곳만 따라갔다. ★ **3은 모양 둘을 다 읽게 했다** — 문구가 다시 `GuardWatch`의 계수를 읽어도
그 주장은 여전히 참이므로, 그때 빨간불이 되면 **참인데 우는 검사**가 된다(그 자리는 T-69 1의 몫이다).

### 변이

```

M2  상한 계수를 확장한다 (재확인도 센다)   → 2만   ✅  (466·1)

```

⚠️ **M7a가 못 가른 것은 필연이고 증명이 있다**(T-65·T-70이 쓴 그 구별):
두 계수에 **같은 pref 키**를 주면 그 순간 **상한이 실제로 재확인까지 세게 된다** — 2가 보는
*"상한 계수를 만지는 파일이 하나인가"* 가 **참으로 깨진다.** 이름을 합치는 것과 상한을 넓히는 것이
**같은 결함의 두 얼굴**이라 한 변이가 둘을 건드린다. **M7b가 7의 단독 자리를 증명한다.**

★ **4는 두 절반을 갖는다.** M4에서 게이트 값 `[35,23,23]`은 **그대로였고**(변이가 `GuardWatch`의
*부르는 곳*만 바꿨으므로) **구조 절반(`조건줄`)이 잡았다.** M5에서는 반대로 값이 움직여 5가 잡았다.
**같은 밤을 값과 구조 둘로 보고 있어서** 어느 쪽으로 밀어도 한 자리가 선다.

### ⚠️ 남긴 것 — 셋

**1. 링 버퍼가 창보다 짧을 수 있다.** `GuardActivityLog.MAX = 300`은 60초 폴링에서 **약 5시간**인데
취침 창은 `00:30~06:00` = **5.5시간**이다. 앱 전환 표본이 많은 밤이면 더 짧다.
앞이 잘리면 창을 연 `screen_on`이 사라져 **모자라게 말한다.**
★ **틀리는 방향이 안전한 쪽이다** — 넘치게 말하면 안 한 일을 사람에게 씌운다.
(게이트도 같은 버퍼를 쓰므로 **새로 생긴 한계가 아니다.**)

**2. 진단 발동이 세어진다.** `testNotify`로 밤에 시험 발동을 쏘면 그 밤의 *"N번째"* 가 오른다.
거짓은 아니다 — 그것도 Guard가 사용자 앞에 섰다. ★ **밤 실측에서 ★★ 줄(발동 횟수·시각)은
`firedTonight`(=`K_NIGHT_N`)로 보므로 영향이 없다.** 헷갈리는 것은 문구의 수뿐이다.

**3. T-68이 적어 둔 불변식 하나가 깨졌다 — 주석을 정정했다.**
T-68은 *"첫 발동은 늘 Level 2이므로 아침 한 줄과 누적 한 줄이 같은 발동에 함께 서지 않는다"*
고 적었다. 그때는 `n`이 감시 발동 수라 `n == 1 ⟺ level == 2`였다. **이제 `n`은 방해 수라**
경로 A 알람이 창 안에서 먼저 울린 밤이면 **첫 감시 발동에 이미 `n >= 2`** 이고 둘이 함께 선다.
★ **그것이 맞다** — 둘 다 사실이고, 방해가 두 번이었다는 것도 사실이다.

### 덤으로 잡은 것 — 스캐너가 줄바꿈에 물려 있었다

변이를 돌리다 **구현이 그대로인데 검사 4가 빨간불**이 됐다. 값은 맞고 `조건줄=false`였다 —
변이 스크립트가 파일을 **CRLF로 다시 썼기** 때문이다. `t46Bare`가 `\r`를 안 걷어서
*"두 줄이 붙어 있는가"* 를 세는 스캐너가 `)\r\n`에 걸렸다.
⚠️ **윈도우 편집기가 한 번 다시 저장하면 그만인 일**이라 *"회귀했다"* 와 구별이 안 된다.
`t46Bare`가 이제 `\r`를 먼저 걷는다.
