# T-08′ — 모드 화면: 왜 막혔는지가 보여야 한다

**발행** Cowork · 2026-08-05 · **담당** Codex CLI · **상태** ⛔ 차단 — **T-19 선행**

---

## 왜 지금

T-10이 서버 계약을 세웠다. **화면이 아직 그것을 모른다.**

```
지금 폰에서 모드를 내리면 → 400 또는 409 → 화면은 정체불명의 실패
```

**사용자가 오늘 이 상태를 만난다.** 그래서 다른 백로그보다 먼저다.

## 옛 T-08은 폐기한다

`stash@{0}`에 남은 작업은 **"하향에 확인만 붙이고 막지 않는다"** 판이다.
그것은 ADR-019 부수 규칙 1·2를 정면으로 어겼고 검토에서 불합격했다.
**전제가 달라졌으니 되살리지 않는다** — 서버가 이제 실제로 막는다.

## 이 화면의 목적

> 마찰이 **벌**로 느껴지면 사용자는 우회로를 찾는다.
> **사전 서약**으로 읽히면 납득하고 지나간다.

같은 409라도 이 둘은 다르다:

```
✗  "변경할 수 없습니다"
✓  "'물리학 중간고사' 보호 중이라 지금은 내릴 수 없어요.
    8/7 09:00 이후에 다시 시도할 수 있어요."
```

**무엇이 · 언제까지**가 나와야 사용자가 자기가 세운 규칙을 다시 본다.

**해제 시각은 `protecting.until`이다 — 취침 데드라인이 아니다.**
보호 구간은 `protect_from ~ start`이고, 끝은 **일정 시각**이다.
데드라인(01:30 꼴)은 그 구간 *안*의 발동 시점이지 해제 시점이 아니다.
직접 계산하지 말고 `until`을 그대로 쓴다.

## 세 경로

```
상향·동일     지금 그대로. 사유도 대기도 없다
하향 (밖)     사유 입력 + 60초 대기 → PUT { key, reason }
하향 (보호 중) 시도 자체가 막힌다 — 이유와 해제 시각을 보여준다
```

### 판정은 전부 서버가 준다 — **T-19의 응답을 읽는다**

```
GET /api/guard/modes
  modes[].downgrade   그 모드로 가는 것이 하향인가
  protecting          지금 보호 중인 일정 { title, start, until } 또는 null
```

**프런트가 하향을 판정하지도, 데드라인을 역산하지도 않는다.** 둘 다 boolean·값으로 온다.

`public/app.js`의 `protectionDeadline`(694행 근처)이 서버와 같은 식을 이미 갖고 있다 —
T-05가 남긴 사본이다. **이 티켓에서 그것을 늘리지 않는다.** 새 계산을 붙이지 말고 조회한 값을 쓴다.

### 대기 60초는 클라이언트가 건다

ADR-027 결정 ③ — 서버는 60초가 흘렀는지 알 수 없다. **Override와 같은 구조다.**

- 대기 중에 취소할 수 있다. 취소는 아무것도 바꾸지 않는다
- 대기가 끝나야 요청이 나간다. **먼저 보내고 기다리는 척하지 않는다**
- 사유가 비어 있으면 대기를 시작하지 않는다 — 60초를 세고 나서 400을 받으면 두 번 기다리게 된다

### 409·400이 여전히 올 수 있다

대기 60초 사이에 보호 구간이 **시작될 수 있다.** 그때는 서버가 409를 낸다.
**클라이언트 판정을 믿고 오류를 삼키지 않는다** — 서버 응답을 그대로 보여준다.

## 범위

```
public/index.html   모드 영역
public/app.js       모드 전환 · 사유 · 대기 · 오류 표시
public/api.js       PUT 본문에 reason
public/style.css    표시
test/front.mjs      검사
```

**서버를 건드리지 않는다.** T-10이 세운 계약을 그대로 쓴다.

## 금지

| 하지 말 것 | 왜 |
|---|---|
| 상향에 사유·대기 붙이기 | ADR-019 부수 규칙 1 — 상향은 자유 |
| 데드라인 역산을 새로 작성 | 서버가 준다. 사본이 이미 하나 있고 **늘리지 않는다** |
| 하향 판정을 프런트에서 다시 구현 | 다섯 파라미터 비교는 서버 몫이다. 갈라지면 화면과 결과가 다르다 |
| 서버 409·400을 삼키고 자체 문구로 대체 | 대기 중 구간이 시작될 수 있다. 서버가 최종이다 |
| 대기를 건너뛰는 경로 (길게 누르기 등) | 마찰이 마찰이 아니게 된다 |
| 사유 없이 대기 시작 | 60초 뒤 400. 두 번 기다리게 된다 |
| 짧고 일반적인 새 클래스명 | 전역 충돌 **세 번**. 접두사(`.mode-…`) |
| 색 리터럴 · `scrollIntoView` | 함정 5 · 1 |

## 완료 조건

```
typecheck 통과 · smoke 260(변화 없음) · front 223 → 229 이상 · 실패 0
```

검사:

1. 상향에 사유 칸도 대기도 나타나지 않는다
2. 하향을 고르면 사유 칸이 뜨고, **비어 있으면 대기가 시작되지 않는다**
3. 대기 중 취소하면 모드가 그대로다 (요청이 나가지 않았다)
4. 서버가 409를 주면 **일정 이름과 해제 시각이 화면에 있다**
5. **대기가 끝나기 전에는 PUT이 나가지 않는다**
6. 서버가 400을 주면 사유 칸으로 돌아간다

**5번이 이 티켓의 덫이다.** 요청을 먼저 보내고 60초 타이머를 화면에만 돌리면
1·2·3·4·6은 전부 통과하고, **마찰은 사라진 채 연출만 남는다.**
jsdom에서 타이머를 앞당기고 `PUT` 호출 여부를 본다.

## 확인 절차 (사용자)

deploy 후. APK 재빌드 불필요.

```
□ coach로 올리는 것은 즉시 된다
□ secretary로 내리면 사유를 묻고 60초를 센다
□ 대기 중 취소하면 모드가 안 바뀐다
□ 보호 일정이 있는 시간대에 내리면 그 일정 이름이 화면에 나온다
```

네 번째는 **보호 일정이 실제로 잡혀 있어야** 확인된다.

## 곁일 — 역산식 사본 (별도 커밋 없음 · 기록만)

`public/app.js` `protectionDeadline`이 서버 `schedule()`과 같은 식을 갖고 있다.
**지금 갈라져 있지 않지만, 기본값(`DEFAULT_SLEEP_MIN`·`DEFAULT_PREP_MIN`)을 조정하면
한쪽만 따라간다.** 조용히 갈라지고 아무 오류도 나지 않는다.

**이 티켓에서 고치지 않는다** — 범위를 넘고, 미리보기는 저장 전이라 서버 왕복이 부담이다.
`BACKLOG`에 올린다. 해법 후보는 둘:

```
A  서버가 미리보기 값을 준다        원칙에 맞으나 입력마다 왕복
B  검사가 두 식을 같은 입력으로 묶는다   갈라지는 순간 빨간불
```

**B가 현실적이다.** 다음 티켓에서 판단한다.
