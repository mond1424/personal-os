# T-57 — 앱의 기다림에도 상한이 있다

**발행** Cowork · 2026-09-03 · **담당** Claude Code · **보통**
**근거** T-56 실측(HEAD 4회 중 1회 재현) · `CLAUDE.md` §함정 8 · **APK 무관 · 서버 무변경**

---

## 무엇이 어긋났나

**검사 러너에는 상한이 있는데 앱에는 없다.**

```
HEAD(T-55)  1: 124.0초 394/0   3: 123.8초 394/0   4: 123.1초 394/0
            2: 420.0초 ★요약 없음★  ← 안전망에 걸렸다
```

**자리가 고정이다** — 매번 T-54 검사 2 직후,
`t54Sync({ok:true})` → `calSyncNow` → `refreshToday()`/`renderCalendar()` 구간.

⚠️ **함정 8이 세운 장치가 제 일을 했다** — 러너가 *"안전망 420초에 걸렸다"* 고 **이름을 말했다.**
그래서 이것은 미스터리가 아니라 **관측된 결함**이다.

## ★ 이것은 검사의 문제가 아니다

**러너의 420초는 마지막 방벽이지 설계가 아니다.** 같은 일이 폰에서 일어나면:

```
워커가 응답을 한 번 놓친다  →  fetch 가 영원히 매달린다
                          →  #cal-result 가 영원히 안 뜬다
                          →  ★ T-54 가 없앤 "조용한 실패"가 그대로 돌아온다
```

**T-54·T-55가 두 티켓에 걸쳐 세운 것이 상한 하나가 없어서 무너지는 자리다.**
그리고 이 프로젝트에서 응답이 늦는 순간은 **네트워크가 나쁜 새벽**이다 —
정확히 Guard가 일해야 하는 시각이고, T-31 초안이 물렸던 그 자리와 같은 종류다.

⚠️ **원인은 아직 안 짚었다**(워커가 안 주는 것인지 jsdom 잔여 핸들러인지).
**이 티켓은 원인을 고치지 않는다** — **상한이 없는 것**을 고친다. 둘은 다른 결함이고,
상한은 원인이 무엇이든 필요하다.

## 할 일

### ① 진단 — 어느 쪽인지 먼저 가른다

```
워커가 정말 안 주나        요청은 갔는데 응답이 없나 · 아예 안 갔나
jsdom 잔여 핸들러인가      앞 검사의 미완 프라미스가 이 fetch 를 붙잡나 (함정 14의 이웃)
```

⚠️ **①이 ②를 막지 않는다.** 원인이 무엇이든 상한은 넣는다 — 다만 **원인을 알면 상한 값이
근거를 갖는다.** 모르면 임의의 숫자가 된다.

### ② ★ `fetch`에 상한을 건다

**`AbortSignal.timeout()` 또는 그에 준하는 것.** 자리는 **`api.js`의 `_req` 하나**다 —
호출부마다 걸면 **빠뜨린 곳이 조용히 남는다**(T-52가 방벽을 SQL에 둔 것과 같은 판단).

⚠️ **값을 여기에 적지 않는다.** 상한은 설정값의 성질을 갖는다 —
`AI_TIMEOUT_MS = 8_000`이 선 자리와 같은 급으로, **한 곳에 상수로 두고 그것을 가리킨다.**

### ③ ★ 상한에 걸린 것과 실패한 것을 가른다

```
timeout   "응답이 안 와요 — 잠시 뒤 다시 해 주세요"
실패      기존 오류 경로 그대로
```

⚠️ **뭉개면 안 된다**(T-43·T-53과 같은 판단). `HTTP 500`과 *"아무 답도 없음"*은
**사용자가 할 일이 다르다** — 앞은 신고할 것이고 뒤는 다시 눌러 볼 것이다.

### ④ Guard 경로는 인질이 되지 않는다

⚠️ **`GuardSync`의 `runCatching`과 같은 원칙**(T-53): 캘린더가 안 와도 **보호 일정 예약은 돈다.**
상한이 새로 생기면서 **그 순서가 깨지지 않는지** 확인한다.

## 범위

```
public/api.js       _req 에 상한 · 상수 하나
public/app.js       timeout 문구 (③)
test/front.mjs      검사
```

**서버 무변경 · 마이그레이션 없음 · APK 무관**(웹만이다).

⚠️ **`android/guard/` 아래를 안 건드린다.** 네이티브의 `fetch`는 별개이고 이 티켓이 아니다 —
**같은 결함이 그쪽에도 있으면 고치지 말고 보고한다.**

**Antigravity 위임 가능** — ①의 진단은 직접.

## 금지

| 하지 말 것 | 왜 |
|---|---|
| 호출부마다 상한 걸기 | **빠뜨린 곳이 조용히 남는다.** `_req` 하나다 |
| timeout 과 실패를 같은 문구로 | 사용자가 할 일이 다르다(T-43·T-53) |
| 상한 값을 문서·주석에 적기 | 상수 하나가 원본이다. **두 곳에 두면 갈라진다** |
| 러너의 안전망을 늘려 해결 | ⚠️ **경합을 미루는 것이다**(함정 14). 늘려서 다시 죽은 전례가 있다 |
| 원인을 못 짚었다고 상한을 미루기 | **상한은 원인과 독립이다** |
| `guard/` 네이티브까지 손대기 | 범위 밖. 있으면 보고한다 |

## 완료 조건

```
typecheck 통과 · smoke 394(변화 없음) · front 398 → 402 이상 · 실패 0 · verify exit 0
```

⚠️ **기준선은 `STATE.md` §기준선이 원장이다** — 위 숫자가 그것과 다르면 STATE를 따르고 그 사실을 말한다.

**검사**

```
1  응답이 안 오면 상한에서 끊긴다
2  ★ 정상 응답은 안 끊긴다                       ← 1의 짝
3  ★ timeout 문구가 일반 실패 문구와 다르다
4  ★ 상한이 _req 한 곳에 있다 (스캐너 — 호출부에 흩어져 있지 않은가)
5  ★ 4의 스캐너가 살아 있는가
```

**⚠️ front 를 20회 돌려 hang 이 사라졌는지 센다.** 4회 중 1회였으므로 **한 번 통과는 증거가 아니다.**
이것이 이 티켓의 진짜 판정이고, 검사 다섯이 대신하지 못한다.

⚠️ **검사 신호에 토스트나 `until`을 쓰지 마라**(함정 14).

**변이**
- 상한을 뺀다 → **1만** 죽는다
- 상한을 0으로(항상 끊는다) → **2만** 죽는다
- 두 문구를 합친다 → **3만** 죽는다
- 상한을 호출부로 옮긴다 → **4만** 죽는다
- 스캐너를 눈멀게 한다 → **4는 초록 · 5만** 죽는다
