# T-57 — 앱의 기다림에도 상한이 있다

**발행** Cowork · 2026-09-03 · **담당** Claude Code · **보통**
**근거** T-56 실측(HEAD 4회 중 1회 재현) · `CLAUDE.md` §함정 8 · **APK 무관 · 서버 무변경**

---

## 무엇이 어긋났나

**검사 러너에는 상한이 있는데 앱에는 없다.**

```
HEAD(T-55)  1: 124.0초 394/0   3: 123.8초 394/0   4: 123.1초 394/0
            2: 420.0초 ★요약 없음★  ← 안전망에 걸렸다
```

**자리가 고정이다** — 매번 T-54 검사 2 직후,
`t54Sync({ok:true})` → `calSyncNow` → `refreshToday()`/`renderCalendar()` 구간.

⚠️ **함정 8이 세운 장치가 제 일을 했다** — 러너가 *"안전망 420초에 걸렸다"* 고 **이름을 말했다.**
그래서 이것은 미스터리가 아니라 **관측된 결함**이다.

## ★ 이것은 검사의 문제가 아니다

**러너의 420초는 마지막 방벽이지 설계가 아니다.** 같은 일이 폰에서 일어나면:

```
워커가 응답을 한 번 놓친다  →  fetch 가 영원히 매달린다
                          →  #cal-result 가 영원히 안 뜬다
                          →  ★ T-54 가 없앤 "조용한 실패"가 그대로 돌아온다
```

**T-54·T-55가 두 티켓에 걸쳐 세운 것이 상한 하나가 없어서 무너지는 자리다.**
그리고 이 프로젝트에서 응답이 늦는 순간은 **네트워크가 나쁜 새벽**이다 —
정확히 Guard가 일해야 하는 시각이고, T-31 초안이 물렸던 그 자리와 같은 종류다.

⚠️ **원인은 아직 안 짚었다**(워커가 안 주는 것인지 jsdom 잔여 핸들러인지).
**이 티켓은 원인을 고치지 않는다** — **상한이 없는 것**을 고친다. 둘은 다른 결함이고,
상한은 원인이 무엇이든 필요하다.

## 할 일

### ① 진단 — 어느 쪽인지 먼저 가른다

```
워커가 정말 안 주나        요청은 갔는데 응답이 없나 · 아예 안 갔나
jsdom 잔여 핸들러인가      앞 검사의 미완 프라미스가 이 fetch 를 붙잡나 (함정 14의 이웃)
```

⚠️ **①이 ②를 막지 않는다.** 원인이 무엇이든 상한은 넣는다 — 다만 **원인을 알면 상한 값이
근거를 갖는다.** 모르면 임의의 숫자가 된다.

### ② ★ `fetch`에 상한을 건다

**`AbortSignal.timeout()` 또는 그에 준하는 것.** 자리는 **`api.js`의 `_req` 하나**다 —
호출부마다 걸면 **빠뜨린 곳이 조용히 남는다**(T-52가 방벽을 SQL에 둔 것과 같은 판단).

⚠️ **값을 여기에 적지 않는다.** 상한은 설정값의 성질을 갖는다 —
`AI_TIMEOUT_MS = 8_000`이 선 자리와 같은 급으로, **한 곳에 상수로 두고 그것을 가리킨다.**

### ③ ★ 상한에 걸린 것과 실패한 것을 가른다

```
timeout   "응답이 안 와요 — 잠시 뒤 다시 해 주세요"
실패      기존 오류 경로 그대로
```

⚠️ **뭉개면 안 된다**(T-43·T-53과 같은 판단). `HTTP 500`과 *"아무 답도 없음"*은
**사용자가 할 일이 다르다** — 앞은 신고할 것이고 뒤는 다시 눌러 볼 것이다.

### ④ Guard 경로는 인질이 되지 않는다

⚠️ **`GuardSync`의 `runCatching`과 같은 원칙**(T-53): 캘린더가 안 와도 **보호 일정 예약은 돈다.**
상한이 새로 생기면서 **그 순서가 깨지지 않는지** 확인한다.

## 범위

```
public/api.js       _req 에 상한 · 상수 하나
public/app.js       timeout 문구 (③)
test/front.mjs      검사
```

**서버 무변경 · 마이그레이션 없음 · APK 무관**(웹만이다).

⚠️ **`android/guard/` 아래를 안 건드린다.** 네이티브의 `fetch`는 별개이고 이 티켓이 아니다 —
**같은 결함이 그쪽에도 있으면 고치지 말고 보고한다.**

**Antigravity 위임 가능** — ①의 진단은 직접.

## 금지

| 하지 말 것 | 왜 |
|---|---|
| 호출부마다 상한 걸기 | **빠뜨린 곳이 조용히 남는다.** `_req` 하나다 |
| timeout 과 실패를 같은 문구로 | 사용자가 할 일이 다르다(T-43·T-53) |
| 상한 값을 문서·주석에 적기 | 상수 하나가 원본이다. **두 곳에 두면 갈라진다** |
| 러너의 안전망을 늘려 해결 | ⚠️ **경합을 미루는 것이다**(함정 14). 늘려서 다시 죽은 전례가 있다 |
| 원인을 못 짚었다고 상한을 미루기 | **상한은 원인과 독립이다** |
| `guard/` 네이티브까지 손대기 | 범위 밖. 있으면 보고한다 |

**검사**

```
1  응답이 안 오면 상한에서 끊긴다
2  ★ 정상 응답은 안 끊긴다                       ← 1의 짝
3  ★ timeout 문구가 일반 실패 문구와 다르다

5  ★ 4의 스캐너가 살아 있는가
```

**⚠️ front 를 20회 돌려 hang 이 사라졌는지 센다.** 4회 중 1회였으므로 **한 번 통과는 증거가 아니다.**
이것이 이 티켓의 진짜 판정이고, 검사 다섯이 대신하지 못한다.

⚠️ **검사 신호에 토스트나 `until`을 쓰지 마라**(함정 14).

**변이**
- 상한을 뺀다 → **1만** 죽는다
- 상한을 0으로(항상 끊는다) → **2만** 죽는다
- 두 문구를 합친다 → **3만** 죽는다
- 상한을 호출부로 옮긴다 → **4만** 죽는다
- 스캐너를 눈멀게 한다 → **4는 초록 · 5만** 죽는다

## 보고 (담당이 채운다)

```
티켓: T-57
바꾼 파일: public/api.js · public/app.js · test/front.mjs
기준선: typecheck 통과 · smoke 394 무변경 · front 398 → 404 · 실패 0 · verify exit 0
```

**① 진단 — 워커다. jsdom 잔여가 아니다.**

계측(in-flight `fetch` 목록 · 마지막 통과 검사 이름 · `process.getActiveResourcesInfo()`)을 넣고
front 를 돌려 **2회차에서 재현**했다(420.1초 · 요약 없음).

```
GET /api/periods           280.1초   직전통과="T-54 1"
GET /api/collected/status  280.1초   직전통과="T-54 1"
GET /api/today             280.1초   직전통과="T-54 2"   ← T-54 검사 3의 calSyncNow
활성 리소스: TCPSocketWrap ×3 · Timeout ×4
```

**갈라 준 것은 `TCPSocketWrap` 셋이다** — 요청은 갔고 소켓이 열린 채 살아 있다.
잔여 핸들러라면 TCP 소켓이 있을 이유가 없다. 직전 in-flight 가 **8**까지 올라간 것도 남았다
(로컬 D1 에 동시 요청이 몰린 구간). ⚠️ **원인은 워커 쪽에 남아 있고 이 티켓은 그것을 안 고쳤다.**

**② 상한 — `_req` 하나. 상수는 `api.js` 안에만 있다.**

`REQ_TIMEOUT_MS = 15_000` 이 기본이고, **모델을 부르는 셋**(`POST /analyses`·`/ai/test`·
`/daily/classify-feelings`)만 `REQ_TIMEOUT_SLOW_MS`를 쓴다 — 서버가 2-pass 로 모델을 **두 번**
부르는 길이라(`services/analysis.ts`) 같은 상한을 씌우면 **상한이 정상 동작을 끊는다.**
어느 쪽을 쓸지도 `_req`이 고른다. 호출부는 상한을 모른다.

두 겹이다: `AbortSignal.timeout`이 **죽은 요청을 끊고**, 시계가 **앱을 빼낸다.**
격리 프로브로 다섯을 실측했다 — 정상 요청 통과 · `HTTP 500` 문구 그대로 · **실서버 무응답을
abort 가 실제로 회수**(서버가 끊김을 봤다) · **안 정산되는 `fetch`는 abort 로는 못 빠져나오고
시계가 빼냈다** · 연결 거부 문구 그대로. **뒤의 하나 때문에 시계를 뺄 수 없다.**

**③ timeout 과 실패**

`e.timeout` 한 칸으로 갈린다. 토스트는 상한 문구가 그대로 뜨고, 부팅 오버레이는
*"서버에 연결하지 못했어요"* 와 **따로 선다**(M2 로그가 그 화면을 실제로 찍었다).

**④ Guard 경로 — 상한이 순서를 깬 게 아니라, 상한이 없던 쪽이 인질이었다**

`boot()`은 `await loadData()` **뒤에** `syncGuardNative()`를 부른다(`app.js`).
상한이 없으면 **응답이 안 오는 것만으로 Guard 예약이 영영 안 돈다.** 검사 6이 그것을 센다 —
M1(상한을 뺀다)에서 `안옴=(false)`, 즉 예약이 안 돌았다.

**★ front 20회 중 hang 0회** (전: 4회 중 1회). 20회 전부 `404 · 실패 0`.

⚠️ **이 0회를 *"상한이 삼켰다"* 로 읽지 않는다.** 20회의 실행 시간이 **147.8~148.7초로 균일**하고
상한 문구가 뜬 회차가 **0**이다 — 상한을 한 번이라도 먹었으면 그 회차만 15초가 더 붙었어야 한다.
**이번 20회엔 워커가 안 멈춘 것이다.** 상한이 증명한 것은 *"멈춰도 앱은 빠져나온다"* 이고,
그것은 검사 1과 6이 센다. **워커가 왜 멈추는지는 여전히 안 짚었다.**

**변이 — 셋은 하나씩만, 둘은 예상보다 크게 죽였다** (기준 M0 = 404/0)

| | 변이 | 결과 | 표의 예상 |
|---|---|---|---|
| M1 | 상한을 뺀다 | 400/4 — **1·3·6 + 콘솔 오류** | *1만* ✗ |
| M2 | 상한을 0으로 | **부팅이 먼저 죽어 검사가 한 건도 안 돈다** | *2만* ✗ |
| M3 | 두 문구를 합친다 | 403/1 — **3만** | ✓ |
| M4 | 상한을 호출부로 | 403/1 — **4만** | ✓ |
| M5 | 스캐너를 눈멀게 | 403/1 — **4는 초록 · 5만** | ✓ |

⚠️ **M1·M2 가 어긋난 것은 검사가 겹쳐서가 아니라 변이가 큰 것이다.** M1 은 기능을 통째로
없애므로 상한이 있어야 성립하는 검사 셋이 다 죽는 게 맞고, **그 셋이 서로 다른 것을 센다는
증거는 M3·M4 가 따로 준다.** M2 는 *"모든 요청을 즉시 끊는다"* 라 부팅이 먼저 죽는다.
⚠️ **처음엔 1도 `timeout` 플래그를 같이 셌는데, 그러면 3을 겨냥한 M3 가 1까지 죽여
1이 자기 몫을 못 센다** — T-56 에서 겪은 그 모양이라 1을 좁혔다(플래그는 3의 몫이다).
⚠️ M1 의 `✗ 콘솔 오류 없음`은 **변이의 부산물**이다 — 상한을 빼도 `cap` 프라미스는 남아
15초 뒤 아무도 안 받는 거절이 된다. 배포될 코드에는 없는 경로다.

**하니스에 실측으로 드러난 틈 하나**

jsdom 의 `AbortSignal` 을 node `fetch` 에 넘기면 `RequestInit: Expected signal … to be an
instance of AbortSignal` 로 **모든 요청이 죽는다.** 브라우저엔 없는 틈이고 하니스가 두 런타임을
이으면서 생긴 것이라, `front.mjs` 의 fetch 다리 셋(`w`·`wx`·`w2`)을 `bridgeFetch` 하나로 모아
abort 원시값도 함께 잇는다.

**`android/guard/` 는 안 건드렸다.** 네이티브 쪽에 같은 결함이 있는지는 이 티켓에서 안 봤다.
