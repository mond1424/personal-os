## ★★★★★ 스크린샷 둘이 자리를 갈랐다

```
날짜 상세   ★ "예정" / "수업" / "일정" 섹션이 갈리고, 제목이 온전하고, 시각이 있다
            → 완벽하다. 한 글자도 안 건드린다

월간 셀     25
            [시험] 7...     ← event
            추석            ← ⚠️ 남의 것이 사이에 끼었다
            [시험] 7...     ← task
```

★★★★ **T-83이 제목을 갈랐는데 셀에서는 무효다 — 차이가 끝(`"기한"`)에 있고 끝이 잘린다.**
**함정 15 계열이다: 구별이 보이지 않는 자리에 있으면 구별이 없다.**

⚠️ **그리고 구별 축이 진하기 하나뿐이고**(T-81 ①: `700` vs `600` · `--ink` vs `--sub`),
**기간 색이 붙으면 그마저 사라진다**(둘 다 `p.color`를 우선 쓴다).

★★★ **밀도가 진짜 문제다**(T-81 ① 계산):

```
N=1   일정 1 + 할 일 1 = 2줄   ★ 같은 말을 두 번
N=2   4줄 — 셀이 꽉 찬다 (CELL_MAX_LINES=4)
```

## ★★ 명제 — 셀은 *"있다"*, 상세가 *"무엇을"*

**역할 분담이 이미 잘 돼 있다.** 그러니 **셀에서 같은 과제를 두 번 말할 이유가 없다.**

### ⚠️ 다만 *항상* 합치는 것이 아니다 — 같은 날일 때만

```
예정일 = 마감일   ⚠️ 같은 칸에 둘. 같은 말을 두 번이다     →  ★ 합친다
예정일 ≠ 마감일   ★ 다른 칸에 하나씩. 둘 다 뜻이 있다      →  ⚠️ 그대로 둔다
                    ("마감은 30일, 나는 25일에 한다")
```

★★★★★ **그것이 이 티켓에서 제일 쉬운 잘못이다** — *"task 를 셀에서 빼면 된다"* 로 읽으면
**사용자가 예정을 앞당긴 것이 화면에서 사라진다.** T-80이 만든 값이 통째로 없어진다.

### 남기는 쪽은 `event` 다

```
event  ★ 안 움직인다. 마감은 사실이다
task   움직인다 — 앞당기면 다른 칸으로 간다. 그때 둘이 갈려 하나씩 뜬다
```

⚠️ **합쳐서 잃는 것은 *"그날 할 예정"* 인데, 눌러 보면 상세가 말한다.**
★ **그 줄에 추가 표시를 얹지 않는다** — 셀은 *"있다"* 까지다.

## 할 일

### ① 먼저 확인한다 — ⚠️ 짝을 알 수 있는가

```
□ ★★ 셀을 그리는 쪽이 "이 event 와 이 task 가 같은 수집에서 왔다" 를 알 수 있는가
      · /api/calendar 응답에 그 연결이 실려 오는가
      · 안 오면 collected_items.event_id · task_id 를 어떻게 실을지
□ ★ 지금 셀의 정렬 규칙 — event 먼저 · task 뒤인가 (스크린샷이 그렇게 보인다)
□ 상세 화면(openDay)이 쓰는 경로가 셀과 같은 응답인가, 다른가
```

⚠️ **연결을 못 실으면 멈추고 보고해라.** ★ **제목으로 짝짓는 것은 답이 아니다** —
T-83이 갈라 놨고, `task.title` 은 사용자가 고칠 수 있는 칸이다(`CLAUDE.md` §아키텍처 원칙).

### ② 셀에서 — 같은 날 + 같은 출처면 `event` 만 그린다

⚠️ **`CELL_EV_MAX`·`CELL_TK_MAX` 예산 계산이 합친 뒤의 수를 봐야 한다.**
합치기 전 수로 자르면 **합쳤는데도 `+N` 배지가 남는다.**

★ **memo 예산은 건드리지 마라** — `room - memoNeed > 0` 규칙 그대로다.

### ③ 상세 화면 — **한 글자도 안 건드린다**

★★ **스크린샷이 그것이 완벽하다고 말했다.** 섹션이 갈리고 제목이 온전하고 시각이 있다.
⚠️ **거기서도 합치면 이 티켓이 잃는 것이 생긴다** — *"그날 할 예정"* 을 확인할 자리가 사라진다.

## 금지

| 하지 말 것 | 왜 |
|---|---|
| **날짜와 무관하게 합친다** | ⚠️⚠️ **예정을 앞당긴 것이 화면에서 사라진다.** T-80이 만든 값이다 |
| **상세 화면을 건드린다** | ★ 스크린샷이 완벽하다고 말했다 |
| task 를 셀에서 통째로 뺀다 | 위 첫 줄과 같은 잘못 |
| **제목으로 짝짓는다** | ⚠️ T-83이 갈라 놨고, `task.title` 은 사용자가 고친다 |
| 합친 줄에 표시를 얹는다 | 셀은 *"있다"* 까지다. **상세가 말한다** |
| 손으로 만든 event·task 를 합친다 | ★ **수집에서 온 짝만이다** |
| 예산 계산을 합치기 *전* 수로 한다 | ⚠️ 합쳤는데 `+N` 배지가 남는다 |
| memo 예산 규칙을 바꾼다 | `room - memoNeed > 0` 그대로다 |
| `CELL_MAX_LINES` 를 늘린다 | ★ 줄이는 티켓이지 늘리는 티켓이 아니다 |

## 완료 조건

```
typecheck 통과 · front +N · smoke ±N · 실패 0 · verify exit 0
★ ①의 확인 결과가 §보고에 있다 — 짝을 어디서 아는가
```

**검사**

```
1  ★ 같은 수집에서 온 event·task 가 같은 날이면 셀에 한 줄이다      ← 본체
2  ★★ 날짜가 다르면 각 칸에 하나씩 — 둘 다 뜬다                     ← 1의 짝. ⚠️ 제일 중요
3  ★ 남은 한 줄이 event 다 (task 가 아니다)
4  ★ 손으로 만든 event·task 는 같은 날이어도 안 합친다               ← 수집분만
5  ★ 상세 화면은 여전히 둘 다 보여준다                               ← 회귀
6  ★ 합친 뒤 줄 수로 예산을 잰다 (불필요한 "+N" 이 안 남는다)
7  ★ memo 가 여전히 자리를 받는다                                    ← 회귀
```

⚠️⚠️ **2가 이 티켓에서 제일 중요한 검사다.** *"수집분 task 를 셀에서 다 뺀"* 구현이
**1·3·6·7을 전부 초록으로 통과한다** — 셀은 깔끔해지고, **예정을 앞당긴 날에만 드러난다.**
★ **그리고 그 날은 사용자가 스스로 옮긴 날이라, 사라진 것을 제일 아프게 느낀다.**
⚠️ **4가 없으면 *"같은 날 같은 제목이면 합치는"* 구현이 통과한다** — 손으로 만든 짝이 먹힌다.
⚠️ **6이 없으면 합치고도 `+N` 이 남는다** — 화면에서 줄 수가 안 준다.
⚠️ **픽스처에 고정 날짜를 쓰지 마라**(함정 12).

**변이**

```
안 합친다                          → 1 만 죽는다
★★ 날짜와 무관하게 합친다          → 2 만 죽는다 (1·3·6·7 초록 — 더 깔끔해진다)
task 를 남기고 event 를 뺀다        → 3 만 죽는다
출처 조건을 뺀다 (제목·날짜로만)    → ★ 4 만 죽는다 (1은 초록)
상세에서도 합친다                   → 5 만 죽는다
예산을 합치기 전 수로 잰다          → ★ 6 만 죽는다 (1은 초록 — 합치긴 했으니)
memo 예산을 먼저 안 뺀다            → 7 만 죽는다
```

★★ **둘째·넷째·여섯째가 짝의 존재 이유다.**
★★★ **변이가 *붙었는지*와 *되돌아갔는지*를 둘 다 본다**(함정 16).
⚠️ **그리고 검사가 *저절로 참*이 되지 않았는지 본다**(`AGENT-CHAIN` §8 다섯 기제 —
**⑤ jsdom 이 계약을 안 싣는 자리**. 셀 표시는 정확히 그 자리다).

## 보고 (담당이 채운다)

### ① 짝을 어디서 아는가 — **알 수 있다. 다만 지금은 안 실려 온다** (2026-09-23)

```
□ 셀을 그리는 쪽이 짝을 알 수 있는가     →  ★ 지금은 모른다. 한 칸을 실으면 안다
□ 지금 셀의 정렬 — event 먼저 · task 뒤  →  ★ 맞다 (스크린샷이 본 그대로)
□ 상세 화면이 셀과 같은 응답인가          →  ⚠️ 다르다 — 그래서 ③이 저절로 지켜진다
```

**`/api/calendar` 가 주는 것**(`services/daily.ts:244`)은 `periods · entries · diary · events · memos` 다.

| 조각 | SQL | 짝을 아는가 |
|---|---|---|
| `entries` | `db.calEntries` — `schedule_entries ⋈ tasks ⋈ periods` | ❌ |
| `events` | `db.eventsRange` — `events ⋈ periods` | ❌ |

**둘 다 `collected_items` 를 안 탄다.** 그런데 **원장은 이미 안다** — `collected_items.event_id`(T-42) ·
`task_id`(T-78)가 한 행에 같이 있다. ★ **마이그레이션은 필요 없다**(§범위의 그 줄이 맞았다).

**그래서 `calEntries` 에 칸 하나를 얹었다** — `collected_event_id`.

```sql
(SELECT c.event_id FROM collected_items c
  WHERE c.task_id = t.id AND c.event_id IS NOT NULL LIMIT 1) AS collected_event_id
```

⚠️⚠️ **JOIN 이 아니라 상관 서브쿼리인 것이 중요하다.** `collected_items.task_id` 엔 UNIQUE 가 없다 —
같은 task 를 가리키는 행이 둘이면 `LEFT JOIN` 은 **`entries` 를 두 줄로 불리고**,
그러면 **셀에 같은 할 일이 두 줄로 뜬다.** ★ **고치려던 증상과 글자 하나까지 같은 모양**이라
합치는 코드가 멀쩡해도 화면은 그대로다. **smoke 3 이 그 자리를 지킨다.**

★ `calEntries` 를 부르는 곳은 `daily.calendar` **하나뿐**이라(전수 확인) 이 칸이 다른 화면에 안 샌다.
`daily.ts` 는 `entries.results` 를 그대로 넘기므로 **서비스는 한 줄도 안 고쳤다.**

**정렬은 그대로다** — 셀 조립이 `evByDate` 를 먼저 그리고 `tkByDate` 를 뒤에 붙인다(`app.js`).
**T-84는 순서를 안 바꾼다.** 빼는 것만 한다.

★★ **③이 저절로 지켜지는 이유**: 상세 화면(`openDay`)은 `/api/days/:date` → `daily.assembleDay` 를 쓰고
**그 응답엔 짝이 없다.** 셀과 다른 길이라 **셀을 고쳐도 상세엔 닿지 않는다** — 한 글자도 안 건드렸다.

### ② 셀에서 — 거르는 자리가 **예산보다 앞**이다

`renderCalendar` 의 `cal.entries` 루프 한 줄이다(`app.js`). 예산 계산(`rowHtml`)은 그 뒤라
**합친 뒤 수를 저절로 본다** — 따로 맞춘 것이 아니라 **자리로 지킨다.**

```js
const pairedInCell = (e) =>
  !!e.collected_event_id && (evByDate[e.date] || []).some((x) => x.id === e.collected_event_id);
...
if (!e.deferred_to && pairedInCell(e)) continue;
```

⚠️ **`!e.deferred_to` 를 왜 붙였나** — 티켓에 없던 줄이라 근거를 적는다.
옮겨간 줄은 **예정이 아니라 자취**다. 그 할 일의 예정일은 이미 다른 날이므로
§명제의 표에서 **"예정일 ≠ 마감일"** 쪽이고, 합치면 *"여기서 옮겼다"* 가 사라진다.
★ 티켓의 규칙을 **어긴 것이 아니라 그대로 적용한 것**이다.

`CELL_MAX_LINES`·`CELL_EV_MAX`·`CELL_TK_MAX`·`room - memoNeed > 0` **한 글자도 안 건드렸다.**

### ③ 상세 화면 — **한 글자도 안 건드렸다**

`openDay` 의 diff 는 0줄이다. ①에 적은 대로 **다른 응답을 쓰기 때문에** 닿을 일도 없었다.

### 검사와 변이 — ★ 돌리기 전에 예상을 적고 대조했다

**기준선 → 지금: `typecheck 통과 · smoke 494 → 497 · front 515 → 523 · 실패 0 · verify exit 0`**

변이 **아홉 전부 붙었고 아홉 전부 되돌아갔다**(스냅샷 방식 — 바이트로 확인).
⚠️ **붙는 것만 보면 절반이다**(함정 16의 T-79 줄) — 되돌리기가 죽으면 다음 변이가
오염된 트리에서 돌고 **그 수는 빨간불이라 의심을 안 산다.**

| 변이 | 예상 | 실제 | |
|---|---|---|---|
| M1 안 합친다 | front 1 · 6 | front 1 · 6 | ✅ |
| M2 **날짜와 무관하게 합친다** | front 2 만 | front 2 만 | ✅ |
| M3 task 를 남기고 event 를 뺀다 | front 3 (· 6) | front 3 · 6 | ✅ |
| M4 출처 조건을 뺀다 (제목 접두·날짜) | front 4 만 | front 4 만 | ✅ |
| M5 상세에서도 합친다 | front 5 만 | front 5 만 | ✅ |
| M6 예산을 합치기 전 수로 잰다 | front 6 만 | front 6 만 | ✅ |
| M7 memo 예산을 먼저 안 뺀다 | front 7 만 | front 7 만 | ✅ |
| M8 서버가 그 칸을 안 싣는다 | smoke 1·2 · front 9 | smoke 1·2·**3** · front 9 | ⚠️ 아래 |
| M9 서브쿼리 대신 LEFT JOIN | smoke 3 만 | smoke 3 만 | ✅ |

★★★ **M2 가 이 티켓의 값을 그대로 보여 줬다.** 죽은 검사 하나가 남긴 출력:

```
예정 2026-09-06 → (빈 칸)      ← ⚠️ 사용자가 앞당긴 날이 통째로 빈다
마감 2026-09-08 → [시험] 옮긴 과제 기한
```

**나머지 여덟 검사는 전부 초록이었고 셀은 더 깔끔해졌다.** 티켓이 *"제일 중요한 검사"* 라고
쓴 그대로다 — **2가 없으면 이 구현이 통과한다.**

#### ⚠️ 티켓의 변이표와 두 줄이 달랐다 — 둘 다 같은 원인이다

티켓은 M1·M3 을 *"1 만"* · *"3 만"* 으로 봤는데 **둘 다 6 을 함께 죽였다.**
원인은 하나다: **검사 6 은 "할 일 줄이 실제로 빠졌는가" 위에 선다.** 할 일이 칸에 남으면
`restN` 이 1 이 되어 `+1` 배지가 남는다 — 안 합치든(M1) 엉뚱한 쪽을 빼든(M3) 똑같다.

★ **이것은 겹침이 아니라 정상이다**(`AGENT-CHAIN` §8 — *"기능을 통째로 없애는 변이는 그 기능
위에 선 검사를 다 죽이는 것이 맞다"*). **가르는 물음의 답이 배터리 안에 있다:**
M6 이 **6 만** 죽이고, M1 이 1 을, M3 이 3 을 각각 데려간다 — **셋이 서로 다른 것을 센다.**

⚠️ **M8 이 smoke 3 을 함께 죽인 것도 같은 모양이다** — 칸이 아예 없으면 *"값이 그 event 다"* 도
성립할 수 없다. **M9 가 smoke 3 을 혼자 죽여** 그것이 무엇을 세는지(행이 안 분다)를 따로 보인다.

#### ★ 검사 3 에서 조각 하나를 뺐다 — 근거를 적는다

처음엔 `evt === 1 && tsum === 0` 이었다. **`tsum === 0` 은 검사 1(*"한 줄이다"*)과
`evt === 1` 에서 연역된다** — 남겨 두면 M1 이 1·3·6 셋을 죽여 **어느 결함인지 못 읽는다.**
⚠️ **빼면 무엇을 못 보게 되는가**(T-63의 물음): 못 보게 되는 것이 **검사 1 에 그대로 있다.**
그래서 뺐고, 실제로 M1 의 사망자가 셋에서 둘로 줄었다.

#### ★★ 함정 15 — 검사와 구현이 같은 이름을 공유하는 자리를 따로 막았다

front 1~7 은 **검사가 지은 픽스처**를 쓴다(`Api.calendar` 를 갈아끼운다).
⚠️ **서버가 다른 이름으로 실어 보내면 그 일곱이 전부 초록인 채 폰에서만 안 합쳐진다** —
*"선택자·키를 검사가 구현에서 복사해 오면 양쪽이 함께 틀린다"* 의 그 자리다.

★ 그래서 **front 9 가 실제 응답에 그 칸이 있는지 한 번 묻는다.** M8 이 그것을 증명했다:

```
M8 (서버가 칸을 안 싣는다)  →  front 1~7 초록 · ★ front 9 만 죽었다
```

**픽스처가 못 보는 것을 9 가 본다.** 값이 아니라 **칸의 존재**를 세므로(`"key" in row`)
수집 안 된 할 일만 있는 검사 DB 에서도 선다.

#### ⚠️ jsdom 이 계약을 안 싣는 자리는 피했다 (다섯 기제 ⑤)

셀 표시를 **CSS 로 재지 않는다** — 세는 것은 전부 **DOM 노드**(`.ev` / `.evt` / `.tsum` / `.memo` ·
`+N` 배지는 `.tsum b`)다. jsdom 이 외부 CSS 를 안 먹어도 **계약을 코드가 진다.**

#### 픽스처가 일부러 갖춘 것

- **날짜는 보고 있는 달의 04~14일**(함정 12) — 어느 달에도 있고 `weeksOf` 가 늘 6주다.
- **제목 접두를 겹쳐 놨다**: `"[시험] 붙은 과제"` ⊂ `"[시험] 붙은 과제 기한"`.
  ⚠️ **이것이 없으면 티켓의 예상이 뒤집힌다** — T-83 이 갈라 놓은 실제 제목으로는 `===` 짝짓기가
  아예 안 물어 **M4 가 4 대신 1 을 죽인다.** 접두 짝짓기가 *"순진한 구현"* 의 실제 모양이라 그쪽으로 맞췄다.
  손으로 만든 짝은 **제목이 아예 같다** — 그래서 M4 가 4 를 정확히 문다.
- **`Api.calendar` 를 통째로 갈아끼운다** — 앞 검사들이 만든 실 행이 수를 안 섞는다(§8 ③).
