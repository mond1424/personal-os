# T-54 — 캘린더가 아무것도 안 했으면 그렇게 말한다

**발행** Cowork · 2026-09-01 · **담당** Claude Code · **보통**
**근거** [T-53 §②](T-53-cal-read-device.md) 의 미완 · 2026-09-01 실측 진단 · **APK 필요 · 서버 무변경**

## 무엇이 어긋났나 — 실측된 것

**T-53의 핵심은 ②였다: *"권한이 없으면 조용하지 않다."*
그런데 사용자가 `[저장하고 지금 동기화]`를 눌렀고, 아무 일도 안 일어났고, 화면은 그것을 말하지 않았다.**

```
permission true   targets []   configured true
lastOkAt null     lastError null   lastCount -1      ← 셋 다 초기값
```

**⚠️ 원인은 결함이 아니었다 — 빈 목록이 저장된 것이다.** 읽기·보내기·창·배선은 실측으로 전부 정상:
provider 26행 · 대상 `[10]` 넣으면 `sent 5 · upserted 5`.

**★ 그래서 이 티켓은 A(왜 안 왔나)가 아니라 B(왜 그것이 안 보였나)를 고친다.**
A는 고칠 것이 없고, **B를 고치면 A가 다음번에 스스로 드러난다.**

## ★ 세 겹으로 조용했다 — 그리고 넷째는 로그가 없다

### ① 빈 선택 저장이 막히지도, 말해지지도 않는다

```
save.onclick 은 ids.length === 0 을 안 본다
CalPlugin.setTargets 는 빈 배열을 정상 저장으로 처리한다
시트가 닫히는 것이 유일한 피드백이고 — 그것은 성공 신호로 읽힌다
```

⚠️ **"안 고르고 저장"과 "선택 해제"가 같은 연산이다.** 뜻이 정반대인데 화면에 가르는 말이 없다.

### ② `skipped`가 화면까지 안 온다

**네이티브는 `no_target`을 성실히 실어 보내는데** `calSyncNow`의 `else` 가지가 `r`을 통째로 버리고
`loadCalStatus()`만 부른다. **그 둘은 설계상 prefs에 흔적을 안 남기므로**(*"실패가 아니다"*)
다시 그린 줄은 **저장 누르기 전과 글자 하나 안 다르다.**

### ③ (잠복) `sent === 0`을 성공으로 말한다

`r.ok && r.sent === 0`이면 **초록 토스트 `캘린더 0건을 맞췄어요`**가 뜬다.
**휴일 캘린더만 고르면 바로 이 모양이다** — T-43이 `0건`과 로그인 HTML을 가른 그 자리와 같다.

### ④ ★ `cal/` 셋에 `Log` 호출이 0건이다

**화면이 조용하면 로그라도 남아야 하는데 둘 다 없었다.** `guard/`는 `noteFire`로 흔적을 남긴다 —
**같은 문제를 이미 한 번 겪은 자리다.**

## 할 일

### ★ 원칙 하나로 묶는다 — 시도는 언제나 흔적을 남긴다

```
성공 · 스킵 · 실패  →  셋 다 "마지막 시도의 결과"로 남는다
```

⚠️ **지금은 `lastOkAt`·`lastError`·`lastCount` 셋뿐이라 `skipped`가 갈 곳이 없다.**
그것이 ②의 뿌리다 — **prefs에 자리가 없으니 화면도 못 읽는다.**

### ① 빈 선택 — 막거나 말한다

**담당이 고른다. 근거를 보고에 적는다.**

```
(a) 저장을 막고 그 자리에서 말한다        "하나 이상 골라 주세요"
(b) 저장은 허용하되 결과를 말한다         "선택을 해제했어요 — 이제 아무것도 안 가져와요"
```

⚠️ **(b)를 고르면 "해제"가 의도된 행동으로 남는다** — 그것도 사용자가 할 수 있는 일이다.
어느 쪽이든 **시트가 조용히 닫히는 지금의 모양은 안 된다.**

### ② 결과를 화면까지

`calSyncNow`가 `r`을 버리지 않는다. **`skipped`·`sent`·`upserted`가 사용자에게 닿는 경로를 만든다.**

⚠️ **상태 줄(`#td-cal`)과 섞지 마라.** 그것은 *"지금 어떤 상태인가"*이고, 이건 *"방금 한 행동의 결과"*다.
**T-53이 `calStatusLine` 하나로 상태를 정한 구조는 그대로 둔다** — 두 곳에서 정하면 갈라진다.

### ③ `sent === 0`은 성공이 아니다

```
sent 0 · ok true   →  "가져올 일정이 없었어요 (대상 N개 · 창 M일)"   ← 초록 아님
sent 5 · ok true   →  "일정 5개를 맞췄어요"
```

**0이 왜 0인지를 함께 말한다** — 대상 수와 창을 보이면 *"휴일 캘린더만 골랐다"*가 그 자리에서 드러난다.

### ④ ★ `cal/`에 흔적

**`guard/`의 `noteFire`와 같은 급으로.** 최소한 **마지막 시도의 사유가 `Cal.status()`에 실려야** 한다 —
그래야 화면이 안 보여도 CDP 한 줄로 갈린다.

⚠️ **`Log`만 늘리는 것으로 끝내지 마라.** logcat은 개발자만 보고, **이 결함의 피해자는 사용자다.**

## 범위

```
android/.../cal/CalSync.kt · CalPlugin.kt    시도 결과 기록 · status 노출
public/app.js · index.html                  빈 선택 · 결과 표시
test/front.mjs                              검사
```

**서버 무변경 · 마이그레이션 없음.**

⚠️ **`calStatusLine`의 상태 넷(`noperm`·`notarget`·`error`·`ok`)을 늘리지 마라.**
결과는 상태가 아니다 — 섞으면 T-53이 세운 것이 무너진다.

⚠️ **`guard/` 아래를 안 건드린다.** T-53의 `GuardSync.kt` 한 줄은 그대로 둔다.

## 금지

| 하지 말 것 | 왜 |
|---|---|
| 빈 선택을 조용히 저장 | **①이 이 티켓의 시작점**이다 |
| `sent === 0`에 초록 토스트 | **0건과 실패가 안 갈린다**(T-43) |
| 결과를 상태 줄에 합치기 | 상태와 행동 결과는 다른 것이다 |
| `calStatusLine` 상태 늘리기 | 넷이 곧 `CAL_ACT`의 넷이다. 구조가 무너진다 |
| `Log` 만 늘리고 끝내기 | **피해자는 사용자다.** logcat 은 안 본다 |
| A(빈 목록) 를 "고치려" 들기 | **결함이 아니다.** B 를 고치면 다음번에 드러난다 |
| 경합이 있는 신호로 검사 짜기 | ⚠️ 토스트가 그것이다 — 담당이 직전 커밋에서 물렸다 |

**검사**

```
1  빈 선택으로 저장하면 그 사실이 사용자에게 닿는다
2  ★ 하나 이상 고르면 닿지 않는다                        ← 1의 짝
3  ★ sent === 0 이 성공 문구로 안 나온다
4  ★ sent > 0 은 성공 문구로 나온다                      ← 3의 짝
5  ★ skipped(no_target) 가 화면까지 온다 — 저장 전후로 화면이 달라진다
6  Cal.status() 에 마지막 시도의 사유가 실린다

```

**1·2와 3·4가 각각 짝이다.** 1만 보면 *"항상 경고하는 구현"*이, 3만 보면
*"성공도 실패처럼 말하는 구현"*이 통과한다.

**5가 이 티켓의 본체다.** *"저장 전후로 화면이 달라진다"*를 세라 — **글자가 같으면 실패다.**

⚠️ **검사 신호에 토스트를 쓰지 마라.** `until`이 `refreshToday()`의 DOM 쓰기를 보고 먼저 빠져나와
**던지기 전에 읽는다** — 담당이 직전 커밋에서 실측했다. **호출을 세거나 상태를 세라.**

**변이**
- 빈 선택 경고를 뺀다 → **1만** 죽는다
- 항상 경고한다 → **2만** 죽는다
- `sent 0`에 성공 문구 → **3만** 죽는다
- `sent > 0`에도 실패 문구 → **4만** 죽는다
- `calSyncNow`의 `else`에서 `r`을 다시 버린다 → **5만** 죽는다
- `status`에서 사유를 뺀다 → **6만** 죽는다

### ① 빈 선택 — **(a) 막았다**

**(b)를 이 티켓 범위에서 안전하게 못 만든다.** 대상을 비우면 `syncNow`가 `no_target`으로 **먼저**
빠져나가므로 **서버 미러가 정리되지 않는다.** *"해제했어요"* 라고 말한 뒤 창 안의 devcal 일정이
영원히 남는 것은 **조용한 실패를 하나 더 만드는 것**이고, 이 티켓이 고치려는 바로 그 부류다.

치우려면 빈 배치를 보내야 하는데, 그러면 **대상이 없는 새 설치가 서버 미러를 지운다** —
T-53 ③(*"선택 전에는 아무것도 안 가져온다"*)과 정면으로 부딪힌다.

⚠️ **그래서 '해제' 간선은 지금 UI에 없다. 이건 이 티켓이 만든 빚이다** — 별도 티켓이 필요하다
(대상을 비울 때 빈 배치로 미러를 치우고, 그 경로를 *"새 설치"* 와 구별하는 신호가 함께 있어야 한다).
`CalPlugin.setTargets`는 빈 배열을 그대로 받으므로 **API 층의 간선은 살아 있다**(진단 때 그것으로 원복했다).

### ② `r`을 어디까지 가져왔나 · 상태 줄과 어떻게 갈랐나

`calSyncNow`가 `r`을 **`calResultLine(r)` → `showCalResult()`** 로 화면까지 가져온다.
`skipped`·`sent`·`error`가 전부 문구로 갈린다.

**상태와 결과는 함수·자리·재료가 전부 다르다:**

| | 상태 | 결과 |
|---|---|---|
| 함수 | `calStatusLine(st)` (그대로) | `calResultLine(r)` (신설) |
| 재료 | `Cal.status()` — 지금 어떤 상태인가 | `Cal.sync()`의 반환 — 방금 무슨 일이 있었나 |
| 자리 | `#td-cal` (Today 한 줄) | `#cal-result` (시트 안 한 줄) |
| 수명 | 상태가 바뀔 때까지 | 다음에 시트를 열면 지워진다 |

`calStatusLine`·`CAL_ACT`는 **한 글자도 안 건드렸다** — 검사 7이 그것을 센다.
`blocked`만 웹이 만드는 재료다(저장을 막은 것은 기기가 아니라 화면이 한 일이다).

### ④ 흔적을 prefs의 무엇으로 남겼나 · `status`가 무엇을 말하나

`cal_last_try` **한 줄(JSON)** — `guard/`의 `noteFire`(`last_fire`)와 같은 모양이다.

```json
{ "at": "2026-09-01T04:50:17Z", "outcome": "skipped", "sent": 0, "reason": "no_target" }
```

`outcome`은 `ok`·`skipped`·`error` 셋뿐이고 **`syncNow`의 모든 출구가 `noteTry`를 지난다**
(`skip()`·`fail()`·성공 경로). `Cal.status()`가 `lastTry`로 그대로 돌려주므로
**화면이 안 보여도 CDP 한 줄로 갈린다** — 2026-09-01 진단이 `Cal.status()` 하나로 (a)~(e)를
가른 그 자리다. `Log.i(TAG, …)`는 **덤으로만** 넣었다(§금지: 피해자는 사용자다).

⚠️ **키를 넷으로 쪼개지 않았다** — 갱신이 원자적이지 않으면 새 `outcome` 옆에 낡은 `sent`가
붙는 순간이 생긴다. `lastError`와도 **합치지 않았다**: 합치면 `no_target`이 '실패'로 적히고
그 순간 상태 줄이 *"동기화 실패"* 로 거짓말한다.

**`CalPlugin.kt`는 안 고쳤다** — `sync()`가 이미 `ok`·`sent`·`error`·`skipped`·`status`를 전부
싣고 있었고, `status`에 `lastTry`가 붙으면서 다리는 자동으로 넓어졌다. 범위에 적혀 있어도
**고칠 것이 없으면 안 고친다.**

### 검사 5가 "저장 전후 화면이 다르다"를 실제로 세는가

**센다. 토스트를 안 썼다.** 앞뒤로 `#cal-result`를 집어 `t54Skip.text !== t54Before5.text`를 본다 —
그리고 앞을 `showCalResult({kind:"",text:""})`로 **명시적으로 비운 뒤** 잰다.
*"비어 있지 않다"* 로만 세면 앞이 이미 차 있을 때 그 검사는 아무것도 안 본다.

신호로 쓴 것은 둘뿐이다: **`#cal-result`(사라지지 않는다)** 와 **플러그인 호출 기록**(`set:7|sync`).
검사 1은 *"아무 일도 안 일어났다"* 를 `calls === ""`로 세므로 **막았다는 말이 실제와 맞는다.**

`calResultLine(r && r.ok ? r : null)`, 즉 **실패·스킵일 때만 `r`을 버린다.** 3·4는 `ok:true`라 안 죽는다.

### ⚠️ 배터리가 잡은 것 하나 — **내 직전 커밋의 검사가 진짜로 새고 있었다**

M2·M4·M7 1차에서 `★ [추가]가 조용히 실패하지 않는다`(T-53 진단 커밋)가 함께 죽었다.
**셋 다 그 절과 무관한 자리를 건드리는 변이**이고 M3·M5·M6에서는 살아 있었다.

**처음엔 부하 탓으로 읽고 대기를 4초 → 20초로 늘렸다. 틀렸다 — M4에서 또 죽었다.**
대기를 늘리는 것은 경합을 없애는 것이 아니라 미루는 것이다. 시계를 빼고 `onclick()`이 주는
`run(...)` 프라미스를 직접 기다리자 **진짜 원인이 그대로 찍혔다**:

```
invalidate|render|invalidate|render      ← 한 벌이어야 하는데 두 벌이다
```

★ **바로 위 검사 `④`가 `click()`으로 띄운 핸들러가 아직 날고 있었다.** ④의 대기(`until`)는
`refreshToday()` **도중에** 바뀌는 DOM 문구를 보고 빠져나오므로, 통과한 뒤에도 그 핸들러의
`invalidate`·`render`가 **나중에** 도착해 다음 검사의 스파이에 섞인다. 부하는 그 도착 순서만
바꿨을 뿐이고, `until(calls.length >= 2)`는 **남의 한 벌을 자기 것으로 세고 초록이 되기도 했다.**

고친 것: **④와 ★ 둘 다 `click()` → `await …onclick()`.** 시계가 사라지고 `until` 둘이 없어졌다.
T-54의 검사 1·2도 같은 모양으로 짰다(§금지의 *"경합이 있는 신호"*가 토스트만이 아니었다).

★ **변이 배터리가 자기 목적 밖의 것을 잡았다** — *"이 변이는 이 검사와 무관한데 왜 죽지"*가
그 신호다. 짝이 안 맞는 것을 넘기지 않은 덕이고, **첫 진단(부하)을 실측이 반증한 것이 더 중요하다.**

### ⚠️ 배터리 자신도 한 번 물렸다 — STATE.md가 경고한 그것

1차 러너가 `M3` 앵커를 못 찾고 멈췄다. **`public/app.js`는 CRLF인데 앵커에 `\n`을 썼다** —
T-52 때 *"`from`에 개행을 넣은 둘은 CRLF 트리에서 아예 안 맞았다"*와 **같은 함정**이다.
이번엔 **조용히 넘어가지 않고 멈췄다**(앵커가 정확히 1번 걸리지 않으면 중단 + 복원).
복원은 매 회 `sha256` 대조로 확인한다 — 1차 배터리가 누적 오염으로 깨진 그 자리를 막는다.
