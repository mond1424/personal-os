# T-36 — 검사 날짜를 상대로 잡는다

**발행** Cowork · 2026-08-14 · **담당** Claude Code · **작음 · 지금**
**상태** 🟡 **구현·보고 완료 (2026-08-14)** · **검토 대기** · 검사만 — 소스 무변경

---

## 무엇이 터졌나

**smoke가 292/11이다. 회귀가 아니라 달력이 fixture를 따라잡았다.**

```
test/smoke.ts:453   { date: "2026-08-15", time: "09:00" } + protect_from: "-1d 00:00"
                  ⇒ 보호 구간 = 08-14 00:00 ~ 08-15 09:00
```

**오늘이 그 안이다.** `protecting === null` 검사가 깨지고, 하향 차단(ADR-027)이 발동해
모드 검사가 줄줄이 따라 죽는다. T-35 담당이 자기 변경을 stash하고 깨끗한 트리에서
**같은 292/11**을 확인했다 — T-35와 무관하다.

## 왜 지금 고치나

**빨간 검사가 일상이 되면 다음 회귀를 못 본다.** 11건이 상시 빨간불이면
`npm run verify`가 신호를 잃고, 그 상태로 9월 실사용에 들어가면 그때의 진짜 회귀가
이 11건에 섞여 안 보인다.

**T-12가 같은 것에 물렸고 `front.mjs`는 그때 손질됐다.** `smoke.ts`엔 안 됐다 —
**고정 날짜는 언젠가 반드시 현재가 된다**(CLAUDE.md 함정 12).

## 할 일

**`smoke.ts`의 고정 날짜를 상대로 바꾼다.**

기준은 응답이 주는 값이다 — `GET /api/guard/schedule`의 `d`, 또는 라우트가 넘긴 `t.d`.
**검사가 날짜를 스스로 계산하지 않는다**(T-05·T-26이 역산식을 다시 구현하지 말라고 한 것과 같다).

**§6.1의 `01:30` 예시는 유지된다** — 그것은 *역산 결과*이지 달력 날짜가 아니다.
`09:00 − 90 − 360`이 데드라인을 정하는 구조는 그대로 두고, **어느 날의 09:00인지만** 상대로 바꾼다.

## 범위

```
test/smoke.ts   fixture 날짜
```

**소스·프런트·마이그레이션 무변경.** 검사가 보는 것을 바꾸지 않는다 —
**같은 것을 언제 돌려도 같게 보도록** 만드는 것뿐이다.

## 금지

| 하지 말 것 | 왜 |
|---|---|
| 실패하는 검사를 지우거나 느슨하게 | 검사는 옳다. **날짜가 틀렸다** |

| 고정 날짜를 다른 미래로 옮기기 | **같은 폭탄을 다시 심는 것이다** |

### 11건이 정말 한 원인이었나

**그렇다. 한 줄이었다.** `smoke.ts:453`의 일정 하나를 상대로 바꾸자 **11건이 한꺼번에** 초록이 됐다.
연쇄는 이랬다:

```
보호 구간이 오늘을 덮는다
  → 'protecting=null' 검사 하나가 깨지고               (직접 원인 1건)
  → 하향 차단(ADR-027)이 발동해 secretary 전환이 막힌다  (여기서 10건이 딸려 죽었다)
```

**하나가 남지 않았다** — 원인이 하나였다는 뜻이다(§완료 조건 1번의 취지).

⚠️ **다만 첫 시도에서 다른 하나를 죽였다 — 피해야 할 시계가 둘이었다.**
`D+3`으로 고치자 11건은 전부 돌아왔는데 **T-23 검사가 죽었다**(305/1):

```
gEv 보호 구간 = (gEvDate − 1) 00:00 ~ gEvDate 09:00
피해야 할 것 ①  실시각 = D
피해야 할 것 ②  T-23이 **주입하는 시계** = gNow.start + 1분 = D+2 09:01
D+3 ⇒ 구간이 D+2 00:00에 시작해 ②를 삼킨다 → "주입한 t를 따른다"가 빨간불
D+4 ⇒ 구간 D+3 00:00 ~ D+4 09:00 — 둘 다 밖
```

**그 검사가 일했다.** "넘겨받은 `t`를 따르는가"를 보는 검사가 **내 fixture 선택이 그 t를 오염시킨 것**을
잡아냈다. 고정 날짜를 상대로 바꿀 때 봐야 할 것은 *"오늘을 피했나"*만이 아니라
**"이 파일이 주입하는 모든 시계를 피했나"**다 — 그 이유를 코드 주석에 남겼다.

### 상대 기준을 어디서 받았나 · 검사가 다시 계산하지 않는가

**`const D = t0.d`(`smoke.ts:55`) 하나다.** `loadTime(env)`이 준 귀속일이고,
파일이 이미 `addDays(D, n)`으로 상대 날짜를 쓰고 있었다 — **guard 절만 고정이었다.**

| 자리 | 전 | 후 | 그 자리의 성질 |
|---|---|---|---|
| `:453` 일정 | `2026-08-15` | `addDays(D, 4)` | 보호 구간이 **어느 시계도 안 덮는다** |
| `:613` 발동 | `2026-08-15T01:30` | `` `${gEvDate}T01:30` `` | 그 일정의 **데드라인**(09:00−90−360) |
| `:618` 기대 | `=== "2026-08-14"` | `=== addDays(gEvDate, -1)` | 01:30은 경계 아래 → **전날** |
| `:652` 멱등 | `2026-08-15T02:00` | `` `${N1}T02:00` `` | **유예 36시간 안쪽** |
| `:674` UTC | `2026-08-15T05:00Z` | `` `${N1}T05:00Z` `` | KST 14:00 → **당일** |
| `:686` 무반응 | `2026-06-01T02:00` | `` `${D_3}T02:00` `` | **유예를 넘긴 쪽** |

**검사는 데드라인을 다시 계산하지 않는다**(§금지 둘째). `01:30`은 그대로 리터럴이고
— 그것은 *역산 결과*이지 달력 날짜가 아니다 — **간격 450분을 보는 검사도 손대지 않았다.**
바뀐 것은 **어느 날의 09:00인지**뿐이다. 기대값도 값이 아니라 성질로 적었다:
`addDays(gEvDate, -1)`은 *"전날"*을 말하지 특정 날짜를 말하지 않는다.

### 재발을 막는 것 — 검사가 자기 소스를 훑는다 (§완료 조건 2번)

**고치는 것만으로는 다음에 또 심는 것을 못 막는다.** 스캐너를 붙였다:

```
① 코드 줄에 20\d\d-\d\d-\d\d 가 있으면 실패          — 주석과 순수 함수 인자는 제외
② ★ 스캐너가 살아 있는가 (합성 줄을 실제로 잡는가)
③ 순수 함수에 넘기는 고정 시각은 다섯 줄 그대로인가
```

**②가 ①의 짝이다.** *"0건"*을 세는 검사는 **스캐너가 죽어도 0이 나온다**(AGENT-CHAIN §5) —
합성 줄 하나를 넣어 **잡는 것을 확인한다.** ③은 T-26의 자리다: 시간 블록이 통째로 사라져도
①은 조용히 초록이므로 **"몇이다"를 함께 센다.**

⚠️ **합성 줄의 날짜는 일부러 이어 붙였다**(`"20" + "26-08-15"`) — 그대로 적으면
**①이 자기 자신을 잡는다.** 검사가 자기 소스를 읽는 구조의 대가이고, 주석에 이유를 남겼다.

**고정 날짜가 허용되는 유일한 자리를 정의했다: 순수 함수에 넘기는 시각 인자**
(`attributionDate`·`isoNow`·`mondayOf`). 그 함수들은 시계를 읽지 않고 인자만 보므로
달력이 따라잡을 수 없다 — **오히려 고정이어야** 30일 달·윤년을 날짜와 무관하게 검사한다(T-12).
