## ★★★ 무엇이 어긋났나 — 자동화가 절반에서 끊긴다

**2026-09-17 화면 셋을 나란히 놓으면 보인다:**

```
Calendar   9/19 "2주차…"  ·  11/30 학기과제 …        ← 들어와 있다
Today      TODO 0 · "오늘 담긴 할 일이 없어요"        ⚠️ 비어 있다
Works      "예정된 task가 없어요"                     ⚠️ 비어 있다
```

**uclass 에서 과제 5건이 수집됐고 2건은 `accepted` 인데, 할 일 목록은 0이다.**

★★★★ **`POST /api/collected/:id/accept` 가 `events` 행 하나만 만들기 때문이다**
(`docs/api-surface.md` — *"`events` 행 하나를 만든다(`title` = `summary` 원문 그대로 ·
`date`·`time` = `starts_at`)"*). **task 를 안 만든다.**

⚠️ **그래서 과제는 *"달력에 적힌 날짜"* 로만 존재하고, *"내가 해야 하는 일"* 로는 존재하지 않는다.**

### ★★ 왜 이것이 지금 제일 큰가 — 사용자 판정이 순서를 정했다

**2026-09-17 사용자:**

> *"analysis 를 사용하지 않는 이유는 — **내가 기록을 열심히 하지 않았기 때문에**
> 분석도 하고 싶지 않았어서야."*

★★★ **적극성 3칸에서 막힌 칸이 ②(넣기가 비싸다)이고, ③(값이 안 온다)은 아직 시험조차 안 됐다.**
**분석이 쓸모없다고 판정된 것이 아니라 *판정할 재료가 없었다.***

★★★★ **그러므로 첫 수는 *"사용자가 아무것도 안 해도 재료가 쌓이게"* 하는 것이다.**
**이미 자동으로 들어오는 과제가 할 일이 되면, 손을 안 대도 원장이 채워진다.**

## ★ 그런데 `event` 와 `task` 는 다른 것이다 — 둘 다 만든다

⚠️ **설계 §1.7이 `events` 를 *캘린더 전용 · 완료·이월 없음* 으로 두었다.** 과제는 **둘 다**다:

```
event   11/30 23:59 학기과제 기한        ★ 마감. 안 움직인다
task    "학기과제"                        ★ 할 일. 언제 할지는 움직인다
```

★★★ **마감은 고정이고 할 일은 이동한다** — 설계가 *"미루기는 복사가 아니라 같은 일의 이동"*
이라고 한 것이 그 구분이다. **하나로 합치면 둘 중 하나를 잃는다.**

### ★★ 새 task 의 예정일 — **안 정한다. 대기로 넣는다**

```
마감일에 넣는다   ⚠️ "마감일에 하라"는 뜻이 된다. 거짓이고 나쁜 조언이다
대기(미배정)      ★ "할 일은 있고 언제 할지 안 정했다" — 실제 상태 그대로다
```

**대기는 설계에 이미 있다**(1.4 · 21일 규칙). **날짜는 사용자가 정한다.**

## 할 일

### ① 먼저 확인한다 — 30초

```
□ accept 가 정말 task 를 안 만드는가 (코드로)
□ events 와 tasks 를 잇는 칸이 이미 있는가 (source_event_id 같은 것)
□ 지금 accepted 2건에 대응하는 task 가 정말 없는가 (원격 D1 읽기)
```

⚠️ **있으면 이 티켓의 전제가 틀렸다. 멈추고 보고해라**(`AGENT-CHAIN` §8 — 티켓의 전제도 변이 대상).

### ② `accept` 가 task 도 만든다

```
event   지금 그대로 (title·date·time — 바꾸지 마라)
task    ★ 새로. 제목은 summary 원문 그대로 · 예정일 없음(대기)
```

★ **과목을 task 에 어떻게 실을지**는 `categories` 가 이미 있으니(T-74) 쓸 수 있다.
⚠️ **다만 원문을 쪼개는 것은 표시하는 쪽이다** — 저장은 T-74 규칙 그대로.

⚠️ **멱등을 깨지 마라** — `accept` 는 이미 멱등이다(`duplicate:true`). **task 도 두 번 안 생겨야 한다.**
★ **둘을 잇는 방법이 필요하면 그것이 이 티켓의 유일한 마이그레이션이다.**

### ③ 이미 `accepted` 인 2건은 **손대지 않는다**

⚠️ **과거 행을 소급해서 만들지 않는다** — *"수집된 것"* 과 *"내가 넣은 것"* 이 섞인다(T-74 §확인 절차와 같은 규칙).
★ 그 둘은 이미 지난 과제다. **판정은 다음에 수락하는 건으로 한다.**

## 금지

| 하지 말 것 | 왜 |
|---|---|
| **event 를 없애고 task 만 만들기** | ⚠️ **마감이 달력에서 사라진다.** 둘은 다른 것이다(설계 §1.7) |
| task 의 예정일을 **마감일로** 넣기 | ⚠️ *"마감일에 하라"* 는 거짓 조언이다 |
| 제목을 고치거나 다듬기 | **원문 그대로**(T-74 · `summary` 규칙) |
| 이미 accepted 인 건을 소급 생성 | 수집된 것과 넣은 것이 섞인다 |
| task 생성 로직을 새로 짜기 | ★ **기존 경로를 쓴다.** `deferTask`·`completeTask` 의 하드-원 지식과 갈라진다 |
| 멱등 깨기 | `accept` 는 이미 멱등이다. task 가 두 번 생기면 안 된다 |
| `dismiss` 에 손대기 | 이 티켓 밖이다 |

**검사**

```
1  ★ accept 하면 events 1 · tasks 1 이 생긴다                ← 본체
2  ★ 그 task 에 예정일이 없다 (대기)                          ← "마감일에 하라"를 막는다
3  ★ 두 번 accept 해도 task 가 하나다                         ← 멱등. 1의 짝
4  ★ task 제목이 summary 원문 그대로다                        ← 해석 금지
5     event 는 전과 똑같다 (title·date·time)                  ← 회귀
6  ★ dismiss 는 아무것도 안 만든다                             ← 경계
```

⚠️ **2가 없으면 *"마감일에 예정을 박는"* 구현이 통과한다** — 화면에는 할 일이 생기니까
1만 보면 초록이다. **그게 이 티켓에서 제일 쉬운 잘못이다.**
⚠️ **3이 없으면 멱등이 깨진 것을 아무도 못 센다** — `accept` 가 이미 멱등이라 **event 쪽은
초록인 채로 task 만 늘어난다.**
⚠️ **픽스처에 고정 날짜를 쓰지 마라**(함정 12).

**변이**

```
task 를 안 만든다              → 1 만 죽는다
예정일을 마감일로 넣는다        → 2 만 죽는다 (1은 초록 — task 는 생겼으니)
멱등 가드를 task 에 안 건다     → 3 만 죽는다
제목을 다듬는다                 → 4 만 죽는다
event 의 title 을 바꾼다        → 5 만 죽는다
dismiss 에서도 task 를 만든다   → 6 만 죽는다
```

⚠️ **둘째 변이가 1을 안 죽이는 것이 2의 존재 이유다** — `AGENT-CHAIN` §판정의
*"검사 하나가 두 명제를 담으면 변이가 절반을 안 태운다"* 를 미리 갈라 둔 것이다.
★ **돌려 보고 안 태워진 절반이 있으면 변이를 늘려라**(T-76 ①에서 실제로 났다).

## ★ 이 티켓이 안 하는 것

- **날짜 정하기를 쉽게 만들지 않는다.** ⚠️ 그것이 다음 물음이고,
  **재료가 쌓인 뒤에 마찰을 재는 것이 순서다.**
- **놓친 제안을 다시 보는 자리**는 안 만든다(T-75).
- **자동으로 예정일을 정해 주지 않는다** — 그것은 해석이고, 지금 근거가 없다.
- **이미 달력에 있는 다른 `events`(수업·개인 일정)를 task 로 만들지 않는다.**
  ⚠️ **수락한 수집 항목만**이다. 수업은 시간표가 관리한다.

### ② 무엇을 했나
