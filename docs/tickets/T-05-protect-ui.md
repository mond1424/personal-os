# T-05 — 일정에 보호 규칙 걸기 (UI)

**발행** Cowork · 2026-07-30 · **담당** Codex CLI · **상태** ✅ **닫힘 (2026-08-03)**

> 확인 절차 4번(`G.sync()` → `G.listAlarms()`)까지 실측 완료.
> **시각 발동 경로가 화면에서 알람까지 이어진다** — 이 티켓의 진짜 완료 조건이었다.

---

## 목표

일정 편집 화면에서 **보호 규칙을 걸고 풀 수 있게** 한다.

**왜** — Guard의 발동 경로는 둘인데(ADR-025), 그중 **경로 A(시각)가 콘솔로만 걸린다.**
`PUT /api/events/:id/protect`는 완성돼 있고 smoke가 지키고 있는데 **화면이 없다.**
그래서 지금 Guard는 감지 경로 하나로만 돌고, 시험 전날 데드라인 역산이라는
설계 §6.1의 본보기 시나리오가 실사용에서 한 번도 일어나지 않는다.

## 쓸 API — 이미 있다

```
PUT /api/events/:id/protect
  걸기:  { protect_from?, protect_level?, protect_sleep_min?, protect_prep_min? }
  풀기:  { protect: false }
```

| 필드 | 기본 | 제약 |
|---|---|---|
| `protect_from` | `"-1d 00:00"` | `'-1d 00:00'` 꼴. 일정 시각 **기준 상대**. 서버 정규식이 거부하면 400 |
| `protect_level` | `4` | 1~4 정수 |
| `protect_sleep_min` | `null`(→ 360) | 0~1440 정수 |
| `protect_prep_min` | `null`(→ 90) | 0~1440 정수 |

`api.js`에 `setProtect`가 없으면 추가한다. `_req`를 쓴다 — `fetch` 직접 호출 금지.

## 화면

기존 **일정 시트(`openEventSheet`)** 안에 접히는 영역 하나로 붙인다. 새 시트를 만들지 않는다.

- 기본은 **꺼짐**. 대부분의 일정은 보호 대상이 아니다
- 켜면 네 값이 나오되 **전부 기본값이 채워져 있어** 그대로 저장할 수 있다.
  네 칸을 다 채우게 만들면 아무도 안 쓴다
- **데드라인을 미리 보여준다.** `일정시각 − 준비 − 수면`을 프런트에서 계산해
  "01:30에 자야 합니다"처럼 표시한다. 이게 이 UI의 핵심이다 —
  숫자 세 개보다 **결과 시각 하나**가 판단을 만든다
- 보호가 걸린 일정은 **목록·캘린더에서 알아볼 수 있어야** 한다(작은 표시 하나)
- 푸는 경로가 분명해야 한다

**데드라인은 표시만 계산한다. 저장하지 않는다** — 파생값은 저장하지 않는다(아키텍처 원칙 1).
서버의 `guard.schedule()`이 조회 시 같은 식으로 역산한다.

## 금지

| 하지 말 것 | 왜 |
|---|---|
| `protect_*` 값을 프런트에서 파생 저장 | 원칙 1. 데드라인은 조회 시 계산이다 |
| 새 시트·새 모달 패턴 | 기존 `openEventSheet`·`.sec` 구조를 쓴다 |
| `scrollIntoView` | `.phone`이 `overflow:hidden`이라 셸이 밀린다. 위치는 `scrollTop`만 |
| 짧고 일반적인 새 클래스명(`prot`·`pf`·`on`·`lv`) | 전역 충돌로 **세 번 물렸다.** CSS·JS 양쪽 `grep` 후 접두사 |
| 색 리터럴 | CSS 변수만. 다크 대응은 항상 짝 |
| 서버·마이그레이션 수정 | 위임 금지 영역. 서버는 완성돼 있다 |
| `boot()` 중복 실행 가드(`booted`) 제거 | 스와이프 한 번에 탭 두 칸 |

## 읽을 것

- 설계 §6.1 — Level별 개입과 "09:00 시험 → 01:30" 예시. **이 UI가 만드는 것이 그 시나리오다**
- 설계 §6.2 — 사전 서약. 보호 규칙은 **계획**이라 마감된 날에도 붙일 수 있다(서버가 본문 수정과 분리한 이유)
- `src/services/events.ts` `setProtect` — 400을 내는 조건 전부
- `src/services/guard.ts` `schedule()` — 데드라인 역산식과 `protect_from` 파싱
- `CLAUDE.md` 함정 1·5·7

## 완료 조건

```
typecheck 통과 · smoke 233(변화 없음) · front 185 → 190 이상 · 실패 0
```

검사에 들어가는 것:

1. 보호를 걸면 `PUT .../protect`가 **올바른 본문으로** 나간다 (기본값이 실제로 실린다)
2. **데드라인 미리보기가 입력에 따라 바뀐다** — 수면 360 → 300으로 고치면 표시가 1시간 뒤로 간다.
   고정 문자열을 확인하는 검사는 계산과 구별되지 않는다
3. 푸는 경로가 `{ protect: false }`를 보낸다
4. 잘못된 `protect_from`을 넣으면 저장 전에 막힌다 (서버 400 이전에 프런트에서)

**숫자만 늘고 잘못된 동작을 지키는 검사는 없느니만 못하다.**

## 확인 절차 (사용자)

deploy 후 폰에서. APK 재빌드 불필요.

1. 09:00 일정을 만들고 보호를 켠다 → 데드라인이 **01:30**으로 뜨는지
2. 수면을 300분으로 고친다 → **02:30**으로 바뀌는지
3. 저장 후 목록·캘린더에서 보호 표시가 보이는지
4. 앱 콘솔에서 `await G.sync()` → `await G.listAlarms()` — 그 일정의 발동이 예약됐는지
5. 보호를 푼다 → 표시가 사라지고, 재동기화 후 예약도 사라지는지

**4번이 이 티켓의 진짜 완료 조건이다** — 화면이 아니라 알람까지 이어져야 경로 A가 산다.

`services/guard.ts`의 데드라인 역산식을 **프런트가 다시 구현**하는 티켓이라, 두 구현이 갈라지면

확인해 보니 **그 위험이 이미 막혀 있다.**

### 티켓이 말하지 않은 함정 셋 — 여기가 실제 위험이다

**① 종일 일정은 09:00으로 본다.** `guard.ts:66` — `const hhmm = e.time ?? "09:00"`.
시각 없는 일정의 미리보기를 "시각 없음"으로 비워 두거나 00:00으로 계산하면 **서버와 어긋난다.**
프런트도 같은 폴백을 쓴다.

**② `protect_from` 정규식을 새로 짜지 않는다.** 서버(`events.ts:66`)가 쓰는 것 그대로:

```js
/^([+-]?\d+)d\s+([01]\d|2[0-3]):([0-5]\d)$/
```

`trim()` 후 검사하는 것까지 같다. 손으로 다시 쓰면 그게 갈라지는 자리다.

**③ `protect_from`은 데드라인이 아니다.** 보호 모드 **진입 시각**(일정 기준 상대)이고,
데드라인은 `일정시각 − 준비 − 수면`으로 **별개**다. 미리보기가 보여줄 것은 데드라인이다.
(서버는 `protect_from` 파싱 실패 시 데드라인 −24h로 폴백한다 — `guard.ts:71`.)

### 검사 — 통과 기준

완료 조건 1번("기본값이 실제로 실린다")은 **요청 본문을 봐야 한다.** 서버가 `protect_from`을
`'-1d 00:00'`으로, level을 4로 **알아서 채우기 때문에**(`events.ts:65·69`), 응답이나 서버 상태만
확인하면 **프런트가 아무것도 안 보내도 통과한다.** `Api.setProtect`가 실제로 받은 인자를 잡는다.

완료 조건 2번("미리보기가 입력에 따라 바뀐다")은 고정 문자열 비교로는 계산과 구별되지 않는다.
**수면 360 → 300으로 고치고 표시가 정확히 60분 뒤로 가는 것**을 본다. 설계 §6.1의 09:00 → 01:30을
기준점으로 쓰면 서버 smoke와 같은 예시에 걸려 양쪽이 함께 고정된다.

### 클래스명

`.ev-protect-…` 꼴로 접두사를 붙인다. `prot`·`pf`·`lv`·`on` 같은 2~5자 일반명은 **세 번 물렸다**
(`.tt`·`.wseg`·`.warn`). `style.css`의 CSS 규칙과 `app.js`의 JS 선택자 **양쪽**을 `grep`한다.

### 고친 것 1 — CSS 회귀 (검사가 못 잡는 종류)

날짜 팝업의 일정 제목이 `<span class="en">` → `<button class="ev-protect-event-title">`로 바뀌었는데
(보호 편집 진입점), `.evrow .en{flex:1;font-size:14px;font-weight:600}`이 주던 것을 새 클래스가
받지 않았다. 전역 `button` 리셋이 `font:inherit`을 주므로 글꼴 자체는 괜찮지만 **굵기가 600 → 보통,
크기가 14px에서 상속값으로, `flex:1`이 없어 제목이 행을 채우지 않아 `×`가 오른쪽으로 밀리지 않는다.**

**검사로는 안 잡힌다**(스타일을 보는 검사가 없다) — 폰에서 눈으로 볼 항목이었다. `flex:1`·`14px`·`600`을 되살렸다.

### 고친 것 2 — 검사 3건 추가 · 1건 강화

1. **완료 조건 4번(잘못된 `protect_from`은 저장 전에 막힌다)이 미검사였다.** 코드엔 있다 —
   `protectionBody()`가 `{error}`를 돌려주고 핸들러가 `closeSheet` **앞에서** 반환한다.
   검사가 없으면 다음 사람이 지운다 → `"어제 자정"`을 넣고 `setProtect` 호출이 늘지 않는 것 +
   시트가 열린 채 남는 것 + 토스트가 이유를 말하는 것까지
2. **종일 일정 09:00 폴백이 미검사였다** — 분해가 짚은 **가장 큰 서버-프런트 어긋남 지점**인데
   코드만 맞고 검사가 없었다 → 종일로 열어 기본값(360·90)에서 미리보기가 **01:30**인지 본다.
   **설계 §6.1의 예시 그대로**이고 서버 쪽은 `smoke.ts:445`가 같은 값을 박고 있어, 양쪽이 한 예시에 묶인다
3. **데드라인 검사를 양쪽 값으로 강화.** `deadline300`이 `08:00`인 것만 봤는데,
   그러면 **`prep`을 빼먹은 식(`− sleep`만)도 통과할 수 있다** → `deadline360`의 `07:00`도 함께 박았다
