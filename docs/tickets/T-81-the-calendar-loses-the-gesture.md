# T-81 — 캘린더가 제스처를 뺏기고, 느린 곳이 어디인지 모른다

**발행** Cowork · 2026-09-21 · **담당** Claude Code · **보통**
**근거** 2026-09-21 사용자 실측 — *"캘린더 넘기려는데 탭 넘어가서 불편"* ·
*"캘린더 스크롤 딜레이 길어서 스파이크 쓰고 싶은데"* ·
[T-73 §보고](T-73-compose-spike-calendar.md)(제스처 상수·겹침 실측) · `APP-PLAN` §7 · 함정 18
**프런트 전용 · 서버 무변경 · 마이그레이션 없음 · APK 무관**

---

## ★★★ 둘은 다른 문제다 — 섞으면 둘 다 못 고친다

```
① 제스처를 뺏긴다   가로로 끌면 탭이 먼저 먹는다   ⚠️ 제로섬이다
② 느리다            ★ 어디가 느린지 아직 모른다   ⚠️ 전환 판단이 여기 걸린다
```

★★★★★ **②를 먼저 한다.** 사용자가 *"스파이크 쓰고 싶다"* 고 말한 근거가 ②인데,
**Compose 로 고쳐지는 종류의 느림인지 아무도 안 쟀다.** `APP-PLAN` §7의 전환 비용 추정이
**그 답에 통째로 달려 있다** — T-73 왕복 1이 바이트코드에서 물린 것과 같은 자리다(함정 18).

---

## ② 느린 곳을 먼저 가른다 — ⚠️ 고치기 전에

**넷 중 하나이고, 처방이 전부 다르다:**

```
(a) 달을 넘길 때 API 를 부른다        ⚠️ Compose 로 바꿔도 그대로다 — 전환이 답이 아니다
(b) 6주 DOM 을 매번 새로 만든다        ★ 웹에서 고친다
(c) transform 지속 시간이 길다         ★ CSS 한 줄이다
(d) WebView 가 프레임을 못 낸다        ★ 그때만 Compose 가 후보가 된다
```

### 할 일 — **읽기와 계측만. 아직 아무것도 안 고친다**

```
□ ★ 달을 넘기는 경로가 네트워크를 타는가 (weeksOf · 캐러셀 렌더 경로를 코드로)
□ ★ 한 번 넘길 때 만드는 DOM 노드 수 · 재사용하는가
□ ★ transform 의 transition 지속 시간이 얼마인가 (CSS 원문)
□ ★★ 위 셋으로 설명이 안 되면 → (d) 후보. 그때 폰 계측이 필요하다
```

★★ **①(제스처)은 이 단계에서 안 건드린다.** 둘을 같이 만지면
*"무엇이 좋아졌나"* 를 못 가른다.

⚠️ **사용자에게 물을 것이 생기면 한 줄로 만들어 올려라** — *"넘어가는 데 시간이 걸리나,
넘어가는 동작이 끊기나"* 는 (a)(b)와 (c)(d)를 가르지만, **코드로 먼저 좁힌 뒤에 물어야
답이 쓸모 있다**(`CLAUDE.md` §작업 방식 — 확인 절차를 제시하고 결과를 받는다).

### §보고에 들어갈 것

```
★ 넷 중 무엇인가 (또는 "셋으로 설명이 안 된다")
★ 그 판정의 근거 — 코드 위치와 수
★ (d) 후보면: 폰에서 무엇을 어떻게 재는지 절차
```

⚠️ **(a)로 밝혀지면 그것만으로 APP-PLAN §7의 전환 비용 추정이 바뀐다.** Cowork 가 받는다.

---

## ① 제스처 — ⚠️ 제로섬이다. 한 단계만 넓히고 멈춘다

```
캘린더가 잡는 영역을 넓힌다   =   탭이 잡는 영역을 줄인다
```

★ **T-73이 *"탭 다섯이 전부 가로"* 라고 쟀다.** 공짜가 없다.

### 할 일 — ②의 보고가 온 **뒤에**

```
□ ★ 지금 무엇이 가르는가 — 경계 상수의 이름·값·읽는 자리를 먼저 적는다
□ ★ 캘린더 쪽으로 한 단계 넓힌다.  ⚠️ 한 단계다. 여러 값을 동시에 안 바꾼다
□ ★★ 되돌리는 법을 §보고에 적는다 — 불편하면 다음 왕복에 되돌린다
```

⚠️ **값을 여러 개 바꾸지 마라.** 축비·슬롭·경계비를 함께 만지면
**무엇이 좋아졌는지 사용자도 나도 못 말한다**(T-73이 슬롭 하나만 토글한 이유).

★ **설정으로 만들지 않는다.** 상수 한 곳. **아프면 그때 연다.**

---

## 범위

```
public/app.js       ①의 상수 · ② 계측을 위해 읽기
public/style.css    ②(c) 확인 · ①이 CSS 쪽이면
test/front.mjs      ①을 바꾸면 검사
```

**서버 무변경 · `guard/` 안 건드린다 · 마이그레이션 없다 · APK 무관.**
⚠️ **②는 코드를 안 고친다.** 고칠 것이 보이면 **적고 올려라** — 처방은 ②의 답이 정한다.

## 금지

| 하지 말 것 | 왜 |
|---|---|
| **②를 건너뛰고 ①부터** | ⚠️ 사용자가 원한 것은 *"안 느린 캘린더"* 다. 제스처는 그 절반이다 |
| ②에서 코드를 고친다 | ★ 무엇이 느린지가 처방을 정한다. 고치면 그 답을 못 얻는다 |
| ①에서 값 여러 개를 동시에 | **무엇이 좋아졌는지 못 말한다**(T-73) |
| 경계를 설정으로 뺀다 | 상수 한 곳. 아프면 그때 연다 |
| Compose 쪽에 손댄다 | ⚠️ **스파이크는 보류다.** ②의 답이 그 판단을 다시 연다 |
| 탭 스와이프를 없앤다 | 다섯 탭의 유일한 이동 수단이다 |

## 완료 조건

**②만으로 한 번 닫는다** — ①은 그 뒤 왕복이다.

```
②   ★ 넷 중 무엇인지가 §보고에 있다. 코드 무변경 · 기준선 그대로
①   typecheck 통과 · front ±N · 실패 0 · verify exit 0
```

⚠️ **②에서 숫자가 움직이면 무언가를 고친 것이다 — §금지 위반이다.**

**검사 (①을 할 때)**

```
1  ★ 캘린더 위 가로 제스처가 캘린더를 넘긴다
2  ★ 캘린더 밖 가로 제스처는 여전히 탭을 넘긴다      ← 1의 짝. 제로섬을 지킨다
3  ★ 세로 제스처는 어느 쪽도 안 먹는다               ← 회귀 (축비)
4  ★ 경계 상수가 한 곳에만 있다                      ← 두 벌 금지
```

⚠️ **2가 없으면 *"캘린더가 전부 먹는"* 구현이 통과한다** — 1만 보면 초록이고,
**탭 이동이 죽은 것을 검사가 못 센다.**
⚠️ **jsdom 제스처는 좌표를 `MouseEvent` 생성자로**(함정 3) · **`clientWidth`는 0**(함정 2).
★ **검사가 경계 값을 하드코딩하지 마라**(함정 15) — 상수를 읽어 쓰지 말고, **넉넉히 안팎**으로 잡는다.

**변이**

```
경계를 옛 값으로 되돌린다     → 1 만 죽는다
경계를 끝까지 넓힌다          → ★ 2 만 죽는다 (1은 초록)
축비 판정을 뺀다              → 3 만 죽는다
상수를 두 곳에 둔다           → 4 만 죽는다
```

★★★ **변이가 *붙었는지*와 *되돌아갔는지*를 둘 다 본다**(함정 16).
⚠️ **그리고 검사가 *저절로 참*이 되지 않았는지 본다**(`AGENT-CHAIN` §8 다섯 기제 —
특히 ⑤ **jsdom 이 계약을 안 싣는 자리**. 제스처는 정확히 그 자리다).

## 확인 절차 (사용자)

**②**: 없다. 보고를 읽는다.

**①** (`npm run deploy` 뒤):

```
□ ★ 캘린더에서 가로로 끌면 달이 넘어간다 (탭이 안 뺏는다)
□ ★ 캘린더 밖에서 가로로 끌면 탭이 넘어간다        ← 둘 다여야 한다
□ 세로 스크롤은 그대로다
□ ★ 더 넓혀야 하나 / 이미 과한가 — 말로 받는다
```

---

## ★ 이 티켓이 안 하는 것

- **Compose 전환을 안 연다.** ⚠️ ②의 답이 (d)일 때만 그 판단이 다시 열리고,
  **그것은 `APP-PLAN` §7로 올라가지 이 티켓에서 결정되지 않는다.**
- **애니메이션 라이브러리를 안 넣는다** — 무엇이 느린지 모르는 채 넣으면 근거가 없다.
- **탭 제스처의 구조를 안 바꾼다** — 경계 값 하나다.
- **Guard·수집 쪽은 한 줄도 안 건드린다.**
