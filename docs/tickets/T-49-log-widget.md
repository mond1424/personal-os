# T-49 — 홈에 로그 한 줄

**발행** Cowork · 2026-08-27 · **담당** Claude Code · **작음**
**근거** [ADR-043](../../APP-ADR.md#adr-043) 연장 · **APK 필요 · 서버 무변경 · 마이그레이션 없음**

---

## 무엇을 만드나

**3×1 위젯 하나. 검색창처럼 생겼고, 탭하면 앱의 로그 입력줄로 간다.**

```
┌──────────────────────────────────────┐
│  ✎   지금 뭐 하고 있나요              │
└──────────────────────────────────────┘
```

**딥링크는 이미 있다** — `add-log`가 `DEEPLINK_ACTIONS`에 서 있다(T-48).
**이 티켓은 위젯 하나와 그 배선이 전부다.**

## 왜 지금인가 — 어포던스를 잰다

**T-48 최대 크기에 로그 버튼이 이미 있는데 왜 또 만드나:**

```
T-48 의 로그 버튼   최대 크기로 늘린 사람만 닿는다
T-46 의 "+"        아이콘 하나라 무엇을 하는지 안 읽힌다
이것               가로로 길고 "쓰는 곳"처럼 생겼다
```

**T-46과 이 위젯은 같은 물건이다** — 탭 → 딥링크 → 앱 입력창. **다른 것은 옷뿐이다.**
그래서 **둘 중 어느 쪽이 눌리는지가 "위젯이 안 눌리는 이유가 어포던스인가"를 답한다.**
ADR-043 §재검토가 묻는 것에 대조군이 하나 생긴다.

## ★ 상한 — 여기서 멈춘다

```
✅  3×1 위젯 · 검색창 모양 · 탭 → add-log 딥링크
❌  위젯 안에서 타이핑             ← RemoteViews 에 EditText 가 없다. Android 가 안 준다
❌  오늘 로그 개수·마지막 로그 그리기  ← 데이터를 그리면 다리·갱신이 따라온다
❌  add-log 액션 손보기            ← T-48 이 세웠다. 재사용만 한다
❌  ScaleWidget · AddTaskWidget 손대기  ← 별개 위젯 셋이다
```

**데이터를 안 그리므로 `WidgetPlugin` 다리도, 토큰도, 갱신 스케줄도 필요 없다** —
T-46과 같은 부류다(ADR-041 §맥락).

## 할 일

```
AppWidgetProvider 하나 · 3×1 · RemoteViews = 아이콘 + 힌트 텍스트
전체를 하나의 PendingIntent → personalos://add-log
```

**모양**

- 둥근 모서리 · 옅은 배경 · 옅은 글씨 — **입력줄로 읽혀야 한다**
- ⚠️ **placeholder 처럼 보이되 실제로 못 친다.** 탭하면 앱이 열리는 것이 전부이고,
  그것은 Google 검색 위젯과 같은 계약이라 **거짓말이 아니다**
- 색은 `values/` ↔ `values-night/` **짝**(함정 5의 Android판). T-46이 세운 그 자리다
- 문자열은 `strings.xml`. **레이아웃에 리터럴을 박지 않는다**

**⚠️ 주석에 `/api/…/*` 꼴을 적지 마라** — `/*`가 Kotlin 블록 주석을 새로 연다.
**T-46·T-48이 두 번 물렸고 `verify`가 초록인 채로 `assembleRelease`만이 잡았다**(함정 13).

### app.js 를 안 고쳤는가

**안 고쳤다.** `git diff --stat`에 `public/app.js`가 **없다** — 이 티켓이 건드린 것은
`android/` 아래와 `test/front.mjs`뿐이다. `add-log`는 T-48이 세운 그대로 재사용했고,
고쳐야 할 것도 나오지 않았다(검사 ②가 그 액션을 살아 있는 대장에 물어서 확인한다).

### 1·2 짝을 어떻게 세웠나

**두 문자열을 각자 정규식으로 보지 않는다.** 그러면 갈라져도 둘 다 초록이 된다(T-46이 세운 자리).

```
①  배선만 본다 — setOnClickPendingIntent · PendingIntent.getActivity · ACTION_VIEW ·
    MainActivity::class.java, 그리고 던지는 것이 `personalos://<이름>` 꼴인가.
    ★ 여기서 **이름은 안 본다.** 이름의 옳고 그름은 ②의 몫이다
②  Kotlin의 `DEEP_LINK` 문자열을 뽑아 **살아 있는 `deepLinkAction()`에 먹인다.**
    `deepLinkAction`이 대장(`DEEPLINK_ACTIONS`)에 `hasOwnProperty`로 물어 보므로,
    이름이 한 글자라도 틀리면 `null`이 돌아온다. 여기에 대장 자체의 키 확인을 하나 더 붙였다
```

①이 이름을 안 보는 것이 짝을 성립시킨다 — 이름을 바꾸는 변이가 **②만** 죽는다.
`add-logs`처럼 한 글자 틀린 딥링크가 위험한 이유는 티켓이 적은 그대로다: `deepLinkAction`이
`null`을 주고 T-46의 폴백이 그냥 Today를 띄워서, **"안 눌렸다"가 아니라 "앱이 열리긴 했다"** 로 보인다.

### 주석에 `/*` 를 만들지 않았는지 어떻게 확인했나

**세 겹으로.**

1. **애초에 그 경로를 안 적었다** — 와일드카드가 붙는 API 경로를 주석에 쓰지 않고
   *"api 아래 와일드카드"* 라고 말로 적었다(`LogWidget.kt`의 머리 주석에 그 경고를 남겼다).
2. **여는 것과 닫는 것의 수를 셌다** — `LogWidget.kt`에 `/*`가 **3**(전부 `/**` KDoc),
   `*/`도 **3**이다. 중첩이 열렸으면 이 둘이 안 맞는다.
3. **`assembleRelease`가 통과했다.** 함정 13이 말하는 그대로 **`verify`는 이것을 못 잡는다** —
   T-48에서는 verify가 초록인 채로 이 단계만 빨간불이었다. APK가 붙은 티켓이라 이 단계까지 돌렸다.

XML 쪽 짝인 하이픈 둘(T-46)도 피했다 — 새 XML 넷의 주석에 `--`가 없다(`mergeReleaseResources` 통과).

### 변이 넷이 각각 하나씩만 죽였는가

**그렇다. 기준선 357에서 넷 전부 356 · 실패 1이다.**

| 변이 | 통과 | 죽은 검사 |
|---|---|---|
| A 딥링크 이름을 한 글자 바꾼다(`add-log` → `add-logs`) | 356 | ② 대장이 해석한다 |
| B ①의 스캐너를 눈멀게 한다 | 356 | ⑤ (①은 초록) |
| C `values-night`를 지운다 | 356 | ③ 다크 짝 |
| D 레이아웃에 색을 박는다 | 356 | ④ 리터럴 0 |

**A가 ②만 죽인 것이 짝의 증거다** — ①이 아직 이름을 보고 있었다면 둘이 함께 죽었을 것이다.

⚠️ **C를 위해 검사 ③의 파일 읽기를 감쌌다.** 안 감싸면 파일이 없을 때 `readFileSync`가 던져
**러너가 통째로 멈추고 숫자를 잃는다** — "검사 하나가 죽는다"와 "검사가 안 돈다"는 다르다
(T-44가 처리되지 않은 거절로 숫자를 통째로 잃은 그 자리다).

⚠️ **변이 스크립트가 B에서 한 번 헛돌았다 — 줄끝이다.** 이 리포는 **파일마다 줄끝이 다르다**
(`test/front.mjs`는 CRLF, `.kt`는 LF). 여러 줄짜리 find가 `\n`으로 적혀 있어 CRLF 파일에서
안 맞았다. **스크립트가 "대상 문자열을 못 찾았다"로 죽게 해 둔 것이 이걸 살렸다** —
조용히 넘어갔으면 *"변이를 적용했는데 아무 검사도 안 죽었다"* 로 읽혀 **검사가 약하다는 오진**이
나왔을 것이다. 찾는 문자열을 그 파일의 줄끝에 맞추도록 고쳤다.

**변이 뒤 원상복구 확인**: `npm run verify`가 **370/357 · 실패 0**으로 돌아왔고,
`assembleRelease`가 **166 up-to-date**로 끝나 **APK가 한 바이트도 안 바뀌었다** —
위에 적은 MD5 `8e1743b3dfae9bc47fb24c68ebf6828d`가 최종이다.
(변이가 검사를 고치게 만들지 않았으므로 소스가 그대로다.)

⚠️ **C를 위해 검사 ③의 파일 읽기를 감쌌다.** 안 감싸면 파일이 없을 때 `readFileSync`가 던져
**러너가 통째로 멈추고 숫자를 잃는다** — "검사 하나가 죽는다"와 "검사가 안 돈다"는 다르다.

### 범위 밖 — 파일 하나

**`res/drawable/widget_log_bg.xml`.** 티켓 §모양이 *"둥근 모서리"* 를 요구하는데
**`RemoteViews`에는 런타임에 모서리를 깎는 수단이 없다** — shape 드로어블이 유일한 길이다.
`res/drawable/`은 이미 있는 디렉터리이고, 색은 그 안에서도 `@color/…` 참조라
`values-night/`가 그대로 일한다(참조는 인플레이트 시점의 설정으로 풀린다).

그래서 **검사 ④는 레이아웃만 보지 않고 드로어블까지 본다** — 레이아웃만 보면
*"색을 드로어블에 박는 구현"* 이 통과한다.

색 파일도 위젯마다 따로 뒀다(`widget_log_colors.xml`). T-46의 검사가
*"`widget_colors.xml`의 색 이름은 전부 그 레이아웃이 쓴다"* 를 세므로 한 파일에 몰면
**남의 검사가 빨간불이 된다** — T-48이 겪고 나서 정한 규칙이다.

### 티켓보다 하나 더 — 검사 ⑥ (Manifest)

티켓의 검사 목록은 다섯인데 여섯째를 넣었다: **Manifest가 이 위젯을 선언하는가**
(`exported="true"` · `APPWIDGET_UPDATE` · 자기 메타). §금지가 `exported="false"`를 막고 있는데
그것을 세는 검사가 없었다. 빠지면 위젯이 목록에 안 뜨거나, 떠도 `onUpdate`가 안 와서
`initialLayout` 그대로 굳어 **눌러도 아무 일이 없다** — T-46이 물린 자리다.

### Codex 위임

**0.** Manifest만 직접 하라는 조건이었는데, 나머지가 파일 여섯에 걸친 **한 배선 한 벌**이라
(리시버 · 메타 · 레이아웃 · 드로어블 · 색 짝 · 문자열) 갈라 넘기면 검토가 곧 재작성이 된다.
T-46·T-48과 같은 판단이다.
