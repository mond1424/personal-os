# T-41 — 학사 마감을 cron이 수집한다 (해석은 미룬다)

**발행** Cowork · 2026-08-21 · **담당** Claude Code · **보통**
**근거** [ADR-037](../../APP-ADR.md#adr-037) · 마이그레이션 있음 · **APK 무관 · 서버만**

---

## 왜 지금인가 — 8월로 당긴 이유

**시스템이 비어 있다.** 2026-08-21 실측:

```
todo 0 · done 0 · events 0 · periods 0 · waiting 0 · overdue 0 · logs 0 · daily 없음
risk_score  60건 중 18건이 0 · 40 이상은 5건 · 최대 55
```

그리고 모델이 격상을 거부하며 **정확히 그 이유를 말했다**(8/20 07:00):

> *"연결된 일정·마감·위험 지표가 없어 격상 근거가 불충분하다"*

**`approve = 0`과 적극성 문제는 같은 문제다.**

```
안 넣는다 → 시스템이 아는 게 없다 → 개입 근거가 없다 → 개입이 약하다 → 더 안 넣는다
```

**이 티켓은 그 루프를 사람 손이 아닌 쪽에서 끊는다** — ADR-028이 적은
*"시스템의 존재 이유가 사용자의 성실성에 의존한다"*는 모순을, **원천을 성실성 밖에 두어** 끊는다.

⚠️ **9~11월이 §6.5의 전례를 쌓는 기간인데, 넣는 것이 없으면 쌓일 전례도 없다.**
그 기간이 빈 채로 지나가면 **12월에 읽을 것이 없다.** 그것이 이 티켓의 기한이다.

## 무엇을 만드나

```
cron → GET {iCal 토큰 URL}  → VEVENT 파싱 → UID 기준 diff → 저장
                                                             ↑ 여기까지가 이 티켓
                                                    T-42 가 제안 카드로 꺼낸다
```

## ★ 이 티켓의 핵심 결정 — 해석을 미룬다

**`SUMMARY`를 파싱하지 않는다. 원문 그대로 저장한다.**

실측에서 확인한 것과 못 한 것이 갈린다(ADR-037 §실측):

```
✅ UID · SUMMARY · DTSTART · DTEND · LAST-MODIFIED · DTSTAMP · CLASS 가 온다
✅ DTSTART 는 UTC(Z)
❌ CATEGORIES 가 없다 — 강좌 구분이 어디 실리는지 모른다
❌ 과제 due 이벤트의 SUMMARY 형식을 모른다 (화면은 "… 기한")
```

**모르는 것을 지금 정하면 개강 첫날 틀린다.** 그래서:

| | 지금 한다 | 개강 뒤에 한다 |
|---|---|---|
| `UID`·`DTSTART`·`LAST-MODIFIED` | 구조가 확정돼 있다 | — |
| `SUMMARY` | **원문 그대로 보관** | 활동명·강좌 추출 |
| `DESCRIPTION` | **원문 그대로 보관** | 강좌 구분이 여기 있는지 확인 |
| 키워드 필터 | **안 한다** | 노이즈가 실제로 생기면 |

**원문을 버리지 않는 것이 이 결정의 전부다.** 나중에 형식을 알게 되면
저장된 원문에서 다시 뽑을 수 있고, 버렸으면 그 기간이 통째로 못 쓰게 된다.

## 할 일

### ① 마이그레이션 0018 — 수집 원장

**성질만 정한다. 이름·칼럼명은 담당이 리포 관례에 맞춘다.**

```
uid            iCal 의 UID. UNIQUE — diff 의 기준이자 멱등 키
source         'uclass'  (원천이 늘 것을 전제로 칸을 둔다)
summary        원문 그대로
description    원문 그대로 (비어 있어도 칸을 둔다)
starts_at      DTSTART 를 로컬 오프셋 표기로 정규화 (record() 의 normalizeIso 와 같은 이유)
last_modified  변경 감지
first_seen_at  처음 본 시각
last_seen_at   마지막으로 목록에 있던 시각  ← 사라짐 판정의 근거
state          'new' | 'accepted' | 'dismissed'
event_id       accepted 일 때 만들어진 events 의 id (NULL 허용)
```

⚠️ **이것은 파생값이 아니다**(원칙 1과 충돌하지 않는다). 원천이 **밖**에 있고
창이 `-5일 ~ +365일`로 좁아 **다시 못 가져오는 것**이므로 사본이 아니라 기록이다.
그 판단 근거를 마이그레이션 주석에 적는다.

⚠️ **새 마이그레이션을 추가하면 `test/smoke.ts`의 스키마 목록(하드코딩)에도 파일명을 넣는다.**

### ② 수집 — 기존 cron에 얹는다

**`autoClose`와 같은 자리이되 독립이다.** `finalizeIgnored`가 이미 그 모양이다:

```ts
const ign = await finalizeIgnored(env, t).catch(() => ({ ignored: 0 }));
```

**수집 실패가 자동 마감을 멈추면 안 된다.** 같은 이유로 `.catch`로 삼키고,
**무엇 때문에 실패했는지는 남긴다** — T-31이 `unavailable`에서 배운 자리다.
*"조용히 아무 일도 안 일어난다"*가 이 리포가 반복해서 물린 실패 모양이다.

**빈도**: `autoClose`는 30분마다 돈다. **매번 fetch하지 않는다** — 마감이 분 단위로
생기지 않는다. **하루 2~4회**로 제한하고, 마지막 수집 시각을 기준으로 건너뛴다.

**토큰이 없으면 조용히 건너뛴다.** 그래야 이 티켓을 지금 배포해도 아무것도 안 바뀐다 —
사용자가 시크릿을 넣는 순간부터 돈다.

### ③ diff — `UID`가 기준이다

```
목록에 있고 uid 가 처음  →  새 행 · state='new'
목록에 있고 last_modified 가 바뀜  →  갱신 (state 는 건드리지 않는다)
목록에서 사라짐  →  ★ 지우지 않는다. last_seen_at 으로만 안다
```

**⚠️ 사라진 것을 지우지 않는다.** 창이 `-5일 ~ +365일`이라 **지난 마감은 자동으로 목록에서 빠진다.**
사라짐을 삭제로 읽으면 **어제 한 과제가 오늘 사라진다.** 취소와 만료를 구별하는 것은
`starts_at`이 과거인지로 판단할 일이지 목록 부재로 판단할 일이 아니다.

## 금지

| 하지 말 것 | 왜 |
|---|---|
| `SUMMARY`·`DESCRIPTION` 해석 | **형식을 모른다.** 지금 정하면 개강 첫날 틀린다 |
| 키워드 필터 | 노이즈가 실제로 생기는지 아직 모른다. iCal은 화면과 달리 이미 깨끗했다 |
| 자동으로 `events` 에 넣기 | ADR-030 위반. 오수집이 캘린더를 오염시킨다. **제안까지가 상한** |
| 목록에서 사라진 것을 삭제 | 창이 좁아 지난 마감이 자동으로 빠진다. **어제 한 일이 사라진다** |
| 수집 실패를 던지기 | 자동 마감이 통째로 멈춘다(`finalizeIgnored`가 같은 이유로 `.catch`) |
| 30분마다 fetch | 마감은 분 단위로 안 생긴다. 하루 2~4회 |
| 토큰 없을 때 오류 | 지금 배포해도 안전해야 한다 — 시크릿을 넣는 순간부터 돈다 |
| iCal 라이브러리 추가 | 쓰는 필드가 여덟이다. **파서를 직접 쓰는 편이 작다** — 다만 줄 접힘(RFC 5545 folding)은 반드시 처리한다 |

## 완료 조건

```
typecheck 통과 · smoke 325 → 330 이상 · front 291(변화 없음) · 실패 0 · verify exit 0
npx wrangler d1 migrations apply personal-os --local 성공
```

**검사** — 파싱은 순수 함수다. **고정 날짜를 써도 되는 자리**이고(T-36이 정의한 예외),
실제로 고정이어야 형식을 날짜와 무관하게 검사한다.

```
1  VEVENT 하나를 파싱한다        ← 실측으로 받은 그 파일을 fixture 로 쓴다
2  줄 접힘(folding)을 편다       ← 긴 SUMMARY 는 반드시 접혀서 온다
3  같은 UID 를 다시 넣으면 갱신이지 중복이 아니다
4  last_modified 가 바뀌면 갱신되고 state 는 안 바뀐다
5  ★ 목록에서 빠져도 행이 남는다        ← 3·4의 짝. "지우지 않는다"를 세는 검사
6  토큰이 없으면 조용히 건너뛴다        ← 예외를 안 던진다
7  ★ 수집이 던져도 autoClose 가 끝까지 간다
```

**5와 7이 짝이다.** 1~4만 보면 *"사라지면 지우는 구현"*과 *"실패하면 마감을 멈추는 구현"*이
둘 다 통과한다. 이 리포가 T-33·T-38·T-39에서 세 번 물린 자리다.

**변이**: `.catch`를 떼면 7이 죽고 1~6은 산다. 사라짐 처리를 삭제로 바꾸면 5만 죽는다.

## 확인 절차 (사용자)

**시크릿을 넣기 전까지 아무것도 안 바뀐다.** 넣는 시점은 개강 뒤여도 된다.

```
① https://uclass.uos.ac.kr/calendar/export.php
   내보낼 일정 = 모든 이벤트 · 기간 = 범위 설정  →  [달력 URL 가져옴]
② npx wrangler secret put UCLASS_ICAL_URL      ← 이름은 담당이 정한 것으로
```

**같은 마감이 두 경로로 들어온다**(ADR-037 §감수하는 비용).

## 변이 — 실제로 돌렸다

| 변이 | 기대 | 실제 |

| `.catch` 제거 (`scheduled.ts`) | 7이 죽고 1~6은 산다 | **334/1 — 7만.** 실패 줄이 `autoClose가 던졌다 — .catch가 없다: uclass down` ✅ |
| 사라짐을 삭제로 (`uid NOT IN (…)`) | 5만 죽는다 | **334/1 — 5만.** `A=0` (행이 지워졌다) ✅ |

⚠️ **첫 변이가 처음엔 러너를 죽였다.** `.catch`를 떼자 던짐이 그대로 올라와 **요약도 개수도

## 검사가 열이 된 이유 — 티켓의 일곱에 셋을 보탰다

- **빈도 제한**(§금지 *"30분마다 fetch"*)이 검사에 없었다. `fetch` 호출 수를 세어
  **두 번째 호출이 실제로 네트워크를 안 타는 것**을 본다 — 반환값만 보면 통과하는 종류다.
- **실패가 조용히 사라지지 않는다** — 사유가 `settings.uclass_last_error`에 남고
  **거기에 URL이 안 실리는 것**까지 본다. 그 값이 열쇠다(ADR-037 §근거 ④).
- **`DTSTART`가 로컬 오프셋으로 정규화되는 것** — 원문은 `Z`인데 저장은 로컬 표기다
  (`record()`의 `normalizeIso`와 같은 이유 · 안 하면 KST 09~15시가 전날로 귀속된다).

## T-36 스캐너에 걸렸고, 그 가드를 넓히지 않았다

검사에 `"2026-08-18T00:00:00Z"`를 적었더니 **고정 날짜 스캐너가 잡았다** — 설계대로다.
티켓은 *"순수 함수라 고정 날짜를 써도 되는 자리"*라고 했지만, **예외를 넓히는 대신
기대값을 fixture에서 독립으로 계산**하도록 바꿨다(`isoOf()`).

```
fixture 의 DTSTART:20260818T000000Z   ← 대시가 없어 스캐너에 안 걸린다
isoOf() 가 그것을 ISO 로 편다          ← 테스트 안의 독립 구현. icalDateToIso 를 부르면 순환이다
```

**가드를 건드리지 않고 통과하는 길이 있으면 그쪽이 맞다** — 예외 목록은 한 번 넓히면
다음 사람이 그 자리를 근거로 또 넓힌다.

## 알아 둘 것 — 이 티켓이 답하지 않은 것

**`DTSTART`가 마감 시각인지 모른다**(ADR-037 §실측 ❌ 셋째). 그래서 `starts_at`은
*"iCal이 시작이라고 말한 시각"*이고 **마감이라고 부르지 않았다.** T-42가 제안 카드를
만들 때 이 이름을 그대로 믿으면 안 된다 — **개강 첫 과제가 답한다.**
