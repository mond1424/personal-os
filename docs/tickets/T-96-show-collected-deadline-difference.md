# T-96 — 저장한 일정과 최근 수집 마감이 다르면 날짜 상세에서 말한다

**발행** 설계층 · 2026-10-08 · **담당** 감독층 · **상태** ⛔ 취소 · 미착수 종결 · 사용자 결정 2026-10-08
**근거** ADR-050 2026-10-08 개정 · T-88 ①-d 첫째 · 과거 기록 불변 원칙
**착수하지 않는다.** 아래 구현안·검사·보고 서식은 취소된 제안의 이력이다.

## 종결 결정 (설계층 · 2026-10-08)

과제는 Tasks.org가 맡고 pOS는 새 과제를 수락하지 않으며 기존 기록은 보존한다는 사용자 결정으로 접는다.
마감 차이 표시·`source_deadlines` 응답 필드는 구현하지 않는다. 대신 [T-97](T-97-stop-collected-acceptance.md)을 발행한다.
T-88 ①-d 첫째의 옛 일정 시각은 자동으로 고쳐지지 않는다. 이 취소는 마감 불일치 해결이나 구현 검증 합격이 아니다.
기존 일정은 pOS의 저장 기록으로 남고, 현행 과제 마감·알림·완료는 Tasks.org에서 관리한다(ADR-050 추가 개정).

---

## 목표

uclass 원장의 마감이 바뀌었는데 pOS 일정은 수락 당시 시각에 남아 있는 차이를 사용자가 알 수 있게 한다.
자동 덮어쓰기는 하지 않는다. pOS의 과제 기록을 유지하는 동안 필요한 표시이며, 수집 자체를 종료하기로 결정되면
착수 전에 범위를 다시 판단한다. **이 티켓은 마감 자동 동기화나 일정 수정 UI 확장이 아니다.**

## 범위 — 이 파일들만 고친다

```
src/db/index.ts              날짜에 표시할 events에 연결된 수집 원장 조회
src/services/daily.ts        assembleDay의 events에 조회 결과와 차이 판정 추가
public/app.js               openDay의 일정별 최근 수집 마감 표시
public/style.css            그 안내에 필요한 범위의 스타일
test/smoke.ts               실제 날짜 응답·원장 갱신·무변경 검사
test/front.mjs              날짜 상세 표시·실제 응답 필드 짝 검사
docs/api-surface.md         날짜 응답의 새 필드 설명
```

범위 밖은 고치지 말고 보고한다. SQL은 db/index.ts에만 둔다.

## 할 일

1. `/api/days/:date`의 각 event에 **`source_deadlines` 배열**을 추가한다. 연결은 `collected_items.event_id`로만 찾고
   제목으로 맞추지 않는다. 배열 원소는 `{collected_id, starts_at, last_seen_at, comparison}`이다.
   `comparison`은 `same | different | unknown`이며 조회 때 계산한다. 연결 없는 일정은 `[]`다.
   원장 행의 state로 실제 연결을 숨기지 않는다. 복수 원장 참조는 id순 배열로 실어 event 자체가 중복되지 않게 한다.
2. 비교는 현재 `collected.accept`가 일정을 만드는 계약과 맞춘다. 유효한 `starts_at`의 날짜·시각(앞 16자리)을
   `events.date/time`과 비교한다. 날짜만 비교하지 않고, 초·귀속일로 마감일을 바꾸지 않는다.
   원장 시각이 없거나 형식을 해석할 수 없으면 `unknown`, 원장 시각은 있는데 일정이 종일이면 `different`다.
   현재 시간대 설정으로 과거 원장을 재해석하거나 새 마감을 서버의 「오늘」로 옮기지 않는다.
3. 날짜 상세의 해당 일정 바로 아래에, `different`이면 **「저장한 일정과 최근 수집 마감이 달라요」**와
   **최근 수집 마감 날짜·시각, 마지막 확인(`last_seen_at`)**을 표시한다. `same`에는 경고하지 않는다.
   `unknown`은 **「최근 수집 마감을 확인할 수 없어요」**로 구별한다. 연결 없는 일정에는 아무 안내도 추가하지 않는다.
   「최근 수집」을 학교의 현재 실시간 마감이라고 말하지 않는다. 여러 참조면 각각의 관측을 생략 없이 구분해 보여준다.
4. 안내는 **「과제 알림과 완료는 Tasks.org에서 확인하세요. pOS 일정은 자동으로 바뀌지 않아요.」**로 끝낸다.
   앱 설치 여부를 추측하는 링크·가짜 동기화 버튼은 만들지 않는다. 기존 일정 편집은 그대로 둔다.
   현재 일정 시트의 날짜는 편집 입력이 아니므로, 「여기서 새 날짜를 반영하세요」 같은 불가능한 행동을 약속하지 않는다.
5. 읽기 요청은 events·tasks·schedule_entries·수집 원장·보호 규칙을 쓰지 않는다. 마감된 날도 읽기 전용으로 차이를 보여준다.
   월간 셀·Today·Works의 자동 날짜 이동, 과제 완료, 보호 알람 재예약은 하지 않는다.

## 금지

| 하지 말 것 | 왜 |
|---|---|
| uclass.collect에서 수락 일정·task 예정일을 자동 변경 | 수동 수정·보호 시각·마감된 기록과 충돌한다 |
| 비교 결과·대기 일수·차이 경고를 DB에 저장 | 조회 시 계산하는 파생이다 |
| 과거 event를 새 마감으로 옮기거나 보호 시각 수정 | 읽기 경고가 기록 변경이 되어서는 안 된다 |
| iCal에서 사라진 항목을 삭제/완료로 읽기 | 피드의 기간 창 이탈과 제출은 다르다 |
| Tasks.org와 pOS를 제목으로 연결 | 제목은 수정 가능하며 공통 id 계약이 없다 |

## 완료 조건

```
typecheck 통과 · smoke A → B · front C → D · 실패 0 · schema 일치 · verify exit 0
```

- 정상 수락 직후 same, 이후 같은 uid의 원장 시각만 바꾸면 different. 날짜만 변경·시각만 변경을 각각 검사한다.
  날짜 응답의 새 필드가 실제 원장의 값과 관측 시각을 싣는지 직접 확인한다.
- 원장 NULL/잘못된 시각은 unknown, 손 일정은 빈 배열, 복수 참조는 event 수 불변 + 원장 수만큼 배열이다.
- 위 조회 전후의 event·task·예정·보호 값이 동일하다. 마감된 날에서도 예외 없이 표시하고 기록은 불변이다.
- front는 일치/불일치/unknown/무관한 일정을 차례로 열어 경고·날짜·시각·마지막 확인 표시가 정확한지 본다.
  실제 API 필드의 짝 검사도 둔다. 긴 안내의 실제 폰 폭은 자동 검사 통과로 단정하지 않는다.
- 변이: 항상 same / 시각을 빼고 날짜만 비교 / 조인으로 event 중복 / 원장 값을 일정에 쓰기를 각각 구별하는 검사와 결과를 보고한다.

## 확인 절차 (사용자)

1. 배포 후 실제 마감 변경이 수집된 일정의 날짜 상세를 폰에서 확인한다. 저장 일정과 최근 수집 마감·마지막 확인이
   함께 읽히고 안내가 잘리지 않아야 한다(할 일 3). 해당 표본이 아직 없으면 **폰 확인 미실시**로 남긴다.
2. 일치·연결 없는 일정에는 경고가 없다. unknown 분기는 격리 검사 표본으로 검증하고, 실사용에서 관측하지 않았으면
   폰에서도 봤다고 보고하지 않는다(할 일 3).
3. 안내가 자동 갱신이나 Tasks.org 완료 연동을 약속하지 않는지 확인한다(할 일 4).
   이 절을 위해 실사용 원장을 직접 변조하지 않는다. 구현 검사 통과와 위 폰 확인 여부는 별도로 보고한다.
