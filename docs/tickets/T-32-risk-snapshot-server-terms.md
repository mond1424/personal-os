# T-32 — 위험도 스냅샷에 서버 항을 얹는다

**발행** Cowork · 2026-08-11 · **담당** Claude Code (**위임 금지** — 귀속일·전례 원재료)
**상태** 🟡 구현·보고 완료 (2026-08-11) · **검토 대기** · 9월 1일 마감

---

## 무엇이 빠졌나

W4 전수(2026-08-11)가 찾았다. **`risk_snapshot`이 §6.6의 항 절반을 담지 않는다.**

APP-PLAN §6.6의 표가 요구하는 것과 실제:

| 항 | 출처 | 실제 |
|---|---|---|
| 현재 시각 | 파생 | ✅ `hour` |
| 데드라인까지 남은 시간 | 파생 | ❌ |
| 보호 모드 여부 · 대상 event | `events` | △ `cause`·`event_id` 칼럼으로만 |
| 최근 Log 활동 (각성 신호) | `logsRange` | ❌ |
| 수면 추정 (Log 첫/마지막) | `logsRange` | ❌ |
| 최근 Feelings · Score 추세 | `feelingsRange`·`dailyRange` | ❌ |
| foreground app | UsageStats | ✅ `top_apps` |

**빠진 것은 전부 출처가 서버다.** 그리고 `risk_score`는 **항상 `NULL`**이다 —
기기가 그 키를 안 보내고(`GuardEventQueue`), 서버는 받은 것만 넣는다(`guard.ts:275`).

## 실수가 아니라 ADR-021의 부산물이다

계획을 쓸 때는 **서버가 발동을 판단**했으므로 그 자리에서 `logsRange`를 부를 수 있었다.
**ADR-021이 발동을 기기로 옮기면서 스냅샷 생산도 같이 기기로 갔고**,
기기엔 `logs`·`feelings`·`daily`가 없어 서버 출처 항이 통째로 사라졌다.

**그 누락이 어디에도 안 적혔다.** ADR-021이 발동 위치를 옮길 때
*"그러면 스냅샷의 서버 출처 항은 어디서 오나"*를 묻지 않았다 — 발행자의 누락과 같은 모양이다.

## 왜 9월 1일이 마감인가

§6.6이 스스로 답을 적어 뒀다:

> **10월에 실제 스냅샷에서 가중치를 유도한다.**

유도할 항이 없으면 유도가 없다. 그리고 감축 순서가 *"위험도 항 개수"*를 3순위로 두면서
**"전부 빼지는 않는다"**고 못 박았는데 — **지금은 서버 항이 전부 빠진 상태다.**

**기록은 소급되지 않는다.** T-31과 같은 이유이고, 규모가 넷이다.

## 할 일

### ① 서버가 `record()`에서 자기 항을 얹는다

자리는 `src/services/guard.ts`의 `record()` — `stInsertGuardEvent` 호출 직전이다.
지금은 `input.risk_snapshot`을 **그대로 문자열화만** 한다(`:277`).

```
기기가 보낸 항  +  서버가 조회한 항  →  risk_snapshot
```

**키를 갈라 둔다.** 두 출처가 한 평면에 섞이면 12월에 *"이 항은 누가 잰 것인가"*를 모른다.
기기 항의 이름을 바꾸지 않는다 — 8월 표본과 갈라진다.

### ★ `firedAt` 기준으로 조회한다 — 이 티켓의 함정

`record()`는 **오프라인에서 쌓였다가 나중에 올라오는 경로도 탄다**(ADR-023).
서버 항을 *"지금"* 기준으로 조회하면 **새벽 발동의 스냅샷이 아침 값으로 채워진다.**

그리고 그것은 **네트워크가 나쁜 밤에만 틀린다** — 즉 **가장 읽고 싶은 밤에만.**
T-31이 하마터면 저지를 뻔한 것과 같은 모양이다.

`record()`는 이미 `firedAt`과 `onDate`를 계산해 두었다(`:265~266`). **그 둘을 쓴다.**

### ② `risk_score`를 채운다 — 게이트가 아니다

항이 서버에 다 모이는 지점이 `record()`이므로 **점수도 거기서 낸다.**

**발동은 이미 끝난 뒤다.** 기록 시점에 계산하므로 게이트가 될 수 없고,
그것이 ADR-021이 요구한 형태다 — *"위험도는 기록하되 발동 게이트로 쓰지 않는다."*

식은 단순하게 시작한다. **10월에 실제 스냅샷에서 유도할 것이므로 지금 정교할 이유가 없다** —
지금 필요한 것은 *"그 순간의 값들로 낸 숫자가 남아 있다"*까지다.

### ③ 서로 다른 말을 하는 주석 둘을 정리한다

```
migrations/0010_guard.sql:37   "1단계 결정론 점수 (기록만 — 발동 게이트 아님)"
GuardActivityLog.snapshot()    "점수를 내지 않는다"
```

**둘 다 사실이 된다** — 기기는 안 내고 서버가 낸다. 그 사실을 양쪽에 적는다.

## 범위

```
src/services/guard.ts   record() — 서버 항 조회 · 병합 · risk_score
src/db/index.ts         필요하면 조회 헬퍼 (SQL은 여기에만)
test/smoke.ts           검사
android/.../GuardActivityLog.kt   주석 한 줄
```

**마이그레이션이 필요한지 확인하고 시작한다.** `risk_score`는 칼럼이 이미 있고
`risk_snapshot`은 TEXT JSON이라 **없을 것으로 보이지만, 확인 없이 "없다"고 쓰지 않는다**
(AGENT-CHAIN §5 — T-31에서 이 문장이 틀렸다).

**기기·프런트를 건드리지 않는다**(주석 제외). **발동 경로 무변경.**

## 금지

| 하지 말 것 | 왜 |
|---|---|
| `Date.now()`·현재 시각으로 서버 항 조회 | 오프라인 큐가 아침 값으로 채워진다. **`firedAt` 기준** |
| 기기 항의 키 이름 변경 | 8월 표본과 갈라진다. 더하고, 바꾸지 않는다 |
| 기기 항과 서버 항을 한 평면에 섞기 | 12월에 출처를 모른다 |
| `risk_score`를 발동 판정에 쓰기 | ADR-021. 기록 전용이다 |
| 점수식을 정교하게 만들기 | 10월에 유도한다. 지금은 **남는 것**이 목적이다 |
| `loadTime`을 서비스에서 부르기 | T-23. `t`는 라우트가 넘긴다 |
| 스냅샷이 없을 때 서버 항만으로 행 만들기 | 기기가 안 보낸 것과 서버가 못 찾은 것은 다르다 |

## 완료 조건

```

```

검사:

1. **`firedAt` 기준 조회다** — `fired_at`을 과거로 준 요청이 **그 날의 값**을 담는다
2. **양성 대조** — 오늘 발동은 오늘 값을 담는다
   (1번만 보면 조회가 통째로 죽어 전부 비어도 초록이다 — AGENT-CHAIN §5)

**변이로 확인한다** — 조회를 `t.now` 기준으로 되돌리면 1번만 빨간불이어야 한다.
2번까지 같이 죽으면 둘이 같은 것을 보고 있다는 뜻이다.

### 마이그레이션이 필요했나 (확인 결과)

**없다 — 그리고 `docs/schema-current.sql`을 열어서 확인했다**(AGENT-CHAIN §5, T-31에서 이 문장이 틀렸다):

```
risk_score      INTEGER,     ← CHECK 없음
risk_snapshot   TEXT,        ← CHECK 없음. JSON은 문자열로 들어간다
```

`guard_events`의 CHECK는 `level`·`source`·`ai_verdict`·`reaction`·`override_class`·`outcome`과
0016의 `ai_unavailable_reason`뿐이고 **이 둘엔 없다.** T-31이 물린 그 자리를 먼저 봤다.

⚠️ **다만 트리거가 이 둘을 지킨다**(`trg_guard_event_immutable` — `risk_snapshot`·`risk_score`가
`OLD ≠ NEW`면 ABORT). 이 티켓은 **INSERT 경로에서만** 채우므로 걸리지 않지만,
**나중에 사후 보정으로 채우려는 시도는 409가 된다.** 스냅샷은 발동 시점에 완성되어야 한다.

### `firedAt` 기준인가 — 오프라인 큐 경로를 어떻게 태웠나

`riskServerTerms(env, t, firedAt, onDate, eventId)` — **`t.now`·`t.d`를 안 쓴다.**
`record()`가 이미 계산해 둔 둘을 그대로 넘긴다(`:270~271`).

검사 ①이 **오프라인 큐 경로 그 자체다** — `fired_at`을 9일 전으로 준 요청이 그 날의 Log
(21:00·23:30 두 건)를 담는지 본다: `on_date=P` · `logs_24h=2` · `log_last_min=15`.
검사 ②는 오늘 발동이 오늘 값을 담는지 보는 **양성 대조**다.

**변이가 티켓이 요구한 대로 갈렸다.** 조회를 `t.now`/`t.d`로 되돌리니 **302/1 — ①만 빨간불**이고
②는 초록이다. 둘이 같은 것을 보고 있었다면 함께 죽었을 것이다.
빨간불의 실제 값이 그 오염을 그대로 보여 준다:

```
기대  on_date=2026-08-02 · logs_24h=2 · log_last_min=15     (그 밤)
변이  on_date=2026-08-11 · logs_24h=1 · log_last_min=0      (아침)
```

**한 가지 더 잘랐다 — 발동 이후에 생긴 기록.** 큐가 늦게 오면 그 사이의 Log가 이미 DB에 있는데,
담으면 스냅샷이 **판단 시점에 없던 것을 안다.** `ts <= firedAt`으로 자른다.
티켓은 조회 *기준*만 지적했는데 실제로는 *상한*도 필요했다 — 같은 병의 다른 얼굴이다.
(Feelings·Score는 날짜 단위라 보장도 날짜 단위다. 귀속일 경계 덕에 새벽 발동의 `onDate`는
전날이고 그 날 Feelings는 낮에 쓰인 것이라 실무상 과거다 — 코드에 적어 뒀다.)

### 기기 항과 서버 항을 어떻게 갈랐나

```json
{ "hour": 23.75, "screen_on_sec": 4200, "intervene_sec": 600, ... ,
  "server": { "at": "...", "deadline_min": -12, "protecting": true,
              "logs_24h": 2, "log_last_min": 15, "sleep_prev_first": "08:10",
              "feelings": {...}, "score_last": 62, "score_trend": 7 } }
```

**기기 항은 최상위 그대로 · 서버 항은 `server` 아래 하나에.** 기기 키의 이름을 하나도 안 바꿨다 —
8월 표본과 갈라진다. **더하고, 바꾸지 않는다**(T-31이 `ai_verdict`에서 택한 것과 같은 형태).

검사 셋이 이것을 지킨다: 기기 여덟 키가 **값까지** 같은가 · 서버 항이 최상위에 안 샜는가 ·
그리고 변이 둘(서버가 덮어쓰기 301/2 · 평면에 섞기)이 각각 빨간불이다.
**덮어쓰기 변이는 내가 안 쓴 기존 검사(`risk_snapshot이 JSON으로 보존됨`)도 함께 깼다** —
그 검사가 원래 이 자리를 지키고 있었다.

**스냅샷이 없으면 만들지 않는다.** 기기가 안 보낸 것과 서버가 못 찾은 것은 다른 사실이고,
서버 항만으로 행을 만들면 12월에 그 둘이 같은 모양으로 보인다. 검사 ④의 짝이 그것이다.

### `risk_score` 식 · 왜 이 형태인가

**항 넷. 전부 임시값이고 코드에 그렇게 적었다.**

```
① 심야(0~6시) +25 · 22시 이후 +15
② 사용자가 붙잡고 있던 시간 (screen_on_sec − intervene_sec) 60분↑ +30 · 30분↑ +20
③ 데드라인을 지났으면 +25 · 2시간 이내 +15
④ 발동 직전 60분 안에 Log가 있으면 +10   (각성 신호 §1.2)
상한 100
```

**②가 T-30·T-31을 그대로 쓴다** — 개입 화면이 켜 둔 몫을 빼야 '사용자가 붙잡고 있던 시간'이
된다. 그 둘이 없었으면 이 항은 Guard 자신을 점수로 세었을 것이다.

**넷뿐인 것이 의도다.** 10월에 실제 스냅샷에서 유도할 것이므로 지금 정교할 이유가 없고,
항이 많으면 유도할 때 무엇이 기여했는지 가리기만 어려워진다(§금지 "점수식을 정교하게 만들기").

**게이트가 아니다.** 발동이 끝난 뒤 `record()`에서 계산하므로 **구조적으로** 게이트가 될 수 없다 —
호출부가 INSERT 직전 한 곳뿐이고 어떤 분기도 이 값을 읽지 않는다. ADR-021이 요구한 형태다.
기기가 굳이 `risk_score`를 보내면 그것을 존중한다(9월 PC 에이전트 자리, ADR-022).

### §6.6의 항이 이제 다 있는가 (전수)

| §6.6 / APP-PLAN 항 | 전 | 후 |
|---|---|---|
| 현재 시각 | ✅ `hour` | ✅ (+ `server.at`) |
| 데드라인까지 남은 시간 | ❌ | ✅ `server.deadline_min` (음수 = 지났다) |
| 보호 모드 여부 · 대상 event | △ 칼럼만 | ✅ `server.protecting` (+ `event_id`) |
| 최근 Log 활동 (각성 신호) | ❌ | ✅ `server.logs_24h` · `log_last_min` |
| 수면 추정 (Log 첫/마지막, §1.2) | ❌ | ✅ `server.sleep_prev_first` · `sleep_prev_last` |
| 최근 Feelings · Score 추세 | ❌ | ✅ `server.feelings` · `score_last/avg/trend` |
| foreground app | ✅ `top_apps` | ✅ |
| **`risk_score`** | 항상 NULL | ✅ 서버가 낸다 |

### 설계와 어긋난 점

**없다. 다만 티켓 §범위 밖 파일 둘을 주석만 고쳤다** — 티켓 §할 일 ③이 지시한 그 둘이다
(`migrations/0010_guard.sql`·`GuardActivityLog.kt`). 범위 블록엔 Kotlin만 있고 0010은 없었다.

⚠️ **적용된 마이그레이션의 주석을 고쳤다.** D1은 파일명으로 적용 여부를 추적하고 내용을
해시하지 않으므로 재적용이 일어나지 않고, smoke는 처음부터 다시 적용하므로 영향이 없다.
그래도 **적용된 파일을 건드린 것은 사실이라 적어 둔다** — 다음에 같은 일이 생기면
`db/index.ts` 쪽 주석만 고치는 편이 안전하다.

**데드라인 역산을 두 벌 두지 않았다.** `schedule()` 안에 있던 것을 `protectAxis()`로 꺼내
양쪽이 같은 함수를 부른다. 두 벌이면 UI는 "01:30"이라 쓰고 알람은 다른 시각에 울린다
(`protectingNow`의 주석이 경고한 그것). 검사가 **`schedule()`의 `deadline`과 스냅샷의
`deadline_min`이 분 단위로 정확히 일치**하는지 본다 — 갈라지면 즉시 빨간불이다.

### 막힌 것

**서버 항은 smoke가 태우지만 `risk_score`의 가중치는 검사할 것이 없다.** 숫자가 나오고
0~100 안이라는 것까지가 검사이고, **그 값이 옳은지는 아무도 모른다** — 10월에 유도할 것이라
지금 옳고 그름의 기준이 없다. 감추지 않는다.

⚠️ **Feelings·Score는 '발동 이후 작성'을 초 단위로 가를 수 없다.** 원본에 시각이 없고
날짜뿐이다(`feelings.date` · `daily.date`). 귀속일 경계 덕에 실무상 과거지만 **보장은 날짜 단위**다.
Log는 `ts`가 있어 초 단위로 잘랐다.

⚠️ **`sleep_prev_*`는 Log가 있는 날에만 나온다.** 기록이 없는 밤은 `null`이고 그것이 사실이다 —
"안 잤다"가 아니라 "모른다". 12월에 이 항을 셀 때 `null`을 0으로 읽으면 안 된다.
