# T-73 — Compose 스파이크: 캘린더 하나로 전환 비용을 잰다

**✅ 닫힘 2026-09-14 · 왕복 3회 · 해결 7 / 우회 3 / 못 함 2 / ★구조 1(모양은 왕복 3) / 안 쟀다 3**

**발행** Cowork · 2026-09-14 · **담당** Claude Code · **큼**
**근거** [`APP-PLAN` §6 Compose 스파이크](../../APP-PLAN.md) · [§7 12월 네이티브 전환 결정](../../APP-PLAN.md) · ADR-017
**지금 쓰는 앱 무변경 · 마이그레이션 없음 · 배포 무관 · `src/`·`public/` 무변경**

---

## ★★ 이 티켓은 만드는 티켓이 아니라 **재는 티켓**이다

**`APP-PLAN`이 *"코드 변환 1주일"* 을 검증 가능한 가설이라고 적어 뒀다.** 이 티켓이 그 가설을 잰다.

⚠️⚠️ **그래서 실패해도 성공이다.** *"Compose 로는 이게 안 된다"* 는 **결과이지 잘못이 아니고**,
그것이 12월에 전환을 **안 하는** 근거가 된다.

★★★ **담당이 "성공시켜야 한다"고 느끼면 그 순간 측정이 오염된다.**
막힌 자리를 우회해서 그림만 맞추면 **12월 결정이 거짓 재료 위에 선다** — 이 리포가
`ignored` 40건으로 이미 한 번 겪은 일이다(ADR-047 §정정).

---

## 왜 캘린더인가

**가장 어렵기 때문이다.** 배경 밴드 경계선 모델(설계 §2.2) · 셀 동적 공간 예산 ·
3-pane 슬라이드 · 날짜 팝업. **여기가 되면 나머지는 쉽고, 여기서 막히면 전부 막힌다.**

★ 그래서 **여기서 나온 막힘 목록이 전체 전환 비용의 상한**이다.

## ★★ 재는 것은 코드 작성이 아니라 **튜닝 재현**이다

`APP-PLAN`이 못 박았다 — **이 숫자들이 제품이다:**

```
AXIS_LOCK 20 · 축비 1.9 · TRACK_RATIO 0.35 · FLICK 0.5
CAL_GAP 20 · STRETCH_MAX 90 · STRETCH_K 0.42 · STRETCH_BACK_MS 460
```

⚠️ **그 값을 그대로 옮기면 안 된다.** Compose 는 제스처 시스템이 달라
(`pointerInput` / `Animatable` / `nestedScroll`) **값이 넘어가지 않는다. 다시 유도해야 한다.**

★★ **값을 복사해 넣고 "됐다"고 하는 것이 이 티켓의 가장 큰 실패 모양이다** —
그러면 잰 것이 *"코드가 도나"* 가 되고, **재려던 것은 안 쟀다.**

---

## ★★★ 판정자는 사용자다 — 담당이 "같다"고 말할 수 없다

**"같게 느껴지는가"는 화면만이 답한다.** `verify`도 스크린샷도 이걸 못 잰다.

```
담당이 만든다  →  사용자가 폰에서 만져 본다  →  "아직 다르다" / "같다"
                                                 ★ 이 왕복을 센다
```

⚠️ **"다르다"가 왔을 때 *무엇이* 다른지를 사용자가 말로 못 할 수 있다** — 그게 정상이다.
**그때 담당이 물어야 할 것은 느낌이 아니라 자리다:**

```
언제 다른가    손 뗄 때 / 끌 때 / 경계에서 튕길 때 / 멈출 때
어느 축인가    가로 / 세로 / 대각선에서 축이 안 잠긴다
```

★ **왕복 한 번마다 무엇을 바꿨는지 적는다.** 그 기록이 §보고의 절반이다.

---

## 할 일

### ① 붙일 자리 — 지금 쓰는 앱에 영향 0

⚠️ **사용자는 서명된 릴리스 APK를 매일 쓴다. 그것이 흔들리면 안 된다.**

```
제약    지금 앱의 진입점·화면·동작이 한 글자도 안 바뀐다
방법    ★ 담당이 정한다 (디버그 소스셋 · applicationIdSuffix · 별도 액티비티 …)
```

⚠️ **릴리스 APK에 스파이크가 섞이면 그 자체가 회귀다.** 어느 길을 골랐는지 §보고에 적는다.

### ② 데이터는 고정 픽스처로

**실 D1 에 붙이지 않는다.** 6주치 셀을 손으로 박아 넣는다.

★ **재려는 것은 제스처이지 데이터 파이프라인이 아니다.** 서버를 붙이면
*"네트워크가 느려서 버벅인 것"* 과 *"제스처가 다른 것"* 이 화면에서 같아진다.
⚠️ **픽스처에 고정 날짜를 쓰지 마라**(함정 12) — 상대로 잡는다.

### ③ 만들고, 보여 주고, 왕복한다

**사용자가 "같다"고 할 때까지.** 또는 **막혀서 더 못 갈 때까지.**

⚠️ **막히면 우회하지 말고 멈추고 적어라.** 막힘이 이 티켓의 산출물이다.

---

## 산출물 — ★ 셋 중 셋째가 본체다

```
①  캘린더가 Compose 로 뜬다                    기초. 이것만으로는 아무것도 안 쟀다
②  사용자가 만져서 "같다"고 한다                ★ 튜닝 재현이 됐는가
③  ★★ 막힘 목록                                ← 12월 결정의 재료
```

**③의 형식** — 한 줄에 하나, 넷을 적는다:

```
무엇을 하려 했나  |  Compose 에서 왜 안 됐나  |  어떻게 했나  |  대가
```

`어떻게 했나`는 셋 중 하나다: **해결 · 우회 · 못 함.**
⚠️ **"우회"와 "해결"을 섞지 마라** — 우회는 나머지 화면에서도 다시 나온다.

## ★ 판정 — 계획의 2~3일 : 1주는 **사람 기준이다**

⚠️ **담당은 사람보다 빠르므로 그 선을 그대로 쓰면 항상 "2~3일"이 나온다.**
**그 수는 이 티켓의 자가 아니다.**

**대신 자로 쓰는 것:**

```
★ 막힘 목록의 "우회" + "못 함" 개수        ← 나머지 화면에서 다시 나올 것들
★ 사용자 왕복 횟수                          ← "아직 다르다" 가 몇 번 왔나
```

### ⚠️ ★★ 정정 (2026-09-14 · 왕복 1 · 담당이 잡았다) — 자에 칸이 모자랐다

**이 절이 처음 적은 것은 *"그중 축·경계·튕김에서 온 것이 몇인가"* 뿐이었다.**
그런데 **왕복 1은 그 셋 중 어느 것도 아니었다** — 렌더 1(텍스트) · 성능 1(렉).

★★★ **제스처 차이를 세려던 자가 제스처 아닌 것을 먼저 잡았고, 그것이 어느 칸에도 없었다.**
⚠️ **자에 없는 칸으로 들어온 비용은 0으로 세어진다.** 텍스트 메트릭은 캘린더 하나가 아니라
**글자 있는 모든 화면**에 걸리므로, 안 세면 전환 비용을 화면 수만큼 과소평가한다.

**그래서 왕복을 네 칸으로 센다:**

```
제스처   축 · 경계 · 튕김                    ← 원래 세려던 것
렌더     ★ 텍스트 메트릭 · 레이아웃           ← 왕복 1 이 만든 칸
성능     프레임                              ← 〃
구조     ★★ 계약이 경합으로 바뀐 자리         ← 제일 무겁다 (아래)
```

★★★ **"구조" 칸이 다른 셋과 무게가 다르다.** 앞의 셋은 *"같게 만들 수 있나"* 인데,
구조는 **모델 자체가 다르다** — 웹에서 좌표 하나로 즉시 갈리던 것이 Compose 에서
재구성 한 장을 도는 **상태 경합**이 되면, *"가끔 어긋난다"* 가 튜닝으로 안 없어진다.
⚠️ **이 칸에 들어간 항목은 "우회"가 아니라 따로 세고, 12월 결정에서 가장 크게 읽는다.**

★ **이 정정 자체가 `AGENT-CHAIN` §8의 *"티켓의 전제도 변이 대상이다"* 의 이웃이다** —
이번에 틀린 것은 전제가 아니라 **자**였고, **담당이 시킨 대로 세다가 안 맞는 칸을 발견했다.**

### ⚠️ ★★★ 정정 둘 (2026-09-14 · 왕복 2) — "안 넘어간다"가 비용이라는 전제가 틀렸다

**슬롭 A/B 를 사용자가 만져 보고 판정했다:**

```
8.2dp  (플랫폼 기본값)   ★ 훨씬 낫다
20dp   (웹 AXIS_LOCK)    ⚠️ 옮기면 더 나빠진다
```

**이 결과가 셋을 한꺼번에 답한다** — ① 스위치가 실제로 주입됐다(차이가 느껴지므로 · 함정 18),
② `AXIS_LOCK 20` 은 옮길 값이 아니다, ③ **그리고 이 티켓의 전제 하나가 뒤집힌다.**

```
티켓·APP-PLAN 의 전제   제스처 상수는 안 넘어간다 → 다시 유도해야 한다 → ⚠️ 비용
★★ 실측                제스처 상수는 안 넘어간다 → 넘길 필요가 없다   → 이득
```

★★★ **웹의 여덟 숫자 중 적어도 하나는 "제품"이 아니라 *브라우저 한계 보정값*이었다.**
`AXIS_LOCK 20` 은 브라우저 포인터 이벤트의 노이즈를 견디려고 크게 잡은 값이고,
**네이티브엔 그 노이즈가 없으니 보정도 필요 없다.** `APP-PLAN` §6이 *"이 숫자들이 제품이다"*
라고 한 것은 **전부에는 해당하지 않는다.**

⚠️ **슬롭 하나로 나머지 일곱을 일반화하지 않는다** — 축비·속도 임계는 다른 상수이고,
사용자가 만져 본 것은 슬롭뿐이다. **일반화는 관측이 아니라 추측이다.**

★ **그래도 판정 자에 미치는 영향이 크다: "못 함" 칸의 무게가 가벼워진다.**
Compose 에 축비·속도 임계가 *없는* 것이 **결함이 아니라 그 플랫폼이 같은 문제를 다르게 푼 것**
일 수 있고, **적어도 한 건은 사용자가 그쪽을 더 좋아했다.**
⚠️ **12월 결정에서 "튜닝 재유도"를 비용으로만 적지 않는다** — `APP-PLAN` §7에 올릴 때
이 정정을 함께 싣는다(Cowork 자리).

⚠️ **판정선은 이 티켓이 긋지 않는다.** 첫 스파이크라 비교할 이전 값이 없다 —
**이번 수가 기준이 된다.** 긋는 척하면 그게 추측이다.
★ **해석은 Cowork 가 한다.** 담당은 수를 들고 온다.

## 확인 절차 (사용자)

```
□ 지금 쓰는 앱이 그대로다 (스파이크를 깔아도)     ← 먼저 이것부터

□ ★ 다를 때 "언제" 다른지만 말하면 된다 (손 뗄 때 / 끌 때 / 튕길 때 / 멈출 때)
```

⚠️ **"같다"고 빨리 말해 주지 마라.** 그 한마디가 12월 결정을 바꾼다.

## ★ 이 티켓이 안 하는 것

- **전환을 결정하지 않는다.** 재기만 한다. 결정은 `APP-PLAN` §7, 12월이다.
- **나머지 화면을 안 만든다.** 캘린더 하나다.
- **스파이크를 제품으로 안 키운다.** ⚠️ 커밋은 하되 **버릴 코드**로 다룬다 —
  여기 든 공을 아까워하는 것이 12월 판단을 흐린다.
- **설계문서·`APP-PLAN`을 안 고친다.** 결과를 §7의 판단 입력으로 얹는 것은 Cowork 자리다.

### ① 격리 — 세 겹. 릴리스 빌드가 스파이크를 **구조적으로 못 담는다**

```
1겹  별도 Gradle 모듈            :spike
2겹  별도 applicationId           dev.mond1424.personalos.spike   (폰에 따로 깔린다)
3겹  release 변이 자체를 비활성화  androidComponents.beforeVariants { enable = false }
```

**기존 파일 중 건드린 것은 `android/settings.gradle`의 `include ':spike'` 한 줄뿐이다.**
(루트 `build.gradle`도 안 열었다 — Compose 컴파일러 플러그인은 모듈 안 `plugins {}`로
Gradle Plugin Portal 에서 받는다.)

**근거는 실측이다. 주장이 아니다:**

| 물음 | 확인한 것 | 답 |
|---|---|---|
| 릴리스 빌드에 섞이나 | `gradlew assembleRelease` 로그에서 `:spike:` 태스크 수 | **0** |
| 릴리스 APK 가 바뀌나 | `:app:packageRelease` | **UP-TO-DATE**(재패키징 안 함) |
| 서명이 그대로인가 | `[signing] release SHA-256=` | `C1:D8:…:A6` — `STATE.md` 기록과 같다 |
| `cap sync` 가 한 줄을 지우나 | `@capacitor/cli/dist/android/update.js:168` | **`capacitor.settings.gradle` 만 쓴다** — `settings.gradle` 은 안 건드린다 |

⚠️ **설치해도 지금 앱은 안 흔들린다** — applicationId 가 다르고 서명도 다르다(디버그 키).
**같은 앱을 덮어쓰는 경로가 아예 없다.**

### ② 무엇을 만들었나

`android/spike/` — **버릴 코드다.** 실 D1·서버에 안 붙는다. 픽스처는 전부 오늘 기준 상대(함정 12).

### 왕복 1 (2026-09-14) — ★ 단위 분석에 칸이 하나 늘었다

사용자 관측: `touchSlop = 8.2dp`(2.44배) · 세로 스크롤 멀쩡 · **달 넘길 때만 렉** ·
**셀 일정 텍스트가 아래로 내려가 잘린다.**

#### ★★★ 정정 1 — 단위 분석은 둘이 아니라 **셋**이다

라운드 0 이 이렇게 적었다: *"레이아웃은 넘어가고 제스처는 안 넘어간다."* **반만 맞았다.**

```
레이아웃   넘어간다            gap · 반지름 · 행 높이 — 순수한 기하
제스처     안 넘어간다          슬롭 · 임계 · 감쇠 — 재는 주체가 다르다
★ 텍스트   레이아웃인데 안 넘어간다
```

**왜 셋째 칸이 생기나:** 줄 상자의 높이를 **폰트가 정하고, 폰트는 플랫폼 소유**다.

| | 줄 상자 높이를 누가 정하나 |
|---|---|
| CSS | `line-height:1.3` 이 **강제한다.** 폰트가 무엇이든 상자는 1.3em 이고, 넘치는 글리프는 넘쳐서 그려진다 |
| Compose | `lineHeight` 를 안 주면 **그 폰트의 ascent+descent+leading** 이다. 한글 폴백은 이 값이 크다 |

그래서 CSS 산술로 계산한 14.2dp 칸에 9dp 글자를 넣으면 **상자가 모자라 아래가 잘린다.**

⚠️⚠️ **이것은 캘린더 하나가 아니다. 글자가 있는 모든 화면에 걸린다.**
`1 CSS px = 1 dp` 가 텍스트에서 깨지므로, **웹에서 픽셀로 맞춘 모든 조밀한 레이아웃**
(셀·칩·배지·목록 한 줄 요약)이 같은 자리에서 다시 나온다.
★ 전환 비용 추정에서 **이 칸을 빼면 안 된다** — 화면 수만큼 곱해진다.

#### ★★★ 정정 2 — 라운드 0 의 A1 분류가 **틀렸다**

라운드 0: *"`HorizontalPager`/`PagerState` 어디에도 슬롭을 넣는 자리가 없다 → 우회."*

**아니다. 주입된다.** 바이트코드가 답했다:

```
SuspendingPointerInputModifierNodeImpl.getViewConfiguration()
    → requireLayoutNode(this).viewConfiguration        (필드를 읽는다)

LayoutNode.setCompositionLocalMap(map)
    → map.get(LocalViewConfiguration) → setViewConfiguration(...)   ★ 여기서 쓴다
```

`LocalViewConfiguration` 을 참조하는 클래스는 `androidx.compose.ui` 전체에서 **둘뿐**이고
(`LayoutNode` · `CompositionLocalsKt`) 그 하나가 이 경로다.
→ **`CompositionLocalProvider` 한 겹이면 `HorizontalPager` 를 그대로 둔 채 슬롭만 바뀐다.**

★ **어디서 틀렸나: 읽는 곳을 보고 멈췄다.** `getViewConfiguration()` 은 *"필드에서 읽는다"* 고만
말하지 *"누가 그 필드를 쓰는가"* 를 말하지 않는다. **함정 18 이 바이트코드에 앉은 자리다** —
도구의 답을 증거로 쓰기 전에 그 답이 무엇의 답인지 먼저 갈랐어야 했다.

⚠️ **이 정정은 전환 비용을 낮춘다.** A1 은 "우회"가 아니라 **"해결"** 이다.

#### ① 텍스트 잘림 — 가설은 틀렸고, 사용자가 미리 갈라 둔 둘째 가지였다

**가설(`includeFontPadding`)을 먼저 확인했다. 아니다.**

```
androidx.compose.ui.text.AndroidTextStyle_androidKt.DefaultIncludeFontPadding
    ConstantValue: int 0        ← Compose 1.8 에서 이미 꺼져 있다
```

그러면 사용자가 적어 둔 둘째 가지다 — **셀 공간 예산이 텍스트 높이를 잘못 잡았다.**
정확히는 **내가 CSS 산술(9 × 1.3 + 1 + 1.5 = 14.2)을 dp 로 그대로 옮기고,
그 14.2 가 실제 줄 상자보다 크다고 가정**했다. 가정이 틀렸다(정정 1).

**고친 방법 — 오프셋이 아니다. 줄 상자를 우리가 선언한다:**

```kotlin
lineHeight = dpSp(11.7f)                              // 상자 높이를 못 박는다
lineHeightStyle = LineHeightStyle(Alignment.Center, Trim.None)   // 그 안에서 글리프를 가운데
platformStyle = PlatformTextStyle(includeFontPadding = false)    // 플랫폼 값에 안 기댄다
```

`Alignment.Center` + `Trim.None` 이 **CSS 의 half-leading 과 같은 모델**이다.
폰트가 무엇이든 상자 높이가 `lineHeight` 로 확정되므로, 폰트가 바뀌어도 배율이 바뀌어도 안 깨진다.
행 높이도 가정을 뺐다 — `EV_ROW = EV_LINE + 위패딩 + 아래패딩` 으로 **유도**한다.

★ **분류: 해결.** 오프셋으로 민 것이 아니라, CSS `line-height` 가 하던 일을
Compose 의 같은 뜻 API 로 옮겼다.

★ **그리고 화면이 증명하게 했다** — 진단줄에 **셀 글줄과 같은 스타일로 그린 샘플의
실측 줄 상자 높이**를 dp 로 찍는다. `11.7` 이 아니면 이 고침이 안 먹은 것이다.
(훑기의 0건에 *"스캐너가 살아 있는가"* 를 먼저 묻는 것과 같은 자리.)

#### ② 슬롭 A/B — 팔이 둘인 스위치

#### ★★ §0.4dp — "증상이 나았으니 됐다"로 안 넘긴다

**질문**: 측정 지점이 틀렸나, 목표 계산이 틀렸나.
**답**: ★ **둘 다 아니다. 틀린 것은 내가 세운 판정 기준이다 — 도달 불가능한 수였다.**

**증거**(`androidx.compose.ui.text.android.style.LineHeightStyleSpan`):

```
private final float lineHeight;                              요청은 float
private int firstAscent; ascent; descent; lastDescent;    ★ 상자는 int 넷이다
void chooseHeight(..., Paint.FontMetricsInt)                 플랫폼 계약이 정수 픽셀이다
calculateTargetMetrics():  Math.ceil → f2i 가 세 번
```

**플랫폼의 텍스트 줄 상자는 정수 픽셀로 양자화된다.** 위·아래를 각각 `ceil` 하므로
요청값보다 최대 2px 커진다. 그래서 **11.7dp 라는 목표는 어떤 폰트에서도 정확히 나올 수 없다.**

**관측이 그 설명에 맞는다**(밀도를 직접 안 재서 증명이 아니라 **정합성 확인**이다):
밀도 ≈ 2.81 이면 11.7dp = 32.9px → 위아래 각각 ceil → **34px = 12.09dp → 화면에 `12.1`.**

★ **그리고 두 후보를 가르는 관측이 이미 있다.** `preserveMinimumHeight`(폰트 자연 높이를
바닥으로 삼는 가지)도 후보였는데, **그쪽이면 한글 폴백의 자연 높이인 13dp 안팎이 나와야 한다.**
**12.1 은 그보다 작다** → 상자는 실제로 **폰트 아래로 줄어들었고**(= `lineHeight` 가 먹었고),
남은 0.4 는 양자화다. ⚠️ 만약 13.0 이 나왔다면 그때는 고침이 안 먹은 것이었다.

★★★ **그래서 이것도 셋째 칸이다 — 판정 기준 자체가 같은 실수를 물려받았다.**
줄 상자를 dp 로 선언하는 것까지는 맞았는데, **"11.7 이어야 한다"는 합격선을 dp 로 적으면서
텍스트 치수가 dp 로 표현된다는 가정을 다시 썼다.**

```
틀린 기준   줄상자 == 11.7dp                       ← 플랫폼이 못 만족시킨다
맞는 기준   줄상자 ≤ 행 높이  ·  글꼴 배율을 바꿔도 안 변한다   ← 사용자가 확인한 바로 그것
```

⚠️ **E1 의 분류는 "해결" 그대로다.** 고친 것(줄 상자 선언)은 먹었고, 배율 실험이 그것을 증명했다.
틀린 것은 **고침이 아니라 내가 붙인 자**다.

### 왕복 3 (2026-09-14) — ★★ 구조 칸이 값 1 로 찼다

**관측(사용자)**: 어지간해선 다 정상이다. 그런데 **Today → 캘린더 전이가 끝나기 전에**
화면 **가운데**를 끌면 캘린더에서 안 멈추고 **나 탭까지 쭉 간다.**

⚠️ **코드는 안 고쳤다.** 스파이크는 닫혔고 이것은 측정값이다.

#### 확인 — Cowork 가설은 방향이 맞다. 그런데 기계는 한 겹 아래에 있다

**가설**: *"`settledPage ≠ targetPage` 라 '지금 어느 탭인가'가 확정이 아니고,
그래서 `userScrollEnabled` 판단의 근거가 없다."*

**① 상태는 있다.** `PagerState` 가 전부 공개한다(실측):

```
getCurrentPage() · getSettledPage() · getTargetPage() · getCurrentPageOffsetFraction() · isScrollInProgress()
```

→ **읽을 수 없어서가 아니다.** 가설의 *"물어볼 상태가 없다"* 는 정확히는
***"답을 적용할 틈이 없다"*** 이다.

**② 진짜 기계 — 바이트코드 체인 넷이 이어진다:**

```
DragGestureNode.shouldAwaitTouchSlop      =  !startDragImmediately()
ScrollableNode.startDragImmediately()     =  scrollingLogic.shouldScrollImmediately()
ScrollingLogic.shouldScrollImmediately()  =  scrollableState.isScrollInProgress
                                          || overscrollEffect?.isInProgress
```

**전이 중에는 `isScrollInProgress = true` → 슬롭을 안 기다리고 즉시 드래그가 시작된다.**
(스크롤 중인 목록을 손가락으로 잡아채는 그 동작이다. 정상 동작이고, 의도된 것이다.)

내 게이트는 `Initial` 패스에서 상태를 쓰고, 그 상태가 `userScrollEnabled` 로 반영되려면
**재구성이 한 번 돌아야 한다.** 정착 상태에서는 슬롭(8.2dp)을 넘기는 데 프레임이 몇 장 들어
그 사이에 돈다 — ★ **"어지간해선 다 정상 작동한다"가 바로 그것이다.**
**전이 중에는 그 틈이 0 이다.**

★★★ **그래서 조건이 속도가 아니라 전이 구간인 것이 설명된다.**
천천히 끌어도 똑같다. **느림·빠름의 문제가 아니라 틈의 유무**다.
⚠️ **Cowork 의 *"지연이면 천천히 끌 때 맞아야 한다"* 가 정확히 이 지점을 갈랐다.**

★★ **그리고 같은 문을 여는 조건이 하나 더 있다: `overscrollEffect.isInProgress`.**
경계 스트레치가 되돌아오는 **동안에도 슬롭이 없다.**
→ **A5(스트레치)와 D1 이 조건 하나를 공유한다.** 겹치는 자리가 하나가 아니라는 뜻이다.

#### 내 왕복 1 분류의 어디가 틀렸나

왕복 1 에 *"재구성 한 장 지연 — 계약이 아니라 경합"* 이라고 적었다.
**"경합"은 맞고 "지연"이 틀렸다.**

```
지연이라면   틈이 짧다        → 더 큰 슬롭 · 더 이른 패스로 늘릴 수 있다   = 튜닝 문제
실제로는     플랫폼이 없앤다   → 늘릴 것이 없다                            = 모델 문제
```

#### ★★★ 웹에는 이 결함이 **존재할 수 없다** — 그래서 "우회"가 아니라 "구조"다

```js
bindCarousel(scr, { blocked: (e) => noSwipe(e) || !!S.pick, ... })
function isSwipeEdge(e, host) { const left = host.getBoundingClientRect().left; ... }
```

`blocked(e)` 는 **`pointerdown` 에서 동기로 답하고**, 기준 프레임은 `.screens` —
**슬라이딩하는 페인이 아니라 고정 컨테이너**다.
→ **전이 중이든 아니든 답이 항상 정의돼 있고, 상태도 재구성도 끼어들지 않는다.**

★ **이식하다 깨진 것이 아니라, 웹 모델에서는 생길 수 없는 결함 부류다.**

#### ⚠️ 내 포팅 결함도 하나 있다 — 따로 적는다. 섞으면 12월 수가 부풀어진다

게이트의 `pointerInput` 을 **페이지 안쪽 Box** 에 달아서 x 를 **움직이는 상자** 기준으로 잰다.
웹은 고정 컨테이너 기준이다. 정착 상태에서는 그 상자가 화면을 정확히 채워 **무해**하지만,
전이 중에는 같은 좌표가 다른 뜻이 된다.

★ **다만 이것은 관측된 결함이 아니다** — 전이 중엔 게이트가 **아예 상의되지 않기** 때문이다(위 체인).
**잠복이고, 고칠 수 있다(우회 급).** ⚠️ **구조 칸에 넣지 않는다.**

#### ★★ 대가 — 화면 수가 아니라 **제스처가 겹치는 자리 수**

웹은 겹침을 **훅 하나**에서 좌표 하나로 가른다. 그 훅이 지금 실제로 가르는 자리(소스에서 셈):

```
noStretch    8 선택자                              =  8
```

**탭 다섯이 전부 가로 스와이프다.** 그래서 겹침은 **화면마다가 아니라 제스처마다** 난다.
`overscrollEffect.isInProgress` 가 같은 문을 여는 것까지 합하면
**이 부류는 캘린더 하나로 끝나지 않는다.**

⚠️ **한계**: 위 체인은 **정적으로 확인**한 것이고 관측과 정합한다. 기기에 계측을 붙여
