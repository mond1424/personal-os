**근거** T-54 실측(2026-09-03) · [T-53 §③](T-53-cal-read-device.md) · **APK 필요 · 서버 무변경**

## ★ A의 진짜 원인이었다 — 9/1 진단이 못 본 자리

**2026-09-03 실측:**

```
캘린더 선택 팝업은 뜨는데 목록이 없다.        permission true · targets []
```

**9/1에 "빈 목록이 저장됐다"로 닫은 것의 뒤에 이것이 있었다** — 사용자는
*"안 고른"* 것이 아니라 **고를 것이 없었다.**

⚠️ **진단이 이것을 못 본 이유가 중요하다.** 9/1에 `(e) 안 불림`을 배제한 근거가
*"`setTargets([10])` 왕복 정상"* 이었는데, 그것은 **UI를 안 거친 확인**이다.
**왕복은 정상이고 목록이 비어 있었다.** 배선을 재는 검사가 화면을 대신 세지 못한다.

## 무엇이 어긋났나 — 둘이다

### ① 목록이 0건인데 화면이 침묵한다 — T-54가 고친 것과 같은 결함이 한 칸 옆에 있었다

```js
// app.js:845
body.innerHTML = (r.calendars || []).map(...)   // ← 빈 배열이면 빈 문자열이 된다
```

**권한 분기를 안 타므로** 안내는 *"가져올 캘린더만 고르세요"* 로 뜨고, **몸통만 비어 있다.**
⚠️ **T-54의 §③(`sent 0`을 성공으로 말한다)과 같은 부류다** — *"0건과 실패가 안 갈린다."*
그것을 고친 커밋 바로 옆에 같은 모양이 남아 있었다.

### ② 왜 0건인지 모른다 — 여기가 이 티켓의 본체다

`CalendarReader`는 **두 곳을 읽는다:**

```
Instances  창 범위의 일정        ← 9/1 진단에서 26행 나왔다 (cal 10 에 실물)
Calendars  계정·캘린더 목록       ← 이쪽이 0건이다
```

**일정은 읽히는데 그 일정이 속한 캘린더가 목록에 없다.** 갈래:

```
(a) 쿼리의 selection 이 너무 좁다        VISIBLE=1 · SYNC_EVENTS=1 같은 조건
(b) 읽는 컬럼이 기기에서 null 이라 걸러진다   ACCOUNT_NAME · CALENDAR_DISPLAY_NAME
(c) 예외를 삼키고 빈 배열을 준다          ★ 그러면 ①과 겹쳐 완전히 조용하다
(d) 권한 범위                            permission true 라 아닐 것이다
```

⚠️ **먼저 갈라라. 고치기 전에.** T-53→T-54가 이 순서를 안 지켜 한 바퀴를 더 돌았다.

```js
await Capacitor.Plugins.Cal.calendars()   // calendars 가 정말 [] 인가 · 그 옆에 뭐가 오는가
```

**그리고 provider 를 직접 조회해 `Calendars` 테이블에 몇 행이 있는지 센다** —
`Instances` 26행과 `Calendars` 0행이 같은 기기에서 동시에 참일 수는 없다.
**그 모순이 (a)~(c) 중 어느 것인지 말해 준다.**

## 할 일

### ① 목록이 비면 그렇게 말한다

```
읽을 수 있는 캘린더가 없어요 — <왜인지 한 줄>
```

⚠️ **T-53이 세운 구조를 따른다**: **네이티브는 사실만 주고**(몇 건 읽었나 · 걸러낸 이유),
**문구는 웹이 정한다.** 두 곳에서 정하면 갈라진다.

⚠️ **`calStatusLine`의 상태 넷을 늘리지 마라.** 이것은 **시트 안의 일**이고 Today 줄이 아니다 —
`#cal-result`(T-54)와 같은 급의 자리다.

### ② 0건의 원인을 고친다

진단이 (a)~(c) 중 무엇을 가리키든, **고친 뒤 목록에 실제로 뜨는 것을 실측으로 확인한다.**
⚠️ **jsdom이 못 보는 영역이다** — 검사는 스캐너이고 **판정은 폰이다.**

### ③ ★ 걸러낸 것을 센다

**보이는 캘린더 수만 주지 말고 "몇 개를 왜 걸렀나"를 함께 준다.**

```
{ calendars: [...], total: 8, hidden: 3 }
```

⚠️ **다음에 또 0이 되면 이 숫자 하나로 갈린다** — `total 0`이면 provider가 안 준 것이고,
`total 8 · hidden 8`이면 **우리 필터가 다 걸러낸 것이다.** 지금은 그 둘이 화면에서 같다.
T-43의 `last_seen_count`가 선 자리와 같다.

## 범위

```
android/.../cal/CalendarReader.kt · CalPlugin.kt   목록 쿼리 · total/hidden
public/app.js · index.html                        빈 목록 문구
test/front.mjs                                    검사
```

**서버 무변경 · 마이그레이션 없음.**

⚠️ **`guard/` 아래를 안 건드린다.**
**Antigravity 위임 가능** — 다만 **진단은 직접 하고**, 원인이 갈린 뒤에 배선만 넘긴다.

## 금지

| 하지 말 것 | 왜 |
|---|---|
| 진단 전에 쿼리부터 고치기 | **T-53→T-54가 그래서 한 바퀴 더 돌았다** |
| 빈 목록을 조용히 두기 | ①이 이 티켓의 시작점이다 |
| 필터를 통째로 없애기 | 잡동사니가 된다(T-53 §③). **왜 걸렀는지를 밝히는 것**이 답이다 |
| `calStatusLine` 상태 늘리기 | 시트 안의 일이다. T-53의 구조를 무너뜨리지 마라 |
| `total`·`hidden` 없이 닫기 | **다음에 또 0이면 같은 진단을 처음부터 한다** |
| 배선 왕복으로 화면을 대신 세기 | ⚠️ **9/1 진단이 그래서 틀렸다** |

## 완료 조건

```
typecheck 통과 · smoke 385(변화 없음) · front 385 → 389 이상 · 실패 0 · verify exit 0
assembleRelease BUILD SUCCESSFUL · npx cap sync android 성공
```

**검사**

```
1  목록이 비면 그 사실이 화면에 뜬다
2  ★ 목록이 있으면 안 뜬다                          ← 1의 짝
3  ★ total 과 hidden 이 응답에 실린다
4  ★ total 0 과 total N·hidden N 이 다른 문구다      ← 3의 짝. 이 티켓의 본체
5  목록 쿼리가 Calendars 를 읽는다 (스캐너)
6  ★ 5의 스캐너가 살아 있는가
```

**3·4가 짝이다.** 3만 보면 *"숫자는 싣는데 화면이 안 쓰는 구현"*이 통과하고,
그러면 **다음에 0이 됐을 때 또 처음부터 진단한다.**

⚠️ **검사 신호에 토스트나 `until`을 쓰지 마라**(함정 14). **핸들러가 프라미스를 주면 `await`한다.**

**변이**
- 빈 목록 문구를 뺀다 → **1만** 죽는다
- 항상 문구를 띄운다 → **2만** 죽는다
- `total`·`hidden`을 안 싣는다 → **3만** 죽는다
- 둘을 같은 문구로 → **4만** 죽는다
- `Events`나 다른 테이블로 목록을 만든다 → **5만** 죽는다
- 스캐너를 눈멀게 한다 → **5는 초록 · 6만** 죽는다
