# T-33 — 루프의 시작점을 검사가 지킨다

**발행** Cowork · 2026-08-11 · **담당** Claude Code · **작음**
**상태** ✅ **최종 검토 합격 (수정 하나)** (2026-08-11) · **웹만 — APK와 무관하다**

---

## 무엇이 어긋났나

W4 전수(2026-08-11)가 찾았다. **outcome 카드는 동작하는데 검사가 0이다.**

`td-guard`·`loadGuardOutcome`·`guardPending`·`pending-outcome` — `test/` 전체에 한 건도 없다.
(`front.mjs`의 `outcome` 언급은 전부 Guard 메모리 화면(T-18)이라 다른 곳이다.)

**그리고 이 카드는 조용히 사라지는 종류다** (`app.js:475`):

```js
} catch {
  bar.style.display = "none";    // Guard가 아직 없거나 조회 실패 — 화면을 막지 않는다
}
```

**카드가 안 떠도 · 버튼이 안 먹어도 front 271/0이다.**

## 왜 이 카드인가 — 루프가 여기서 시작한다

`index.html:31`이 스스로 적어 뒀다:

> 이게 붙어야 Guard Memory의 **루프가 닫히고**, 자기 보정의 입력이 생긴다.

**개입은 저절로 기록되지만 `outcome`은 사람이 붙여야만 생긴다.** 카드가 안 뜨면
9~11월 내내 `outcome`이 전부 `NULL`이고, **12월에 §6.5가 읽을 것이 절반만 남는다** —
"개입했다"는 있고 "그래서 어떻게 됐다"가 없다.

**그리고 그 실패는 아무 소리도 내지 않는다.** T-28의 프롬프트와 같은 종류다.

## `display:none`이 두 가지를 뜻한다

```js
if (!r) return void (bar.style.display = "none");   // 물어볼 게 없다 — 정상
} catch {  bar.style.display = "none";  }           // 못 물어봤다 — 회귀
```

**화면에서 둘이 똑같이 보이고, 검사도 가를 수 없다.**
*"안 뜬다"*만 검사하면 **조회가 항상 실패해도 초록**이다 — AGENT-CHAIN §5의 그 자리다.

## 할 일

### ① 세 상태를 구별해서 남긴다

`#td-guard`에 상태를 적는다. **화면 동작은 바뀌지 않는다** — 여전히 안 뜬다.

```
ask     대기가 있다      → 뜬다
none    대기가 없다      → 안 뜬다 (정상)
error   조회가 실패했다  → 안 뜬다 (회귀)
```

**사용자에게 보이는 것을 늘리지 않는다.** `catch`가 화면을 안 막는 판단은 옳다 —
Guard가 아직 없는 기기에서도 Today가 떠야 한다. **바뀌는 것은 기록뿐이다.**

`chrome://inspect`에서 사람도 한 줄로 볼 수 있게 된다.

### ② 검사를 붙인다

`front.mjs`. **세 상태를 각각** 본다 — 하나만 보면 나머지 둘과 구별되지 않는다.

그리고 **버튼이 실제로 먹는지**까지 본다. 이 카드의 설계는 *"한 번에 하나만 묻고,
확정하면 이어서 묻는다"*이므로(`app.js:452`·`:471`) **둘을 만들어 하나를 확정하면
다음 것이 뜨는지**가 그 계약이다.

## 범위

```
public/app.js      loadGuardOutcome — 상태 표기 셋
test/front.mjs     검사
```

**서버·기기·마이그레이션 무변경.** `index.html`도 안 건드린다 — 상태는 JS가 붙인다.
**이 티켓은 APK와 무관하다** — `npm run deploy`만으로 반영된다.

## 금지

| 하지 말 것 | 왜 |
|---|---|
| `catch`에서 화면을 막기 | Guard 없는 기기에서 Today가 안 뜨게 된다. 판단은 옳았다 |
| 실패를 사용자에게 보이기 | 사용자가 할 수 있는 일이 없다. 늘리는 것은 기록뿐 |
| 카드를 여러 개 늘어놓기 | *"대충 눌러 치우게 되고, 그런 outcome은 없는 것보다 나쁘다"*(`app.js:452`) |
| "안 뜬다"만 검사 | 조회가 항상 실패해도 초록이다 — §5 |
| 상태를 `S`에만 두기 | 검사가 DOM으로 본다. 두 곳에 두면 갈라진다 |

## 완료 조건

```

```

검사:

1. **대기가 있으면 뜬다** — 문구에 날짜·제목이 들어간다
2. **확정하면 다음 것을 이어 묻는다** — 둘 만들고 하나 확정
3. **대기가 없으면 안 뜬다** · 상태가 `none`이다
4. **조회가 실패하면 안 뜬다** · 상태가 `error`다 ← **3과 짝이다**

**변이로 확인한다** — `Api.guardPending`을 항상 던지게 만들면 **1·2·3이 죽고 4는 산다.**
넷이 다 죽으면 넷이 같은 것을 보고 있다는 뜻이고, 3만 살면 상태를 안 가른 것이다.

### 세 상태를 어디에 어떻게 남겼나

`#td-guard`의 `data-state`. **DOM에만 둔다** — 검사가 DOM으로 보고, `S`에도 두면 갈라진다.

```js
const set = (state) => {
  bar.dataset.state = state;
  bar.style.display = state === "ask" ? "flex" : "none";
};
```

**화면 동작이 한 글자도 안 바뀐다.** 표시 여부를 상태 하나에서 파생시켰을 뿐이고,
`ask`만 뜨는 것은 전과 같다. 세 자리가 각각 `set("ask")` · `set("none")` · `set("error")`를 부른다.

`catch`가 화면을 안 막는 판단은 그대로다 — Guard가 아직 없는 기기에서도 Today는 떠야 한다.
**바뀐 것은 그 실패가 이제 이름을 갖는다는 것뿐이다.** `chrome://inspect`에서 사람도 한 줄로 본다.

**한 줄 더 고쳤다(행동 무변경).** `send()` 안의 재조회를 `return loadGuardOutcome()`으로 바꿔
`run()`의 프로미스 체인에 넣었다 — 검사가 확정 후 상태를 결정적으로 기다릴 수 있어야 한다.
`loadGuardOutcome`은 자체 `try/catch`라 던지지 않으므로 `run`의 catch 동작도 그대로다.

### 변이 — 셋이 죽고 하나가 사는가

**티켓이 예측한 대로 갈렸다.**

| 변이 | 결과 | 죽은 것 / 산 것 |
|---|---|---|
| 조회가 항상 실패 | **272/5** | ①②③★·버튼 죽음 · **④는 산다** |
| 상태를 안 가름 (`catch`도 `none`) | **275/2** | **④와 ★만** 죽음 |

앞은 *"넷이 다 죽으면 넷이 같은 것을 보고 있다"*를 배제하고, 뒤는 *"3만 살면 상태를 안 가른 것"*을
배제한다. **둘이 서로 다른 자리를 짚어야 상태가 실제로 갈렸다는 증명이 된다.**

⚠️ **첫 변이가 내 검사 하나를 떨어뜨렸다.** 처음엔 버튼 확인을
`ok("두 번째 버튼도 먹는다", (() => { click(); return true; })())`로 썼는데,
**`return true`라 떨어질 수가 없는 검사**였다 — 변이에서도 초록이었다.
숫자만 올리는 검사라 **뺐다**(278 → 277). 클릭은 남기고 판정은 다음 줄의
*"버튼 둘이 각각 success·failure로 간다"*에 맡겼다. 그쪽은 변이에서 빨간불이다.

### 설계와 어긋난 점

없다. 서버·기기·마이그레이션·`index.html` 전부 무변경이고 §금지 다섯을 다 지켰다 —
`catch`가 화면을 안 막고 · 실패를 사용자에게 안 보이고 · 카드는 여전히 하나씩이고 ·
*"안 뜬다"*만 보는 검사가 아니고 · 상태를 `S`에 두지 않았다.

### 막힌 것

**없다.** 다만 이 티켓이 지키는 것은 **카드의 동작**이지 `outcome`이 실제로 쌓이는지가 아니다 —
사람이 안 누르면 여전히 `NULL`이고 그건 검사가 볼 수 있는 것이 아니다.
**9~11월에 `outcome`이 실제로 붙는지는 데이터로만 확인된다.**

### 수정 — 한 함수 안에서 상태와 화면이 갈리는 자리가 하나 남아 있었다

`send()`가 확정 직후 **`set()`을 안 지나고 `display`만 껐다**:

```js
await Api.guardOutcome(r.id, outcome);
bar.style.display = "none";     // ← data-state는 "ask"에 남는다
```

그 순간 `data-state="ask"`인데 화면은 안 보인다. **이 티켓이 없애려던 어긋남이
같은 함수 안에서 생긴 것**이고, 곧 `loadGuardOutcome()`이 다시 정하므로 창은 짧지만
**"두 곳에 두면 갈라진다"는 그 모양 그대로다.**

`set("none")`으로 바꿨다 — 방금 하나를 답했으니 그 순간은 *"물어볼 게 없다"*가 맞다.
**검사는 못 잡는 종류다**(확정 후를 `await`로 건너뛴 뒤에 보므로 그 창을 지나 있다).
코드 읽기로만 나오는 자리라 검토가 볼 값이 여기 있었다. front 277/0 그대로.

### 담당이 자기 검사 하나를 뺀 것이 옳다

`ok("두 번째 버튼도 먹는다", (() => { click(); return true; })())` — **떨어질 수가 없는 검사**였고
변이에서도 초록이었다. 278 → 277로 **숫자를 줄이면서 빼는 판단**은 이 리포의 기준(T-01)과 맞고,
그 사실을 보고에 그대로 적은 것도 맞다. **통과 개수가 늘었다는 것만으로 승인하지 않는다.**

### 이 티켓이 지키지 못하는 것 — 알고 남긴다

**카드의 동작은 지키지만 `outcome`이 실제로 쌓이는지는 못 지킨다.** 사람이 안 누르면 여전히 NULL이고
검사가 볼 수 있는 것이 아니다. 9~11월 데이터가 답한다 — 보고가 그렇게 적었고 동의한다.
