# T-47 — 미루기 말고도 나갈 문이 있다

**발행** Cowork · 2026-08-25 · **담당** Claude Code · **작음**
**근거** [ADR-042](../../APP-ADR.md#adr-042) · **서버 한 줄 + 프런트 · 마이그레이션 없음 · APK 무관**

---

## 무엇이 어긋났나 — 실측된 한 사건이다

`20260817-001` "test"(이 앱의 첫 task)에서 세 걸음이 실제로 일어났다:

```
①  Works 다섯 섹션 어디에도 없었다     지난 예정 + 미완 + defer_count 0
②  Today 재배정 대기의 "미루기 →" 를 눌렀다   ← 유일하게 보이는 경로
③  날짜 말고 고를 것이 없어 8/27 로 미뤘다     ← 지우려던 것이었다
```

**`defer_count` 가 0 → 1 이 됐다.** 그 값은 ADR-036이 2주 상한을 푸는 근거이고
12월에 §6.5가 읽는다. **강요된 한 번이 재료에 섞였다.**

## 할 일

### ① 서버 — '이월 중'이 지난 예정도 잡는다

`worksDeferring`의 조건 한 줄:

```sql
WHERE s.state = 'not_finished' AND (s.defer_count > 0 OR s.latest_date < ?)
```

**오늘(`t.d`)을 바인딩해야 하므로 시그니처가 바뀐다** — `segment()`의 `deferring` 분기가
`t.d`를 넘긴다(`worksScheduled`가 이미 그렇게 한다).

⚠️ **`first_date`는 그대로 둔다.** 화면이 *"8월 17일의 test"*로 읽히는 근거가 그 값이다.

⚠️ **`reassignQueue`를 건드리지 않는다.** 같은 집합을 닮아 가지만 **다른 화면의 다른 목적**이다
(Today = *"오늘 뭘 할까"* · Works = *"전체를 정리"*). 하나로 합치면 한쪽을 고칠 때 다른 쪽이 딸려 간다.

### ② 프런트 — 날짜 선택 화면에서 그 일로 돌아간다

`#pick-banner`에 출구를 **하나** 더 둔다 — 그 task 의 상세 시트를 연다.

```
지금   [ 날짜를 탭해 일정 정하기 — test ]                 [취소]
뒤     [ 날짜를 탭해 일정 정하기 — test · 이 일 보기 ]     [취소]
```

**미루기 모드(`mode === "defer"`)에서만 보인다.** 대기 → 첫 일정(`mode === "schedule"`)은
미룬 것이 아니라 처음 잡는 것이라 대안이 다르다.

⚠️ **시트를 열어도 pick 모드는 살린다.** 닫으면 캘린더로 돌아와 계속 고를 수 있다 —
*"역시 미루자"* 가 한 단계도 안 늘어야 한다.

### ③ ★ 대상이 사라지면 pick 을 푼다 — 이 티켓의 핵심

```
시트에서 완료 · 취소 · 삭제가 성공  →  exitPick (또는 cancelPick)
```

**대상이 없어졌는데 pick 이 남으면 다음 탭이 없는 일을 미룬다.** 404가 조용히 뜨거나,
더 나쁘게는 **엉뚱한 일이 옮겨간다.** ②를 만들면서 이것을 안 하면 **버그를 하나 새로 만드는 것**이다.

## 금지

| 하지 말 것 | 왜 |
|---|---|
| pickbar 에 완료·취소·삭제 버튼 셋 | **두 벌이 된다.** 시트에 이미 셋 다 있다 |
| Works 에 섹션 새로 만들기 | 세그가 여섯이 된다. '이월 중'의 뜻이 이 집합을 덮는다 |
| `worksScheduled` 에 지난 예정 넣기 | *"예정"*이 과거를 뜻하게 된다 |
| `reassignQueue` 손대기 | 다른 화면·다른 목적이다. 합치면 함께 갈라진다 |
| 시트를 열 때 pick 을 끝내기 | *"역시 미루자"* 가 한 단계 는다 |
| 대상이 사라져도 pick 유지 | **없는 일을 미루게 된다.** ③이 이 티켓의 핵심 |
| `schedule` 모드에도 출구 붙이기 | 미룬 것이 아니다 — 대안이 다르다 |
| 이미 오른 `defer_count` 되돌리기 | **기록은 사실의 기록이다.** 구조를 고쳐 다음을 막는다 |

## 완료 조건

```
typecheck 통과 · smoke 359 → 362 이상 · front 327 → 331 이상 · 실패 0 · verify exit 0
```

**검사**

```
서버
1  지난 예정 + 미완 + defer_count 0 인 task 가 '이월 중'에 나온다      ← 실제로 놓쳤던 것
2  ★ 오늘·앞으로의 예정만 있는 task 는 '이월 중'에 없다                 ← 1의 짝. 조건이 다 삼키지 않았나
3  완료·취소된 task 는 지난 예정이 있어도 없다                          ← state 조건이 살아 있나

화면
4  미루기 모드에서 pickbar 에 '이 일 보기'가 있고 누르면 시트가 열린다
5  ★ 일정 정하기 모드에는 없다                                          ← 4의 짝
6  ★ 시트를 닫으면 pick 이 살아 있다 (캘린더로 돌아온다)
7  ★ 시트에서 취소가 성공하면 pick 이 풀린다                            ← 대상이 사라진 자리
8  pick 이 풀린 뒤 날짜를 탭해도 아무 일이 없다 (없는 일을 안 미룬다)
```

**2와 6이 짝이다.** 1·4만 보면 *"조건이 전부를 삼켜 '이월 중'이 모든 미완이 된 구현"*과
*"시트를 열면서 pick 을 끝내 버리는 구현"*이 둘 다 통과한다 —
T-33·T-38·T-39·T-41·T-43·T-44·T-45·T-46에서 **여덟 번** 물린 자리다.

**7과 8도 짝이다.** 7만 보면 *"배너만 지우고 `S.pick` 은 남는 구현"*이 통과한다.
**8이 실제로 날짜를 탭한다** — 상태가 진짜 없어졌는지는 그것으로만 갈린다.

**변이**
- 조건에서 `defer_count > 0`을 뺀다(지난 것만) → **2는 초록 · 1도 초록 · 3만** 죽는지 확인하고,
  **아니면 검사가 약한 것이다** — 이 변이가 아무것도 안 죽이면 짝을 하나 더 만들어라
- 조건을 `state` 없이 쓴다 → **3만** 죽는다
- 시트를 열 때 `exitPick()`을 부른다 → **6만** 죽는다
- 취소 성공 시 해제를 뺀다 → **7·8** 죽는다 (둘이 같은 결함의 두 증상이다)
- 배너 텍스트만 지우고 `S.pick`은 남긴다 → **7은 초록 · 8만** 죽는다

**'이월 중' 조건 (바인딩 포함)**

```sql
WHERE s.state = 'not_finished' AND (s.defer_count > 0 OR s.latest_date < ?)
ORDER BY s.defer_count DESC
```

`worksDeferring(env, d)`로 시그니처가 바뀌었고 `segment("deferring")`이 `t.d`를 넘긴다
(`worksScheduled`와 같은 모양). `first_date`·`ORDER BY`는 손대지 않았다.
**`reassignQueue`는 한 글자도 안 건드렸다.**

`latest_date`가 NULL인 대기 task는 비교가 NULL이라 안 걸린다 — 그쪽은 '대기'의 몫이다.

**pick 해제를 어디에 걸었나 — 넷이다**

| 자리 | 무엇 |
|---|---|
| `completeFromSheet` | 완료 버튼 |
| `execCancel` | 취소(확인 시트 · 삭제 409의 '대신 취소' 경로도 여기로 온다) |
| `$("#tk-delete").onclick` | 삭제 성공 |
| `setRateOn`의 `rate === 100` | **다이얼이 100에 닿는 것도 완료다** — 결과가 같으면 해제도 같아야 한다 |

전부 `releasePick(id)` 한 함수를 부른다. **`id`로 가른다** — 고르는 중인 것과 다른 일을
처리했다면 그 pick은 여전히 유효하다. 해제는 `exitPick`이 아니라 `cancelPick`이다:
대상이 없어진 캘린더에 남기지 않고 **떠나온 탭으로 돌려보낸다.**

**검사 8이 실제로 날짜를 탭하는가 — 그렇다**

`#cal-track .c[data-d=…]`에 실제로 click을 던진다(셀의 `onclick="openDay('…')"`가 그대로 탄다).
탭할 날짜는 상한·하한을 다시 계산하지 않고 **앱의 `pickable()`에 물어서** 고른다 —
범위 밖을 고르면 `pickable`이 막아 주므로 해제와 무관하게 통과하는 공회전이 된다.
판정은 ① 미루기 확인 시트(`#sh-defer`)가 안 뜬다 ② 그 task의 `entries`에 그 날짜가 없다.

**변이 — 여섯 개를 실제로 돌렸다**

| 변이 | 죽은 것 | 예상대로인가 |
|---|---|---|
| 조건에서 `defer_count > 0` 제거 | **★ 미룬 일은 도착지가 앞날이어도 남는다** 하나 | 티켓이 예고한 대로 **1·2·3은 전부 초록** — 그래서 짝을 미리 하나 더 만들어 뒀다 |
| 조건에서 `state` 제거 | ③ (`fin=true can=true` — 두 갈래 다 잡았다) | ○ |
| `latest_date < ?` → `<= ?` | ★② | ○ (경계 — 오늘 할 일이 '이월 중'이 되는 자리) |
| 시트를 열 때 `exitPick()` | ★⑥ · ⑦′ | ⑦′도 죽는다 — 그 변이는 `origin`을 통째로 잃는다 |
| `execCancel`의 해제 제거 | ★⑦ · ⑦′ · ★⑧ | ○ (`deferSheet=true` — **취소된 일에 미루기 시트가 실제로 떴다**) |
| 배너 class만 지우고 `S.pick` 유지 | ⑦′ · ★⑧ (**⑦은 초록**) | ○ — 7·8 짝이 실제로 갈렸다 |

**첫 변이가 아무것도 안 죽였다 → 짝을 하나 더 만들었다** (티켓 §변이의 지시)

```
★ 미룬 일은 도착지가 앞날이어도 '이월 중'에 남는다 (조건의 두 갈래가 둘 다 산다)
```

미룬 일의 `latest_date`는 **앞날**이라 `latest_date < D`가 안 잡는다. 두 갈래 중 하나만
남기면 여기가 빨간불이 된다. 재료는 [3]이 이미 만들어 둔 `tC`(D → D+2, `defer_count` 1)다.

**⑦을 둘로 갈랐다** — `★⑦`(배너가 사라진다)과 `⑦′`(떠나온 탭으로 돌아온다).
한 줄로 두면 "시트를 열 때 pick을 끝내는" 변이가 ⑥과 ⑦을 함께 죽여 **어느 결함이 무엇을
죽였는지 못 읽는다**. 가른 뒤에는 그 변이가 ⑥+⑦′을, 해제 누락이 ⑦+⑦′+⑧을 죽인다.

**티켓 범위 밖을 한 줄 건드렸다 — `renderWorks`의 '이월 중' 행**

`${r.defer_count}회 이월`이 그대로면 이번에 들어온 것들이 **"0회 이월"**로 읽힌다 —
①이 만든 거짓말이다. `defer_count > 0 ? "N회 이월" : "지난 예정"`으로 갈랐다.
`first_date`는 그대로라 *"8월 17일의 test"*는 유지된다. **금지 목록에 걸리지 않는다**
(새 섹션도, 버튼 복제도 아니다). Cowork 확인 필요.

**검사 픽스처에서 두 번 물렸다 (둘 다 실측)**

1. **마감된 날엔 예정을 *추가*하는 것도 트리거가 막는다** — `CLAUDE.md` 함정 6의
   *"일정은 추가만"* 은 `events` 얘기지 `schedule_entries`가 아니다.
   smoke가 어느 과거 날을 마감했는지는 앞 절이 늘 때마다 달라지므로 고정 오프셋을 박지 않고
   **원장에 물어서** 열린 과거 날을 고른다.
2. **취소는 열린 날의 예정을 지운다** — 항목을 넣고 취소하면 `latest_date`가 NULL이 되어
   **state 조건이 죽어도 통과하는 픽스처**가 된다. 순서를 뒤집어(취소 → 항목) 고쳤고,
   그래서 위 표의 `can=true`가 실제로 잡혔다.
3. front 쪽은 **오늘로 task를 잡을 수 없다**(그 시점의 검사 DB는 오늘이 이미 마감이라 409).
   내일로 잡았고, 그것이 실사용의 미루기와 같은 모양이다.
