## ★★★ 무엇을 바꾸나 — T-78의 결정 하나를 뒤집는다

**T-78 §금지:** *"task의 예정일을 **마감일로** 넣기 — *'마감일에 하라'* 는 거짓 조언이다"*

**2026-09-21 사용자:** *"자동으로 마감일에 넣자."* + *"한 달 이상 남은 일은 목록의 가장
아래쪽에서, 회색으로 비활성화 된 느낌으로 (실제로 비활성화는 아님) 표시하는 게 좋을듯"*

★★★★★ **두 요구가 서로를 완성한다:**

```
T-78 의 근거   ⚠️ 앱이 마감일을 고르면 그것은 앱의 해석이다
지금           ★ 사용자가 정한 기본값이다 — 해석이 아니라 설정이다
남는 위험      "마감일에 하라" 로 읽히는 것
★ 그 완화      먼 것은 약하게 보인다 — "거기 있지만 지금 할 일은 아니다"
```

⚠️ **④ 없이 ②만 하면 화면이 금세 지저분해진다.** 둘은 한 티켓이다.

### ⚠️⚠️ ★★★ 그런데 T-78의 근거 셋 중 하나만 깨끗하게 풀렸다 — 적어 둔다

```
③ "자동은 해석이다"      ★ 풀렸다. 사용자가 고른 기본값이지 앱의 해석이 아니다
② "대기가 실제 상태다"   ⚠️ 안 풀렸다 — 아래가 기각한다
① "마감일에 하라는 거짓"  ⚠️⚠️ 안 풀렸다 — ④는 지저분함을 고치지 늦음을 안 고친다
```

**②를 기각하는 근거 — 신호가 이미 안 읽히고 있었다:**

```
T-78 이후 수락한 것   대기로 갔다
사용자가 날짜를 정했나 ⚠️ 안 정했다
그리고 요청이 왔다     "자동으로 마감일에 넣자"
```

★★★★ **정직한 신호라도 아무도 안 읽으면 신호가 아니다.**
***"자동으로"*** 라는 요청 자체가 **그 신호를 읽는 비용을 안 내겠다는 판정**이고,
**그 판정이 T-78의 가정보다 세다.**

**①은 남는다 — ④가 그것을 안 고친다:**

```
④ 가 고치는 것    지저분함 (사용자가 말한 그것)
④ 가 못 고치는 것 ★ 11/30 과제는 11/29 까지 할 일 목록에 안 뜬다
```

⚠️ **그리고 그날은 이미 늦은 날이다.** ★ 다만 **대기도 그것을 안 막고 있었다** —
T-80이 나쁘게 만드는 것이 아니라 **원래 안 되던 것이 그대로 남는다.**

**★★ 재검토 트리거 — 이것으로 판정한다:**

```
11/30 이 왔을 때 그 과제 둘이 ★ 그날 처음 보이고, 그날 못 한다
  → "마감일에 하라" 가 거짓 조언이었다는 실측이다
  ⚠️ 그때 처방은 "예정을 앞당긴다" 가 아니다 — 그건 여전히 해석이다(③)
  ★ "마감이 다가오는 것을 말한다" 가 그 자리이고, 별도 티켓이다
```

### ★★ 그리고 과거 마감이 지금 처음으로 눌릴 수 있다

**T-75가 창 밖·창 아래를 둘 다 열었다** — `new` 4건 중 **2건이 이미 지난 마감**이다.

```
09-14 13:10  벡터대수학 2주차 …        ★ 과거
09-21 13:15  벡터대수학 3주차 …        ★ 과거 (오늘인데 지났다)
```

**2026-09-21 사용자:** *"시간이 지난 후 추가를 누르게 되면 **'이미 지났는데, 완료했냐?
아니면 등록할까?'** 묻는 과정이 있어야 할 듯"*

⚠️⚠️ **그리고 ②가 함정 6에 바로 부딪친다** — **마감된 날은 `schedule_entries`에
추가조차 안 된다.** 과거 마감을 예정으로 넣으면 **409다.** T-78이 `date`를 안 넘겨서
지금까지 안 걸렸을 뿐이고, **②를 하는 순간 열린다.**

★★★ **그래서 ②·③은 같은 변경의 앞뒤다.**

## 할 일

### ① 먼저 확인한다 — ⚠️ ④의 전제다

```
□ ★★ Works 의 "예정" 목록이 먼 날짜를 지금 어떻게 보여주는가
      · 날짜별 그룹이면 11/30 은 목록에 한 줄인가, 아니면 그 앞 날마다 반복되는가
      · 정렬이 날짜 오름차순이면 "맨 아래" 는 이미 자동인가
□ ★ Today 에는 그날 예정만 오는가 (먼 것이 Today 에 새지 않는가)
□ 먼 예정을 약하게 그릴 자리가 어디인가 (trow 의 클래스 하나면 되는가)
□ ★ 오늘이 마감된 날이면 오늘 날짜로도 schedule_entries 가 막히는가
```

★★ **첫 줄이 사용자 판정과 다를 수 있다.** 사용자는 *"그 앞 모든 날에서 예정의 한 자리를
차지"* 라고 말했는데, **날짜별 그룹이면 한 줄일 뿐이다.**
⚠️ **다르면 고치는 것이 달라진다 — 적고 진행해라.** 처방(맨 아래 · 회색)은 어느 쪽이든 같다.
★ 넷째가 *"막힌다"* 면 ③의 폴백이 필요하다(아래).

### ② `accept` — 미래 마감이면 예정일 = 마감일

```ts
const task = await tasks.createTask(env, t, { title: row.summary });          // 지금
const task = await tasks.createTask(env, t, { title: row.summary, date });    // 바꿈
```

★ **`createTask`를 그대로 쓴다**(T-78 §금지 — 기존 경로). `date`는 이미 `events.create`가 쓰는 그 값이다.
⚠️ **시각은 안 넘긴다** — 마감 시각은 `events`가 갖는다. **예정은 날짜다.**

⚠️⚠️ **T-78 검사 2(*"그 task에 예정일이 없다 (대기)"*)가 이제 옛 동작을 고정한다.**
★★ **지우지 말고 명제를 다시 세워라** — `CLAUDE.md` §기준선의 *"검사가 옛 동작을 검사하고
있으면 검사를 고치고 그 사실을 말한다"* 그대로이고, **§보고에 그 사실을 적어라.**

### ③ 과거 마감이면 — **묻는다**

```
[추가] · 마감이 미래   →  ★ 그대로 들어간다. 안 묻는다
[추가] · 마감이 과거   →  ★ "이미 지난 마감이에요"
                            이미 했어요     →  event 만.  ⚠️ task 를 안 만든다
                            아직 해야 해요  →  event + task,  예정일 = ★ 오늘
                            안 할래요       →  dismiss
```

★★★ **"이미 했어요"가 task 를 안 만드는 이유는 *하지 않은 것을 기록하지 않는다*이다.**
**언제 얼마나 했는지 모르는 채 완료 task 를 만들면 원장이 거짓이 되고, 분석이 그 위에 선다.**
⚠️ **`event`는 만든다** — *"그 마감이 있었다"* 는 사실이고, 달력은 사실의 기록이다.
★ **그 구분은 `collected_items.task_id`가 NULL 로 남아 이미 진다**(T-78). **마이그레이션 없다.**

★★ **"아직 해야 해요"의 예정일이 *오늘*인 이유** — **마감이 지났으면 지금이 제일 빠른 날이다.**
⚠️ **과거 날짜로 넣지 마라. 함정 6이다**(마감된 날은 `schedule_entries` 추가까지 막힌다).
★ **①의 넷째가 *"오늘도 막힌다"* 를 보이면 그때만 대기로 떨어뜨리고 그 사실을 토스트가 말한다.**

⚠️ **멱등을 깨지 마라** — `accept`는 이미 `WHERE state <> 'accepted'`로 멱등이다.
**세 갈래 중 무엇을 골라도 두 번 안 만들어져야 한다.**

### ④ 먼 예정은 약하게 — **끄는 것이 아니다**

```
한 달 이상 남았다   ★ 목록 맨 아래 · 회색      ← 눌리고, 열리고, 완료된다
그 밖               지금 그대로
```

⚠️ **실제로 비활성화하지 마라**(사용자 명시). **`disabled`·`pointer-events:none`을 쓰지 않는다.**
★ **색은 CSS 변수만**(함정 5). 다크 대응은 항상 짝.

★★ **경계는 한 곳에만 둔다.** 파생이므로 **조회 시 계산**이고 저장하지 않는다.
⚠️ **검사가 그 상수를 하드코딩하지 마라**(함정 15 — 검사와 구현이 같은 값을 공유하면
그 값이 틀렸을 때 함께 틀린다). **`now` 기준 상대로 잡고 넉넉히 넘겨라.**

★ **①의 첫째가 *"맨 아래가 이미 자동"* 이면 ④는 회색 하나로 끝난다.** 그러면 그렇게 적어라.

**검사**

```
1   ★ 미래 마감을 수락하면 예정일 = 마감일                  ← 본체 (T-78 검사 2 재정의)
2   ★ 그때 안 묻는다 (바로 들어간다)                        ← "자동으로"
3   ★★ 과거 마감을 수락하면 묻는다                          ← ③의 본체
4   ★ "이미 했어요" → event 1 · task 0                      ← 기록 안 함
5   ★ "아직" → event 1 · task 1 · 예정일 = 오늘             ← ⚠️ 마감일이 아니다
6   ★ "안 할래요" → dismiss. event·task 0                   ← 경계
7   ★ 세 갈래 어느 쪽도 두 번 안 만든다                     ← 멱등
8   ★ 예정에 시각이 안 들어간다                             ← 날짜만
9   ★★ 한 달 이상 남은 예정이 약한 표시를 받는다
10  ★ 그런데 여전히 눌리고 열린다                           ← 9의 짝. "비활성화 아님"
11  ★ 한 달 안쪽은 전과 똑같다                              ← 회귀
12  ★ event 는 전과 똑같다 (title·date·time)                ← T-78 회귀
```

⚠️ **5가 없으면 *"과거도 마감일에 박는"* 구현이 통과한다** — task 는 생기니 3·4만 보면 초록이고,
**409가 실사용에서만 난다**(함정 6).
⚠️ **10이 없으면 9가 *"숨긴다"* 로도 통과한다** — 화면에서 약한 것과 없는 것이 갈려야 한다.
⚠️ **2가 없으면 *"항상 묻는"* 구현이 통과한다** — 사용자가 고른 것의 반대다.
⚠️ **픽스처에 고정 날짜를 쓰지 마라**(함정 12). **과거·미래·한 달 밖은 `now` 기준 상대로.**

**변이**

```
date 를 안 넘긴다                  → 1 만 죽는다
미래에도 묻는다                    → ★ 2 만 죽는다 (1은 초록 — 결국 들어가니까)
과거에 안 묻고 그냥 넣는다          → 3 만 죽는다
"이미 했어요"에 task 를 만든다      → 4 만 죽는다
"아직"의 예정일을 마감일로 넣는다   → ★ 5 만 죽는다 (3·4는 초록)
"안 할래요"가 event 를 만든다       → 6 만 죽는다
멱등 가드를 뺀다                    → 7 만 죽는다
예정에 time 을 함께 넘긴다          → 8 만 죽는다
경계 판정을 뒤집는다                → 9 만 죽는다
약한 표시에 pointer-events:none     → ★ 10 만 죽는다 (9는 초록 — 회색이니까)
경계를 0으로 만든다                 → 9 · 11 이 함께 죽는다 (필연 — 전부 약해진다)

```

★★ **둘째·다섯째·열째가 짝의 존재 이유다.**
⚠️ **열한째가 둘을 죽이는 것은 필연이다** — 좁히려면 검사가 눈이 멀어야 한다
(`AGENT-CHAIN` §8 §가르는 시험: **표본을 바꿔도 안 갈린다**).
★★★ **변이가 *붙었는지*와 *되돌아갔는지*를 둘 다 본다**(함정 16).
⚠️ **그리고 검사가 *저절로 참*이 되지 않았는지 본다**(§8 — `||`로 넓히지 않았나 ·

## ★ 이 티켓이 안 하는 것

- **`events`의 date·time 을 안 바꾼다** — 마감은 마감이다(T-78 · 설계 §1.7).
- **먼 예정을 자동으로 앞당기지 않는다** — *"언제 할지"* 는 사용자가 옮긴다.
- **이미 `accepted`인 건을 소급 처리하지 않는다**(T-74·T-78과 같은 규칙).
- **대기(미배정) 개념을 없애지 않는다** — 손으로 만든 task 는 여전히 대기로 갈 수 있다.
- **Guard 쪽은 한 줄도 안 건드린다.**
- **한 달 경계를 설정으로 만들지 않는다** — 상수 한 곳. **아프면 그때 연다.**
