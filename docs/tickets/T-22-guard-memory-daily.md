# T-22 — Guard 메모리를 일별로 접는다

**발행** Cowork · 2026-08-06 · **담당** Codex CLI · **상태** ✅ 닫힘 (1차 검토 합격 2026-08-06)

---

## 왜

T-18이 만든 Guard 메모리는 **개입 하나가 한 줄**이다. 지금은 몇 건뿐이라 괜찮지만
9~11월 실사용에서 밤마다 2~4건씩 쌓이면 **한 달이면 백 줄이 넘는다.**

`guard_events`는 §6.5 자기 보정의 원재료다 — 사람이 실제로 들여다볼 수 있어야 값이 있다.
**스크롤로만 볼 수 있는 목록은 안 보게 된다.**

## 방향 — 두 층

```
8/5 (수)   개입 3 · 수락 1 · 그래도 계속 1 · 무반응 1     ← 기본
  └ 누르면 그날의 개입 줄들 (T-18이 만든 것)              ← 펼침

최근 7일 표시  →  [더 보기 (N일)]  →  전부
```

**T-18의 줄을 버리지 않는다.** 그 위에 한 층을 얹는 것이다 —
요약만 남기면 "왜 떴나"와 "어떤 사유로 빠져나갔나"가 사라지고, 그게 §6.5의 재료다.

- 접힌 상태가 기본. 하루를 누르면 그날만 펼쳐진다
- `[더 보기]`에 **남은 일수**를 적는다 — T-18의 이력 축약과 같은 형식
- 7일 이하면 `[더 보기]`가 없다

## 요약에 무엇을 담나

```
개입 수 · 반응별 개수
```

반응은 T-18이 이미 사람의 말로 옮겼다 — 그 표기를 그대로 쓴다. **두 벌로 만들지 않는다.**
`reaction = null`(무반응)도 한 종류로 센다. 그날 가장 흔한 것이 무반응이면 그것이 신호다.

## 날짜로 묶는 것 — **이 티켓의 덫**

**`on_date`로 묶는다. `fired_at`으로 묶지 않는다.**

```
guard_events.on_date    귀속일 — 서버가 기록 시점에 확정했다
guard_events.fired_at   발동 시각 — 로컬 오프셋이 붙어 있다
```

`fired_at`의 앞 10자를 잘라 묶으면 **새벽 개입이 다음 날로 간다.**
하루 경계는 05:00이고, Guard가 가장 많이 발동하는 시간대가 바로 그 앞이다 —
**01:30에 뜬 개입은 전날 것이다.**

T-16이 memo에서 겪은 것과 같은 자리다. 그때는 서버에 맡겨 풀었고,
여기서는 **서버가 이미 `on_date`를 주고 있다.** 쓰기만 하면 된다.

## 범위

```
public/index.html   필요하면 훅
public/app.js       일별 묶기 · 요약 · 접기/펼치기 · 더 보기
public/style.css    표시
test/front.mjs      검사
```

**서버를 건드리지 않는다.** `on_date`는 `guard_events` 컬럼이고 `SELECT *`로 이미 실려 온다.

## 금지

| 하지 말 것 | 왜 |
|---|---|
| `fired_at`으로 날짜를 묶기 | 새벽 개입이 다음 날로 간다. `on_date`가 귀속일이다 |
| 프런트에서 귀속일 계산 | 경계가 사용자 설정이다. 서버가 확정해서 준다 |
| T-18의 개입 줄을 지우고 요약만 남기기 | "왜 떴나"가 사라진다. §6.5의 재료다 |
| 반응 표기를 새로 만들기 | T-18이 이미 옮겼다. 두 벌이 되면 갈라진다 |
| 이력을 잘라서 버리기 | 접는 것은 표시다. 펼치면 전부 나와야 한다 |
| 짧고 일반적인 새 클래스명 | 전역 충돌 **세 번**. 접두사(`.gday-…`) |
| 색 리터럴 · `scrollIntoView` | 함정 5 · 1. 펼칠 때 위치를 잡고 싶어지는 자리다 |

```

```

검사:

1. 개입이 날짜별로 묶인다
2. 8일 이상이면 7일만 보이고 `[더 보기]`에 남은 일수가 있다
3. 7일 이하면 `[더 보기]`가 없다
4. **`fired_at`이 새벽 01:30이고 `on_date`가 전날인 개입이 전날에 묶인다**
5. 하루를 누르면 그날 개입 줄들이 펼쳐진다 (T-18의 표시 그대로)
6. 0건이면 "아직 없음"

**4번이 이 티켓의 덫이다.** `fired_at.slice(0,10)`으로 묶어도 1·2·3·5·6은 전부 통과하고,
**밤에 뜬 개입만 하루씩 밀린다** — 그리고 그게 대부분이다.

```

  ✅ 검토 세션이 보고를 믿지 않고 직접 재현했다. 그룹 키를 `row.fired_at.slice(0, 10)`으로 바꾸니
     front 249 → **248 · 실패 1**이고, 유일한 실패가
     「05:00 경계 전 개입은 fired_at 날짜가 아니라 on_date로 묶음」이었다. 원복 후 249 · 실패 0.
     검사가 덫을 제대로 겨눈 이유: 픽스처 `gb1`이 `on_date=2026-08-05`인데 `fired_at=2026-08-06T01:30`이라
     **두 값이 하루 어긋나 있고**, 나머지 픽스처는 둘이 같아 1·2·3·5·6이 변이에 반응하지 않는다.

on_date 를 쓰는가 (프런트에 귀속일 계산이 없는가):
```
