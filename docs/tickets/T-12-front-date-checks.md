# T-12 — front 날짜 검사가 오늘에 의존하지 않게 한다

**발행** Cowork · 2026-08-03 · **담당** Codex CLI · **상태** ⬜ 대기 · **선행: 다른 티켓보다 먼저**

---

## 목표

`test/front.mjs`의 날짜 관련 검사가 **어느 날 돌려도 같은 결과**를 내게 한다.

**왜** — 오늘(2026-08-03) front가 **214 중 209 통과 · 실패 5**다. 코드 변경과 무관하고,
검사가 "오늘"에 의존해 특정 날짜에만 통과하기 때문이다.

**기준선이 깨진 채로는 다음 티켓의 숫자가 의미를 잃는다.** "214 중 209"가 새 기준선인지
회귀인지 구분되지 않는다. T-11·T-09의 커밋이 이것에 막혀 있다.

세 번째다:
- **T-07 (07-31)** — "이번 달 마지막 날 활성" 1건. 7/31에 처음 깨졌다. 한 건만 고쳤다
- 그때 남긴 메모: *"날짜를 문자열로 조립하는 검사(`${D0.slice(0,8)}NN` 꼴)는 달·윤년에서
  조용히 깨진다. 훑어볼 항목으로 올린다"*
- **오늘 5건.** 예고된 대로다

## 실패 5건 (2026-08-03 기준)

```
오늘+14일 달 경계
말일 → 다음 달 1일
다음 달 그리드의 +14일
다음 달 그리드의 +15일
다음 달 그리드 앞머리 활성
```

**증상만 적었다. 원인은 재현해서 확인한다** — 다섯이 한 원인인지 둘 이상인지 모른다.

## 방향 — 오늘을 고정한다

문자열 조립을 `Date` 산술로 바꾸는 것은 **절반의 해법**이다. 그러면 오늘이 며칠이냐에 따라
여전히 다른 경로를 탄다.

**앱은 이미 서버가 준 날짜를 쓴다.** T-09 검토가 `S.today.date`를 `2001-01-15`로 바꿔
"기기 날짜를 쓰면 실패하는" 센티널을 만들었다 — **같은 주입 지점이 여기에도 쓰인다.**

```
날짜 검사는 고정 날짜를 주입하고 돈다.
오늘이 8월 3일이든 2월 29일이든 같은 결과가 나온다.
```

고정 날짜는 **경계를 밟는 값**을 고른다 — 말일, 달을 넘는 +14일, 31일 없는 달.
하나로 안 되면 검사마다 다른 고정 날짜를 쓴다. 그게 이 검사들이 원래 지키려던 것이다.

**주입이 불가능한 검사가 있으면 멈추고 보고한다.** 캘린더 렌더가 `new Date()`를 직접 부르는
자리가 있으면 그건 **앱의 결함**이고 프런트 수정이 필요하다 — 이 티켓의 범위 밖이다.

## 범위

```
test/front.mjs      날짜 검사만
```

**`public/` 를 건드리지 않는다.** 앱 코드에 손이 필요하면 멈춰서 보고한다 —
검사를 통과시키려고 앱을 고치는 것이 이 프로젝트에서 가장 위험한 방향이다.

## 금지

| 하지 말 것 | 왜 |
|---|---|
| 검사를 지우거나 `skip` | 숫자만 맞추는 것이다. 이 검사들이 지키던 달 경계가 사라진다 |
| 앱 코드 수정 | 검사를 통과시키려고 앱을 고치면 앱이 검사에 맞춰진다 |
| 문자열 조립을 유지한 채 값만 조정 | 다음 달에 또 깨진다. **오늘 고치는 이유가 그것이다** |
| 특정 날짜에만 통과하는 새 검사 추가 | 같은 함정을 다시 만든다 |
| 다른 검사 건드리기 | 날짜 검사만이다 |

## 완료 조건

```
typecheck 통과 · smoke 237(변화 없음) · front 214 · 실패 0
```

**검사 개수가 줄면 안 된다.** 지우고 통과시키는 것과 고쳐서 통과시키는 것을 구분하는 유일한 숫자다.

그리고 **날짜를 바꿔서 두 번 돌린다:**

1. 오늘 그대로 → 214 · 실패 0
2. 시스템 날짜를 **말일이 아닌 날**(예: 2월 15일)로 바꿔서 → **같은 214 · 실패 0**

2번이 이 티켓의 전부다. 한 번만 통과하는 것은 지금 상태와 다르지 않다.
시스템 날짜를 못 바꾸면 **고정 날짜 주입이 실제로 걸렸는지**를 다른 방법으로 보이고 보고에 적는다.
