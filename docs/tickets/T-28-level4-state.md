# T-28 — 기기가 Level 4 상태를 노출한다 · 프롬프트에서 거짓을 지운다

**발행** Cowork · 2026-08-10 · **담당** Claude Code (**위임 금지**) · **상태** ✅ 합격 (2026-08-10)

---

## 무엇이 어긋났나

모델에게 주는 프롬프트가 **없는 강제력을 말한다** (`src/services/guard.ts:467`):

```
"Level 3(화면 점유 + 알람)이 이미 발동한 상태에서,
 Level 4(신규 작업 차단까지)로 격상할 근거가 있는지만 판정한다."
```

**"신규 작업 차단"은 구현이 없다.** 격상돼도 대기가 60초에서 180초로 길어질 뿐이다.
모델은 존재하지 않는 대가를 저울에 올리고 판정해 왔고, 그렇게 쌓인 `guard_events`가
**§6.5가 읽을 전례**다. ADR-035가 이 자리를 정리했다.

그리고 화면이 그 규칙을 지키려면 **"지금 Level 4인가"를 물어볼 곳**이 있어야 하는데, 없다.

## 이 티켓이 하는 것 · 하지 않는 것

| | 무엇 | 어디 |
|---|---|---|
| **한다** | 격상 시각을 남기고 30분 창으로 판정해 웹에 답한다 | Kotlin |
| **한다** | 프롬프트에서 **거짓을 지운다** | `guard.ts` |
| **안 한다** | 화면이 그 답을 읽고 날짜를 트는 것 | T-29 |
| **안 한다** | 프롬프트에 **실제 강제력을 적는 것** | T-29 |

**거짓을 지우는 것과 사실을 적는 것을 나눈다.** 지금은 아직 강제력이 없으므로,
여기서 새 문구를 적으면 **거짓말을 다른 거짓말로 바꾸는 것**이다.
지우는 쪽은 오늘 배포할 수 있고, 매일 밤 전례가 오염되고 있으므로 미룰 이유가 없다.

## 할 일

### ① 격상을 기록한다 (Kotlin)

자리는 **`GuardNotifications.kt:250` 근처, `if (v?.upgrades == true)` 안**이다.

```kotlin
if (v?.upgrades == true) runCatching { GuardAlertActivity.upgradeToLevel4() }
```

**`upgradeToLevel4()`의 성공 여부와 무관하게 쓴다.** 그 함수는 살아 있는 화면이 없으면
조용히 지나가고(`live?.get() ?: return`), 마찰에 들어갔거나 끝나는 중이면 `applyUpgrade`가
되돌아간다. **화면의 수명을 기준으로 잡으면 차단이 영원히 안 걸린다** — ADR-035 ③이
기각한 바로 그 구조다. 기준은 **격상이 승인됐다**는 사실이다.

킬 스위치가 꺼져 있을 때(`guard_ai_verify=off` → 결정론으로 항상 격상)도 **같은 자리를 지난다.**
확인하고, 안 지나면 그 사실을 보고한다.

### ② 판정해서 답한다 (Kotlin)

`GuardPlugin`에 `@PluginMethod`를 하나 더 낸다. `state()` 옆이다.

```
{ "level4": true|false, "until": <epoch ms 또는 없음> }
```

**판정은 기기가 한다** — 웹에 시각을 주고 계산시키지 않는다(ADR-035 ②).
`until`은 **표시용**이다. 왜 내일이 됐는지 말해야 하기 때문이다(ADR-035 ⑤).

- 저장은 **기존 `"guard"` SharedPreferences**를 쓴다. 새 파일을 만들지 않는다
- 쓰는 곳과 읽는 곳이 **같은 상수**를 본다. 키 문자열을 두 벌로 두지 않는다
- 창은 **30분**이다. `guard.ts:389`가 *"Level 4는 30분마다 재발동한다"*고 적은 그 주기라
  **다음 발동이 이어받아** 구간이 끊기지 않고, 발동이 멎으면 자연히 닫힌다

> **`GuardWatch.REFIRE_MS`를 재사용하지 않는다.** 값이 같지만 뜻이 다르다 —
> 그쪽은 **감지(경로 B)의 재발동 간격**이고 여기는 **Level 4(경로 A)의 발동 주기**다.
> 우연히 같은 값을 한 상수로 묶으면 **한쪽을 조정할 때 다른 쪽이 끌려간다.**
> 이름이 뜻을 말하는 새 상수를 둔다.

### ③ 프롬프트에서 거짓을 지운다 (서버)

`VERIFY_SYSTEM`의 `"Level 4(신규 작업 차단까지)"`에서 **괄호를 걷어낸다.**
아직 없는 것을 새로 적지 않는다 — T-29가 사실이 생긴 뒤에 적는다.

### 격상 자리가 하나였나 (킬 스위치 경로 포함)

**하나였다. 킬 스위치도 같은 자리를 지난다 — 코드로 확인했다.**

기기가 `verify`를 부르는 자리는 `GuardNotifications.fire`의 `if (candidate4 && clientId != null)`
블록 하나뿐이고, 판정은 전부 `GuardVerify.Verdict.upgrades`로 수렴한다:

```kotlin
GuardVerify.kt:57   val upgrades: Boolean get() = approved && level >= 4
```

킬 스위치가 `off`면 서버가 이렇게 답한다 — `services/guard.ts`:

```ts
return { level: 4, approved: true, reason: "AI 검증이 꺼져 있어요 — 결정론으로 격상해요",
         ai_used: 0, cached: false, source: "off" };
```

`level=4 · approved=true` → **`upgrades`가 참**이다. 그래서 결정론 복귀 경로도 기록된다.
`source`는 `"off"`라 `aiVerdict`가 `null`이 되지만(AI 판정이 아니므로 비운다) **격상 사실과는
무관**하고, 이 티켓이 남기는 것은 격상 사실이다.

`note()`를 `upgradeToLevel4()` **앞**에 뒀다. 뒤에 두면 화면 격상이 던질 때 기록이 건너뛴다 —
`runCatching`이 감싸고 있어 실제로는 안 새지만, 같은 파일의 "① 로컬 기록이 **가장 먼저**"와
순서를 맞춰 두는 편이 다음에 읽는 사람에게 맞다.

### 30분 창을 어디에 두었나 · REFIRE_MS와 어떻게 갈랐다

**새 파일 `GuardLevel4.kt` 하나가 상수·키·쓰기·읽기를 전부 갖는다.**
`GuardNotifications`가 쓰고 `GuardPlugin`이 읽는데, 둘 중 하나가 소유하면 다른 하나가
남의 내부를 알게 된다. `GuardWatch`·`GuardRecheck`·`GuardSync`가 각자 prefs 키를 갖는
그 모양 그대로다.

- **prefs 파일은 기존 `"guard"`** — 새 파일 안 만들었다
- **키는 `K_AT = "level4_at"` 하나**, 쓰는 곳·읽는 곳이 같은 상수를 본다. 문자열 사본 없음
- `activeUntil()`이 **판정까지 끝내고** 끝 시각만 돌려준다 — 웹에 시각을 주고 계산시키면
  창의 길이가 두 곳에 생기고, 두 곳에 있는 같은 사실은 갈라진다(ADR-035 ②)

**`GuardWatch.REFIRE_MS`와 갈랐다 — 값이 같고 뜻이 다르다.**
`GuardLevel4.WINDOW_MS`를 따로 뒀고, 주석에 왜 묶으면 안 되는지 적었다:
그쪽은 **감지(경로 B)의 재발동 간격**, 이쪽은 **Level 4(경로 A)의 발동 주기**다.
한 상수로 묶으면 한쪽을 조정할 때 다른 쪽이 말없이 끌려간다.

### 설계와 어긋난 점

없다. 격상 판정·발동 순서는 한 줄도 안 건드렸다(ADR-024 fail-closed 그대로) — **기록만 얹었다.**
프런트·서버 라우트·마이그레이션 무변경.

**다만 착수 중에 한 자리를 조정했다.** 프롬프트를 왜 이렇게 뒀는지 설명하는 주석에는
"막는다"는 말이 들어가는데, 그 주석을 `VERIFY_SYSTEM` **배열 안**에 넣으면 검사가 그것을
프롬프트로 읽는다. 배열 **밖**(선언 위)으로 뺐다 — 스캐너가 주석을 걷어내게 만드는 대신
**볼 범위를 좁혔다.** T-23이 주석 제거 정규식으로 18줄을 먹은 것과 같은 종류를 피한 것이다.

### 막힌 것

**Kotlin에 검사가 없다 — 감추지 않는다.** 이 층에 Kotlin 러너가 없고 이 티켓이 만들 자리도
아니다. 그래서 ①②의 근거는 **코드 읽기와 빌드 통과**까지이고, *실제로 격상 때 기록이
남는지*는 **밤 실측이 유일한 검사**다(`docs/FIELD-TEST-NIGHT.md` · W5 8/26 게이트).
그 밤에 Doze 통과와 Level 4 기록이 **같이** 확인된다 — 격상 없이는 둘 다 못 잰다.

서버 쪽 검사 셋은 자동으로 잡히고 변이로 확인했다:

| 변이 | 결과 |
|---|---|
| 옛 프롬프트로 되돌림 | **281/1** — 검사 1만 |
| 스캐너 정규식 죽이기 | **280/2** — 양성 대조 둘. **검사 1은 그대로 초록이었다**(`vs=""`이라 '차단 없음') |

두 번째가 §5가 말한 그 자리다 — 양성 대조가 없었으면 **스캐너가 죽은 채로 T-28이 통과한다.**

### ADR을 고친 것은 구현 쪽이다

**ADR-035 ③이 "마지막 발동 + 30분"이었는데 구현은 "마지막 격상 승인 + 30분"이다.**
검토에서 **구현이 맞고 ADR이 틀린 것**으로 판정했고, ADR을 고쳤다.

승인은 검증 왕복만큼 발동보다 **뒤**다. 그래서 창이 다음 발동을 **몇 초 넘겨서** 닫힌다 —
**겹치는 쪽으로 어긋난다.** 발동 시각으로 재면 반대로 **다음 발동 직전에 잠깐 열리는 틈**이
생기고, 그 틈은 새벽에 딱 한 번 열려서 재현되지 않는다.
그리고 승인이 아예 없으면(오프라인·거부) Level 4가 아니므로 잴 것도 없다.

기록 자리가 `upgrades == true` 안이었던 것이 이 성질을 자동으로 준 셈이다 —
ADR 문구를 그대로 따랐다면 `fire()` 초입에서 재야 했고 그쪽이 틀린 자리였다.

### 이 티켓이 남긴 것

- **거짓말 하나가 사라졌다.** 모델이 없는 대가를 저울에 올려 판정하던 것을 멈췄고,
  그 판정으로 오염되던 §6.5의 전례가 오늘 밤부터 깨끗해진다(배포 후)
- **T-29가 물어볼 곳이 생겼다.** `Guard.level4State()` — pull이라 Level 4 중에 앱을
  **새로 여는** 경우도 답한다. 이벤트였으면 그 경우를 놓친다
- **검사가 없는 자리를 이름으로 남겼다.** Kotlin 러너가 없다는 사실을 통과 숫자로 덮지 않고
  "실검사는 밤 실측"이라고 적었다 — 그 밤이 W5 게이트와 같은 밤이다

### 남은 것 (T-28 밖)

⚠️ **서버 배포 대기.** 프롬프트 문구만 바뀌었고 동작은 무변경이다 — 바뀌면 그게 회귀다.
⚠️ **APK 설치 안 함.** T-29 뒤에 한 번(`adb install -r`). 그 전까지 기기의 `level4State`는 옛 APK에 없다.
⚠️ **밤 실측이 T-28의 실검사다.** Doze 통과와 Level 4 기록이 같은 밤에 확인된다 —
   격상 없이는 둘 다 못 잰다. `docs/FIELD-TEST-NIGHT.md` · W5(8/26) 게이트.
