# T-51 — 밤 개입이 더 일찍, 더 자주

**발행** Cowork · 2026-08-28 · **담당** Claude Code · **작음**
**근거** 사용자 실사용 요청 · §6.3 · **APK 필요 · 서버 무변경 · 마이그레이션 없음**

---

## 무엇을 바꾸나

```
첫 발동    연속 사용 20분  →  15분      GuardSettings.watchMinutes (설정값)
재발동     30분마다        →  15분마다   GuardWatch.REFIRE_MS      (코드 상수)
```

**앞은 이미 설정이고 뒤는 상수다 — 같은 성격의 값이 두 곳에 나뉘어 있다.**

## 할 일

### ① 재발동 간격을 설정으로 옮긴다

`REFIRE_MS`를 `GuardSettings`로 내리고 **기본값 15분**. `setWatch`에 인자를 하나 더.

```kotlin
var watchRefireMinutes: Int   // 기본 15 · coerceIn 은 이웃 값들과 같은 모양으로
```

⚠️ **`watchMinutes`가 이미 거기 있다.** 같은 규칙의 두 임계가 한 곳에 있어야
다음 조정에 APK가 안 든다 — **9~11월 실사용에서 가장 먼저 만질 값이 이 둘이다.**

⚠️ **`GuardRecheck.RECHECK_MS`(5분)는 건드리지 않는다.** 그것은 *"[알겠습니다] 뒤 재확인"*이라
성격이 다르고, 사용자가 말한 것이 아니다.

### ② `watchMinutes` 기본값도 15로

새 기기·초기화에서 20이 나오면 두 값이 어긋난다.

⚠️ **이미 깔린 기기의 SharedPreferences 에는 20이 남아 있다.** 기본값을 바꿔도 안 따라온다 —
**§확인 절차가 `setWatch` 를 한 번 불러 덮는다.**

### ③ ★ 밤 상한이 초반에 소진된다 — 이 티켓의 진짜 문제

`watchMaxPerNight = 5`가 그대로면 간격이 절반이 되면서 **상한도 두 배 빨리 닳는다.**

```
지금    20분 + 30분 간격  →  첫 발동 뒤 2시간이면 5회 소진
뒤      15분 + 15분 간격  →  첫 발동 뒤 1시간이면 5회 소진
```

**취침 창이 `00:30~06:00`(5.5시간)인데 01:30에 상한이 끝나면 새벽 4시엔 개입이 없다.**
⚠️ **가장 필요한 시간대가 비는 모양이고, 그것은 "더 자주 개입해 달라"의 반대다.**

**담당이 정한다 — 그리고 근거를 보고에 적는다:**

```
(a) watchMaxPerNight 기본을 올린다            몇으로 · 왜
(b) 상한을 시간당으로 바꾼다                   구조 변경 · 이 티켓엔 크다
(c) 그대로 두고 실사용에서 본다                ← 무엇을 보면 아는지 적어야 한다
```

⚠️ **§6.3이 말하는 실패는 "잔소리로 도구를 떠나는 것"이다.** 상한은 그 방벽이고,
**올리는 쪽도 그냥 안전하지 않다.**

## 범위

```
android/.../guard/GuardSettings.kt   watchRefireMinutes 추가 · watchMinutes 기본값
android/.../guard/GuardWatch.kt      REFIRE_MS → 설정 읽기
android/.../guard/GuardPlugin.kt     setWatch 에 인자 하나 · watchStatus 에 노출
test/front.mjs                       검사 (스캐너)
```

**서버 무변경 · 마이그레이션 없음 · 프런트 화면 무변경.**

⚠️ **`guard/` 아래를 고치는 티켓이다** — 위임 금지 영역(AGENT-CHAIN §4). **Codex 위임 불가, 직접.**

## 금지

| 하지 말 것 | 왜 |
|---|---|
| 15를 코드에 상수로 박기 | **설정값이다.** 그래서 옮기는 것이다 |
| `RECHECK_MS`(5분) 손대기 | 다른 규칙이다. 요청에 없다 |
| `watchMaxPerNight` 를 말없이 바꾸기 | ③의 판단이다. **바꾸든 안 바꾸든 근거를 적는다** |
| 취침 창(`00:30~06:00`) 손대기 | 요청에 없다 |
| 설정 화면(UI) 만들기 | 이 티켓의 범위 밖. 필요하면 별도 |
| 상시 알림·`GuardService` 손대기 | **별개 판단이고 지금 실측 중이다**(채널 끄기) |

## 완료 조건

```
assembleRelease BUILD SUCCESSFUL · npx cap sync android 성공
```

**검사**

```
1  setWatch 가 refire 간격을 받아 저장하고 watchStatus 가 돌려준다
2  ★ 재발동 간격이 코드 상수가 아니라 설정에서 온다 (스캐너 — GuardWatch 에 리터럴 분(分)이 없다)
3  ★ 2의 스캐너가 살아 있는가
4  기본값이 둘 다 15다
5  ★ 범위 밖 값(0 · 음수 · 거대값)이 coerce 된다   ← 이웃 설정들과 같은 모양인가
```

⚠️ **Kotlin 쪽은 jsdom 이 못 본다.** 2·3은 스캐너이고 **진짜 판정은 실측이다.**

**변이**
- 간격을 다시 상수로 박는다 → **2만** 죽는다
- 스캐너를 눈멀게 한다 → **2는 초록 · 3만** 죽는다
- 기본값 하나만 15로 한다 → **4만** 죽는다
- `coerceIn` 을 뺀다 → **5만** 죽는다

## 확인 절차 (사용자) — APK 설치 후

**이미 깔린 기기에는 옛 값(20)이 남아 있다.** 폰 WebView 콘솔에서 한 번 덮는다:

```js
await Capacitor.Plugins.Guard.setWatch({ minutes: 15, refireMinutes: 15 })
await Capacitor.Plugins.Guard.watchStatus()   // 둘 다 15인지 눈으로
```

```
□ watchStatus 가 15 · 15 를 돌려준다
□ ★ 오늘 밤 — 15분 만에 첫 알림이 오는가
□ ★ 그 뒤 15분 간격인가
□ ★ 새벽 늦게까지 개입이 남아 있는가, 아니면 초반에 상한이 끝나는가   ← ③의 실측
```

**마지막 줄이 이 티켓의 진짜 판정이다.** 초반에 다 써버리면 ③의 (a)나 (b)로 다시 온다.

⚠️ **그리고 이번 밤은 상시 알림 채널을 끈 상태로 잔다** — 두 변경이 같은 밤에 겹치므로,
**Guard 가 아예 안 뜨면 원인이 둘이다.** 그때는 채널을 먼저 되살려 가른다.
