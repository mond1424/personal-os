# T-23 — 요청당 `loadTime`은 한 번이다

**발행** Cowork · 2026-08-06 · **담당** Claude Code (**위임 금지**) · **상태** ⬜ 대기

---

## 무엇이 어긋났나

미들웨어가 요청마다 시간 맥락을 만든다:

```ts
c.set("t", await loadTime(...))          // src/index.ts:37
```

그런데 모드 라우트가 그것을 안 넘긴다:

```ts
app.get("/api/guard/modes", async (c) => c.json(await guard.modes(c.env)))
                                                             ↑ t 가 없다
```

그래서 `modes()`가 **스스로 다시 만든다** — `loadTime(env)`(guard.ts:37).

`TimeCtx` 주석이 못 박은 자리다:

> 귀속일은 여기서 한 번만 계산한다 (1.2)

## 증상이 없는데 왜 고치나

지금은 밀리초 차이라 두 값이 같다. **05:00 경계를 넘는 순간에만 갈라진다** —
미들웨어가 8/5로 읽고 `modes()`가 8/6으로 읽는 창이 있다.

드물다. 그러나 **원칙이 지키려던 것이 정확히 그 창이다.**
그리고 이 종류의 어긋남은 **아무 오류도 내지 않는다** — T-07의 UTC 귀속일이 그랬다.

## 이 결함이 어떻게 들어왔나

T-19가 `modes()`에 `protecting`을 얹으라고 했는데, **티켓이 `t`를 어디서 받을지 안 정했다.**
`protectingNow(env, t)`가 `t`를 요구하니 `modes()`가 스스로 만들었다.

그리고 **Codex 검토가 `protectingNow(env, loadTime(env))`를 §검토에 적어놓고도 짚지 않았다** —
같은 층이 자기 것을 봤기 때문이다. 체인 복원 뒤 Claude Code가 즉시 잡았다.

**발행자의 누락이다.** 티켓이 인자를 정하지 않으면 아래층이 만들어 낸다.

## 위임 금지인 이유

귀속일 계산이다. `CLAUDE.md`가 **트리거·마이그레이션·귀속일·Guard 발동 경로**를 위임 금지로 두었고
여기가 세 번째다.

## 할 일

**같은 구멍을 전수로 찾는다.** `guard.modes` 하나가 아닐 수 있다.

```
① src/index.ts 의 라우트를 전부 훑는다
     c.get("t") 를 안 넘기는데 서비스가 loadTime 을 부르는 자리
② 각각이 실제로 갈라질 수 있는가 — 귀속일·하루 경계를 쓰는가
     시간을 안 쓰는 서비스가 loadTime 을 부를 리는 없지만 확인한다
③ 라우트가 넘기도록 고친다. 서비스는 t 를 받는다
```

**서비스 안에서 `loadTime`을 부르는 것을 남기지 않는다** — 남으면 다음에 또 같은 자리가 된다.

## 범위

```
src/index.ts             라우트가 c.get("t") 를 넘긴다
src/services/guard.ts    modes(env, t)  · 그 밖에 찾은 것
test/smoke.ts            검사
```

**마이그레이션 없다. 프런트를 건드리지 않는다.**

## 금지

| 하지 말 것 | 왜 |
|---|---|
| 서비스에 `loadTime` 호출을 남기기 | 다음에 또 같은 자리가 된다. 요청당 한 번이다 |
| `loadTime`을 캐시해서 덮기 | 두 벌인 것은 그대로다. **부르는 자리를 없앤다** |
| `modes()`만 고치고 전수를 안 보기 | 같은 구멍이 더 있을 수 있다 |
| `TimeCtx` 구조 변경 | 주석이 정한 계약이다. 전달만 고친다 |
| 프런트 수정 | 응답 형태는 안 바뀐다 |

## 읽을 것

- `src/index.ts` 37 — 미들웨어가 `t`를 만드는 자리
- `src/lib/time.ts` `TimeCtx` 주석 — "한 번만 계산한다(1.2)"
- `src/services/guard.ts` 34~45 — `modes`·`setMode`. `setMode`는 이미 `t`를 받는다
- `docs/tickets/T-19-mode-verdict.md` §검토 — 이 결함이 통과한 경로

## 완료 조건

```
typecheck 통과 · smoke 268 → 270 이상 · front 249(변화 없음) · 실패 0
```

검사:

1. `GET /api/guard/modes` 응답이 그대로다 (`downgrade`·`protecting`)
2. **서비스 계층에 `loadTime` 호출이 남아 있지 않다**

**2번이 이 티켓의 전부다.** 응답이 같으니 1번만으로는 아무것도 확인되지 않는다 —
`loadTime`을 서비스가 부르든 라우트가 넘기든 **응답은 똑같다.**

검사 방법은 담당이 정한다. 다만 **"고쳤다"가 아니라 "부르는 자리가 0이다"를 보여야 한다.**

## 보고 (담당이 채운다)

```
티켓: T-23
바꾼 파일: src/index.ts · src/scheduled.ts · src/services/guard.ts · test/smoke.ts
기준선: typecheck 통과 · smoke 268 → 272 · front 249 → 249(무변경) · 실패 0 · verify exit 0
```

**전수 결과 — 구멍은 두 곳이었다.**

라우트 67개를 전부 훑었다. `c.get("t")`를 넘기던 것이 39개, 안 넘기던 것이 30개.
그 30개 중 **호출한 쪽이 시계를 다시 읽는 것이 둘**이다:

| 라우트 | 부르던 자리 | 갈라질 수 있나 |
|---|---|---|
| `GET /api/guard/modes` | `services/guard.ts:37` `modes()` | **그렇다** — `protectingNow(env, t)`가 `t.now`로 보호 구간을 판정하고 `normalizeIso`가 `t.offsetMin`을 쓴다 |
| `POST /api/admin/auto-close` | `scheduled.ts:10` `autoClose()` | **그렇다** — `t.d`로 '지난 날'을 고르고 `t.now`를 `daily`·`mech`에 **쓴다**(귀속일이 저장된다) |

나머지 28개는 시계를 아예 안 읽는다. `loadTime` 0건은 물론이고
`Date.now()`·인자 없는 `new Date()`·SQL의 `datetime('now')`도 없다(`src/` 전체 확인).
시간을 쓰는 서비스는 전부 이미 `t`를 인자로 받는다.

**고친 방향은 "부르는 자리를 없앤다"다** — 캐시를 얹지 않았다.
`modes(env, t)`·`autoClose(env, t)`로 인자를 받고, `loadTime`을 부르는 곳은
**진입 계층 둘만 남았다**: `index.ts`의 미들웨어(HTTP)와 `scheduled()`(cron).
cron에는 요청이 없으므로 그 경계가 `loadTime`의 정당한 자리다 —
`autoClose`는 이제 도메인 함수일 뿐이고, 두 진입로 어느 쪽으로 들어와도 시계는 한 번 읽힌다.

**검사 2를 어떻게 짰나 — 소스 호출부를 직접 센다(smoke `[11]`, 3건).**

응답으로는 아무것도 안 보이므로 응답을 보지 않는다. `src/**/*.ts`를 훑어
`loadTime(` **호출 줄**을 센다(선언·주석 줄 제외). 셋을 한 벌로 둔다:

```
① services/ 아래 호출 0                      ← 티켓의 검사 2
② 호출은 진입 계층 둘뿐 (index.ts 1 · scheduled.ts 1)   ← 양성 대조
③ 훑은 범위가 src 전체 (파일 수 · services/ 포함 · lib/time.ts 포함)
```

**②가 없으면 ①은 정규식이 죽어도 초록이다.** 실제로 그 사고가 났다 —
처음엔 파일 전체에서 `/* … */`를 걷어냈는데 `app.use("/api/*")`의 `/*`가 열려
`.replace(/^D1_ERROR:\s*/…)`의 `*/`까지 18줄을 먹고 **index.ts의 진짜 호출을 지웠다.**
①은 그대로 초록이었고 ②만 빨간불이 됐다. 판정을 줄 단위로 바꿔 고쳤다.
②는 `lib/`·`db/`로 옮겨 부르는 우회도 함께 막는다.

**넷째 검사는 런타임이다** — 정적 검사는 "loadTime을 안 부른다"까지만 본다.
`loadTime`을 지우고 다른 방법으로 시계를 읽어도 통과하므로, **판정이 넘겨받은 `t`를
실제로 따르는지**를 (3b) 블록에서 본다: 보호 구간이 살아 있는 상태에서
일정 시각 1분 뒤를 가리키는 `t`를 주입하면 `protecting`은 `null`이어야 한다.

**변이로 확인했다.** `modes()` 안에서 `t = await loadTime(env)`로 되돌리니
**272 → 269/3**, 정확히 이 셋만 빨간불이다(①②와 런타임 검사). 다른 검사는 전부 그대로 초록 —
"응답이 같아서 아무 검사도 안 걸린다"던 티켓의 진단이 그대로 재현됐다.

**설계와 어긋난 점 (범위 밖 — 손대지 않았다).**

`services/guard.ts:143` `schedule()`이 `t`를 받아 놓고 `const nowMs = Date.now()`로
**시계를 한 번 더 읽는다.** 같은 계열이지만 성격이 다르다 — 귀속일도 하루 경계도 아니고
"이미 지난 발동을 `fires`에서 뺀다"는 필터라 어긋남이 요청 소요 시간(밀리초)뿐이다.
`Date.parse(t.now)`로 바꾸는 한 줄이면 되지만 **Guard 발동 경로의 동작을 티켓 밖에서
건드리는 것**이라 보고만 한다. 같은 파일 `protectingNow`는 이미 `Date.parse(t.now)`를 쓴다.

**막힌 것: 없다.** 마이그레이션·프런트 무변경, 응답 형태 무변경(front 249 그대로).
`STATE.md` §기준선 갱신과 커밋은 지시대로 하지 않았다 — 닫을 때 함께.
