# T-56 — 뒤에 또 깨어 있었으면 묻지 않아도 안다

**발행** Cowork · 2026-09-03 · **담당** Claude Code · **작음**
**근거** [ADR-044](../../APP-ADR.md#adr-044) · **마이그레이션 없음 · APK 무관**

---

## 무엇을 만드나

Today 상단의 **잘 했어요 / 못 했어요**가 대부분 답 없이 남는다 — 묻는 때가 다음 날 낮이고,
그때는 그 밤이 이미 멀다.

**답이 없어도 알 수 있는 밤이 있다.**

```
개입 뒤에 같은 밤의 발동이 또 있었다   →  그 사이에 자지 않았다
```

`GuardWatch`는 `continuousScreenOnMin`으로 발동한다 — **화면이 켜져 있어야 뜬다.**
다음 발동의 존재는 추측이 아니라 **관측된 사실**이다.
여섯 밤 관측에서 L3에는 매번 재발동이 뒤따랐으므로, **대부분의 밤이 답 없이 채워진다.**

## ★ 저장하지 않는다 — 이 티켓의 전부가 여기에 걸린다

⚠️ **`outcome`에 자동으로 `failure`를 쓰면 안 된다.**

```sql
outcome  TEXT CHECK (outcome IN ('success','failure'))
trg_guard_event_immutable:
  OR (OLD.outcome IS NOT NULL AND IFNULL(NEW.outcome,'') != OLD.outcome)
```

**append-only다.** 시스템이 먼저 박으면 사용자가 나중에 *"그건 잤다가 깬 거였다"* 라고
**고칠 길이 DB 층에서 막힌다.** 그리고 §6.5가 전례를 읽을 때
*"사용자가 그렇게 말했다"* 와 *"시스템이 그렇게 추론했다"* 가 **한 칸에 섞인다.**

**컬럼도 더하지 않는다.** *"뒤에 발동이 또 있었나"* 는 `guard_events`를 보면 **언제든 나온다** —
**아키텍처 원칙 1: 파생값은 저장하지 않는다.** 저장하면 닫힌 `CHECK`와 트리거를 상대해야 하고
얻는 것이 없다.

## 할 일

### ① 조회할 때 계산한다

그 발동보다 **뒤**이고 **같은 귀속일(`on_date`)**인 `guard_events`가 있으면 `inferred`다.
**레벨은 가리지 않는다** — L2도 화면이 켜져 있어야 뜨므로 증거로는 같다(ADR-044 ③).

⚠️ **귀속일 경계에 시각을 적지 마라.** `on_date`가 이미 그 판정을 담고 있다.

### ② 화면이 셋을 갈라 말한다

```
답이 있다                    그 답을 보인다 — 물음이 사라진다
답 없고 · 뒤에 발동 있다      "못 한 것으로 보여요"   ★ 버튼은 남는다
답 없고 · 뒤에 발동 없다      묻는다 (지금 모양)
```

⚠️ **둘째 줄에서 버튼을 없애지 마라.** 자동 판정은 **사용자의 답을 대체하지 않고 자리를 대신
채운다** — `outcome`이 비어 있으므로 트리거가 안 막고, **사용자가 누르면 그 답이 이긴다.**

⚠️ **문구를 단정하지 마라.** *"못 했어요"*가 아니라 *"못 한 것으로 보여요"* 다 —
관측의 강도가 다르고, 그 차이가 사용자에게 **고칠 수 있다는 신호**가 된다.

## 범위

```
src/db/index.ts     뒤따른 발동 여부 (조회에 얹는다)
src/services/       또는 여기 — 도메인 판단이므로
public/app.js       셋을 가르는 표시
test/smoke.ts · test/front.mjs
```

**마이그레이션 없음 · APK 무관 · `guard/` 무변경.**

⚠️ **`services/guard.ts`의 발동 경로를 건드리지 않는다** — 이 티켓은 **읽는 쪽**이다.
**위임 금지 영역이 아니다**(발동 경로가 아니라 조회다). **Antigravity 위임 가능.**

## 금지

| 하지 말 것 | 왜 |
|---|---|
| `outcome`에 자동 기입 | **사용자가 못 고친다**(append-only). ADR-044 ★ |
| 새 컬럼·마이그레이션 | **파생값은 저장하지 않는다**(원칙 1) |
| 추론된 것에서 버튼 제거 | 관측이 사람의 답을 이기는 구조가 된다 |
| *"못 했어요"* 로 단정 | 관측의 강도가 다르다. 고칠 수 있다는 신호를 지운다 |
| 레벨로 거르기 | L2도 화면이 켜져야 뜬다(ADR-044 ③) |
| 귀속일 경계에 시각 적기 | 설정값이다. `on_date`가 이미 담고 있다 |

## 완료 조건

```
typecheck 통과 · smoke 385 → 389 이상 · front 385 → 387 이상 · 실패 0 · verify exit 0
```

**검사**

```
1  뒤에 발동이 있으면 추론이 붙는다
2  ★ 뒤에 발동이 없으면 안 붙는다                     ← 1의 짝
3  ★ 사용자 답이 있으면 추론이 그것을 덮지 않는다      ← 이 티켓의 핵심
4  ★ 추론이 붙어도 outcome 은 여전히 NULL 이다         ← 없는 것을 세는 검사
5  ★ 추론이 붙은 뒤에도 사용자가 답을 쓸 수 있다       ← 4의 실물. 트리거가 안 막는가
6  다른 귀속일의 발동은 세지 않는다
7  L2 가 뒤따라도 추론이 붙는다
```

**4와 5가 이 티켓의 회귀 검사다.** 4만 보면 *"계산은 맞는데 아무 데도 안 쓰이는 구현"*이 통과하고,
5만 보면 *"쓰기는 되는데 추론이 안 도는 구현"*이 통과한다.

⚠️ **5는 실제로 `POST`(또는 그 경로)를 태워라.** 트리거가 막는지는 **API를 거쳐야 알 수 있고**,
막는다면 이 설계가 틀린 것이므로 **멈추고 보고한다.**

⚠️ **검사 신호에 토스트나 `until`을 쓰지 마라**(함정 14).

**변이**
- 뒤따른 발동 조회를 뺀다 → **1만** 죽는다
- 항상 추론을 붙인다 → **2만** 죽는다
- 추론이 사용자 답을 덮는다 → **3만** 죽는다
- 추론을 `outcome`에 쓴다 → **4·5** 죽는다
- 귀속일 조건을 뺀다 → **6만** 죽는다
- `level >= 3` 으로 거른다 → **7만** 죽는다

## 보고 (담당이 채운다)

```
티켓: T-56
바꾼 파일:
  src/db/index.ts          guardEventsPendingOutcome 에 later_fires 상관 서브쿼리
  src/services/guard.ts    outcomeInferred() · pendingOutcome 이 outcome_inferred 를 얹는다
  public/app.js            guardAskLine() 신설 · set(state, inferred)
  test/smoke.ts            검사 7 + fixture 확인 2
  test/front.mjs           검사 4
기준선: typecheck 통과 · smoke 385 → 394 · front 394 → 398 · 실패 0 · verify exit 0
```

⚠️ **티켓의 완료 조건이 `front 385 → 387`인데 385는 T-55 전 숫자다.** 착수 시점 기준선은
**394**였고(T-55가 385 → 394), 여기서 398이 됐다. `STATE.md` §기준선이 그 원장이다.

**① 계산을 어디에 뒀나 — 둘 다다. 자르는 선이 다르다**

```
db/index.ts        later_fires  = 같은 on_date · 더 뒤인 fired_at 의 수      ← 사실(SQL)
services/guard.ts  outcome_inferred = later_fires > 0 ? "failure" : null   ← 뜻(도메인)
```

근거는 이 리포의 규칙 그대로다 — **SQL은 `db/index.ts`에만, 도메인 규칙은 `services/`.**
*"몇 건이 뒤따랐나"* 는 조회이고 *"그래서 못 잔 것으로 본다"* 는 판단이다. 갈라 두면
**나중에 판단만 바꿀 때 SQL을 안 건드린다** — T-53이 *"네이티브는 사실만, 문구는 웹이"* 로
세운 선과 같은 모양이고, 바로 앞 T-55에서도 같은 선을 그었다.

★ **`later_fires`를 응답에 그대로 싣는다.** 이것이 T-55 §③의 `total`·`hidden`과 같은 자리다 —
다음에 추론이 안 붙으면 `later_fires 0`(뒤에 아무것도 없었다)과 `later_fires 3`인데 추론이
안 붙음(우리 판단이 틀렸다)이 **그 숫자 하나로 갈린다.** 검사 6이 이 숫자를 직접 센다.

**③ 사용자 답과 추론이 화면에서 어떻게 갈리나**

```
답이 있다                    여기 오지도 않는다 — `outcome IS NULL` 필터가 이미 걸렀다
답 없고 · 뒤에 발동 있다      "… 뒤에 또 깨어 있어서 못 한 것으로 보여요 — 아니면 눌러서 고쳐 주세요."
답 없고 · 뒤에 발동 없다      "… 결과가 어땠나요?"  (지금 모양 그대로)
```

**자리**: 문구는 `#td-guard-text` 그대로이고, 추론 여부는 **`data-inferred`라는 다른 칸**이다.
⚠️ **`data-state`를 안 늘렸다** — `ask`가 곧 *"버튼이 뜬다"* 라서 다섯째 상태를 만들면
**버튼이 사라지는 길이 생긴다.** T-54가 결과를 상태에서 떼어낸 자리와 같다. 그리고
`set()`이 `inferred`도 매번 새로 정한다 — 안 지우면 다음 줄에 **남의 판정이 붙는다**(검사 4).

**검사 5가 실제로 API 를 태우는가 · 트리거가 막지 않는 것을 확인했는가**

**태운다. 그리고 막지 않는다.**

```
POST /api/guard/events/{추론이 붙은 행}/outcome  { outcome: "success" }
→ 200 · { outcome: "success" }
```

⚠️ **일부러 추론과 반대되는 답을 넣는다.** `failure`로 넣으면 *"어차피 같은 값"* 이라
선점 여부가 안 드러난다. `outcome`이 비어 있으므로 `trg_guard_event_immutable`은 볼 것이
없고, 그 뒤 검사 3이 **저장된 값이 `success`(사람의 것)** 이고 그 줄이 **물음에서 사라졌음**을
확인한다. **ADR-044 ②가 예측한 대로다 — 이 설계는 틀리지 않았다.**

### 변이 아홉 — 여섯 중 넷이 표대로, 둘이 다르게 나왔다

| 변이 | 죽은 것 | 표의 예측 |
|---|---|---|
| M1 뒤따른 발동 조회를 뺀다 | smoke **1 · 4** | 1만 |
| M2 항상 추론을 붙인다 | smoke **2**만 | 2만 ✓ |
| M3 답한 줄도 물음에 끌어온다 | smoke **3**만 | 3만 ✓ |
| M4 추론을 `outcome`에 쓴다 | smoke **1·3·4·5·7** | 4·5 |
| M5 귀속일 조건을 뺀다 | smoke **6**만 | 6만 ✓ |
| M6 `level >= 3`으로 거른다 | smoke **7**만 | 7만 ✓ |
| M7 추론이 붙으면 줄을 감춘다 | front **1**만 | (표에 없음) |
| M8 `set()`의 초기화를 뺀다 | front **2 · 4** | (표에 없음) |
| M9 문구를 단정한다 | front **1**만 | (표에 없음) |

⚠️ **검사 셋을 일부러 좁혔다 — 겹치면 서로의 몫을 못 센다.** 처음에 넓게 썼다가 예측 실행에서
드러났다: 7에 `=== "failure"`를 두면 M1이 1과 함께 죽여 **레벨을 겨냥한 검사가 자기 몫을 못 세고**,
6에 `outcome_inferred === null`을 두면 M2가 2와 함께 죽인다. 4의 *"pending 전체가 NULL"* 은
M3가 답 있는 옛 행을 끌고 들어와 3을 겨냥한 변이가 4까지 죽였다. **셋 다 좁히고 나서야
M2·M3·M5·M6이 하나씩만 죽였다.**

★ **M1이 4를 함께 죽이는 것은 남겼고, 그게 맞다.** 4의 전제가 *"추론이 붙어도"* 이므로
추론이 없으면 할 말이 없다 — 전제를 빼면 **T-56 기능이 아예 없는 코드에서도 4가 초록이 된다.**

★ **M4가 다섯을 죽였고 그것이 이 티켓의 논거를 실측으로 증명한다.** 추론을 `outcome`에 쓰자
검사 5가 **ADR-044가 적은 바로 그 문장**으로 죽었다:

```
✗ 5 ★ 추론이 붙은 뒤에도 사용자가 답을 쓸 수 있다 — 409 {"error":"이미 결과가 확정됐어요"}
```

표에 적힌 근거가 아니라 **실제 API가 낸 409**다. 나머지 넷이 줄줄이 따라 죽은 것은,
자동 기입이 **한 칸이 아니라 루프 전체**를 무너뜨린다는 뜻이다(답한 행이 물음에서 빠지므로
그 뒤 검사들의 fixture 자체가 사라진다).

M8이 2까지 죽인 것도 정당하다 — **2는 실행 사이의 누수를, 4는 *"이어 묻기"* 안의 누수를** 센다.

### ⚠️ 이 티켓이 만들지 않은 결함 하나를 재현했다 — `front`의 간헐 hang

**T-56과 무관하다. 커밋된 HEAD(T-55)에서 4회 중 1회 재현된다.**

```
HEAD  1: 124.0초 · 394/0     3: 123.8초 · 394/0     4: 123.1초 · 394/0
      2: 420.0초 · ★요약 없음★ · 마지막 줄  ✓ 2 ★ 하나 이상 고르면 그 경고가 안 닿는다 (1의 짝)
```

⚠️ **무작위 느려짐이 아니라 자리가 고정이다** — 매번 **T-54 검사 2 직후**, 즉
`t54Sync({ok:true})` → `calSyncNow` → `refreshToday()`/`renderCalendar()` 구간이다.
앱의 `fetch`엔 상한이 없어 워커가 한 번 응답을 놓치면 영원히 기다리고, **러너의 안전망
420초만이 유일한 출구**다(함정 8이 세운 그 장치가 실제로 이름을 말해 줬다).

⚠️ **첫 진단이 틀렸고 실측이 반증했다** — *"smoke 뒤에 붙어서"* 로 읽었는데(그렇게 두 번
연속 걸렸다), **front 단독 2회에서 1회가 걸렸다.** 상관을 원인으로 읽은 것이다.

**여기서 안 고쳤다** — T-54가 선 자리라 고치면 두 티켓이 한 커밋에 섞인다. Cowork에 올린다.
그 사이 `verify`는 재실행으로 통과한다(위 기준선은 `front 131.8초`인 실행의 것이다).
