# T-43 — 수집이 돌았는지 사람이 볼 수 있다

**발행** Cowork · 2026-08-21 · **담당** Claude Code · **작음 · 지금**
**T-41의 누락을 메운다.** 마이그레이션 없음 · APK 무관 · 서버 + 프런트

---

## 무엇이 어긋났나

**T-41이 실패 사유를 남기게 했는데, 그것을 사람이 볼 자리를 안 만들었다.**

2026-08-21 배포 직후 실측:

```
Api.collectedPending 존재     → 배포 완료
pending: []                   → 7일 창이 비었다

그런데 이것이
  ① 수집이 아직 안 돌았다        (cron 대기 · 토큰 오류 · URL 오타)
  ② 돌았는데 창 밖이라 안 보인다  (방학이라 정상)
중 무엇인지 **가를 수 없다.**
```

`pending`은 7일 창만 주고, `uclass_last_collect_at`은 `settings` 안에 묻혀 있어
콘솔에서 키 이름을 알아야만 꺼낼 수 있다.

**T-41 §할 일 ②가 스스로 적은 문장이 이 티켓의 근거다:**

> *"조용히 아무 일도 안 일어난다"*가 이 리포가 반복해서 물린 실패 모양이다.

## 왜 지금인가

**개강했는데 토큰이 만료되거나 URL이 틀리면, 사용자는 모른 채로 학기를 보낸다.**
T-41·T-42가 통째로 무의미해지는데 **아무 소리도 안 난다.**

그리고 9~11월이 전례를 쌓는 기간이다 — **수집이 죽은 채로 그 기간이 지나가면
다시 못 가져온다**(창이 `-5일 ~ +365일`이다).

**T-38이 `deny` 사유에서 고친 것과 같은 모양이고, 같은 이유로 지금 고친다.**

## ★ T-33의 §금지와 충돌하지 않는다 — 구별해서 적는다

T-33은 *"실패를 사용자에게 보이지 말라"*고 했다. **그 이유는 "사용자가 할 수 있는 일이 없다"였다.**

```
Guard 조회 실패   사용자가 할 수 있는 일이 없다   → 기록만 늘린다 (T-33)
수집 실패        ★ 사용자가 할 일이 있다        → 토큰을 다시 넣어야 한다
```

**행동이 가능한 실패는 보인다.** 이 구별을 티켓과 코드 주석에 남긴다 —
안 적으면 다음 사람이 T-33을 근거로 이 화면을 지운다.

## 할 일

### ① 서버 — 상태 하나

```
GET /api/collected/status
```

돌려주는 것 (이름은 담당이 정한다):

```
last_collect_at     마지막으로 수집을 시도한 시각        ← 없으면 "한 번도 안 돌았다"
last_result         'ok' | 실패 사유                    ← T-41이 이미 남기는 것
last_seen_count     그때 목록에 있던 VEVENT 수          ← 0과 실패를 가른다
counts              state별 개수 { new, accepted, dismissed }
next_earliest_at    다음 수집이 가능해지는 시각 (6시간 간격)
```

⚠️ **`last_seen_count`가 이 티켓의 핵심이다.** *"돌았지만 0건이었다"*와 *"안 돌았다"*를
가르는 유일한 값이고, 지금 그것이 없어서 못 가른다.

⚠️ **URL·토큰을 응답에 싣지 않는다.** 상태만이다.

### ② 화면 — 한 줄

**새 화면을 만들지 않는다.** 설정(⚙) 안 한 줄이면 된다:

```
정상   "학사 캘린더 · 3시간 전 확인 · 12건 중 새로 3건"
실패   "학사 캘린더 · 연결 실패 (http_403) · 주소를 다시 넣어 주세요"
미설정 "학사 캘린더 · 설정 안 됨"
```

**실패일 때만 눈에 띄게 한다.** 정상일 때는 조용한 한 줄이고,
`none` 상태의 제안 카드와 달리 **여기는 안 숨는다** — 숨으면 이 티켓의 목적이 사라진다.

## 범위

```
src/services/collected.ts   status
src/db/index.ts             counts 집계
src/index.ts                라우트 하나
public/api.js               래퍼 하나
public/app.js · index.html  설정 안 한 줄
test/smoke.ts · front.mjs   검사
```

**마이그레이션 없다.** T-41이 이미 `settings`에 쓰고 있는 것을 꺼내 보이는 것뿐이다.
⚠️ **T-41이 실패 사유를 `settings`에 안 남기고 있으면 그때는 남기는 것까지가 이 티켓이다** —
먼저 확인하고, 없으면 보고에 적는다.

## 금지

| 하지 말 것 | 왜 |
|---|---|
| URL·토큰을 응답에 싣기 | 상태만이다. 유출되면 캘린더 전체가 읽힌다 |
| 새 화면·새 탭 만들기 | 설정 안 한 줄이다 |
| 정상일 때 크게 보이기 | 잔소리가 된다. **실패일 때만** 눈에 띈다 |
| 실패를 숨기기 | 이 티켓의 목적이 그것이다. T-33의 §금지는 **행동 불가능한 실패**에 대한 것이다 |
| 수집을 화면에서 강제로 돌리는 버튼 | 6시간 간격이 지출·부하 통제다. 필요하면 별건 |
| `pending` 응답에 상태를 섞기 | 두 벌이 된다. 엔드포인트를 가른다 |

## 완료 조건

```
typecheck 통과 · smoke 342 → 346 이상 · front 298 → 300 이상 · 실패 0 · verify exit 0
```

**검사**

```
1  한 번도 안 돌았으면 last_collect_at 이 없다
2  ★ 돌았고 0건이면 last_collect_at 이 있고 last_seen_count 가 0이다   ← 1의 짝. 이 티켓의 본체
3  실패하면 last_result 에 사유가 들어간다
4  응답에 URL·토큰이 없다                                              ← 없는 것을 세는 검사
5  ★ 화면이 실패를 숨기지 않는다                                        ← T-33 패턴의 반대다
```

**1과 2가 짝이다.** 2가 없으면 *"0건이면 아예 안 보여주는 구현"*이 통과하고,
그것이 지금의 상태 그대로다.

**변이**
- `last_seen_count`를 안 싣는다 → **2만** 죽는다
- 응답에 URL을 싣는다 → **4만** 죽는다
- 실패일 때 화면을 숨긴다 → **5만** 죽는다

**T-41이 실패 사유를 실제로 남기고 있었는가 (§범위의 ⚠️): 남기고 있었다 — 다만 구멍이 있었다.**

`uclass_last_error`에 `${시각} ${사유}`로 남고 성공하면 지운다. 그래서 §범위의 "없으면 남기는 것까지가
이 티켓"은 발동하지 않았다. **대신 `last_seen_count`가 아예 없었다** — 그것을 쓰려면 수집 경로를
고쳐야 하므로 `uclass.ts`가 범위에 들어왔다(§범위 목록 밖 · 아래 두 줄이 그 전부다).

⚠️ **구멍 하나를 같이 막았다(범위 밖 · Cowork 판단 필요).** `res.ok`면 본문을 그대로 파싱하므로
**만료된 세션이 주는 로그인 HTML(200)이 "VEVENT 0건 성공"으로 기록된다.** 그러면 `last_seen_count=0`이
*방학이라 비었다*와 구별되지 않아 **이 티켓이 가르려는 것이 바로 거기서 무너진다.**
→ `BEGIN:VCALENDAR`가 없으면 `not_calendar`로 실패시킨다(검사 ③′).

**`last_seen_count`를 어디서 얻었나:** `parseIcal(text)` **직후, 저장 루프 다음**에
`events.length`(= UID가 있는 VEVENT 수)를 `settings.uclass_last_seen_count`에 쓴다.
`uclass_last_collect_at`과 **같은 자리에서 한 번에** 쓴다 — 둘이 갈라지면 "언제 돌았는지는 아는데
몇 건이었는지는 모르는" 상태가 생기고, 그게 지금 라이브의 상태다(아래 §실측).
DB로 세지 않은 이유: `collected_items`는 **누적 원장**이라 지난 학기 것이 그대로 있다.
"그때 목록에 몇 건이 있었나"는 원장이 답할 수 없는 질문이다.

**화면 문구 (실제 문자열 그대로).** 라벨과 값은 `.srow`의 양 끝이라 가운뎃점은 레이아웃이지 글자가 아니다 —
아래는 `textContent` 그대로다.

```
정상          학사 캘린더3시간 전 확인 · 12건 중 새로 3건
정상(0건)     학사 캘린더1시간 전 확인 · 0건 중 새로 0건
아직 안 돎    학사 캘린더아직 확인 전
실패          학사 캘린더연결 실패 (http_403) · 주소를 다시 넣어 주세요     ← 여기만 --brick + 굵게
미설정        학사 캘린더설정 안 됨
상태 조회 실패 학사 캘린더상태를 못 읽었어요
T-43 이전 수집 학사 캘린더3시간 전 확인 · 건수 기록 전
```

마지막 줄이 **지금 라이브에서 뜰 문구다** — 이미 한 번 수집했지만 그때는 건수를 안 남겼다.
있는 척하지 않고 그대로 말한다. 다음 수집(6시간 간격)부터 숫자가 붙는다.

**변이 셋 — 각각 자기 것만 죽였다(실제로 돌렸다).**

| 변이 | 결과 |
|---|---|
| `last_seen_count`를 안 싣는다 | smoke **354 → 352** · ★②와 그 짝만 죽었다 |

⚠️ **검사 ①을 고쳤다.** 처음엔 ①이 `last_seen_count === null`까지 봤더니 **첫 변이가 ①까지 죽였다** —
그러면 어느 결함이 무엇을 죽였는지 못 읽는다. null과 0의 대비는 ★짝의 몫으로 옮겼다.

### 곁에서 잡은 것 둘 (범위 밖 · 검사 파일 안)

1. **CRLF 트리에서 `npm run front`가 부팅부터 죽는다.** `front.mjs`가 `api.js`의 `API_BASE`를
   `/;\n/`로 치환하는데 **CRLF면 `;\r\n`이라 안 맞는다** → `API_BASE`가 상대 경로로 남아
   node fetch가 URL을 못 만든다. 화면 메시지는 *"부팅 실패 — 서버가 켜져 있는지 확인하세요"*라
   **서버 탓처럼 보인다.** Windows에서 `git stash`·`checkout` 한 번이면 재현된다(그렇게 만났다).
   → `\r?\n`으로 고치고, **치환이 빗나가면 즉시 이름을 말하고 죽게** 했다(T-06의 방향).
2. **T-42 ④가 흔들렸다** — 같은 코드가 4번 중 3번 빨간불. 처리 뒤 `refreshToday()`가 **실 API를
   한 번 왕복**하는데 검사는 `sleep(200)` 고정이었다. **고정 sleep은 상한이 아니라 추측이다.**
   → 상한 있는 `until(조건, 3초)`로 바꿨다. 부수 효과로 front가 **173초 → 121초**.

### §확인 절차 3행 중 2행은 스캐너가 대신 센다

*"눈으로 확인한다"는 확인 절차가 아니다*(`AGENT-CHAIN.md` §5). 문구·유출은 검사가 센다 —
smoke ⑦이 상태 한 줄에 '마감'·'제출'이 없는 것과 `url`·`token`을 화면에 안 쓰는 것을 스캔한다.
**사용자가 눈으로 볼 것은 "마지막 확인 시각이 실제와 맞는가" 하나로 줄었다.**

### §실측 — 이 티켓이 왜 필요했는지 (2026-08-22, 착수 직전)

```
uclass_last_collect_at = 2026-08-21T19:30:20+09:00     ← 돌았다
uclass_last_error      = ""                            ← 성공
collected_items        = 0행                           ← 캘린더가 비었다 (방학)
```

**돌았고 창이 빈 것이 맞았다.** 그런데 이 판정에 `wrangler d1 execute --remote` 두 번이 들었다 —
**사용자는 그걸 못 한다.** 그것이 이 티켓의 근거 그 자체다.
⚠️ 그리고 저 셋만으로는 *"200 HTML을 받아 0건으로 읽었다"*와 구별되지 않는다 —
위 `not_calendar`가 그 자리를 막는다.
