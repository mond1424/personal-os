# T-40 — flush가 자기 스냅샷으로 큐를 덮지 않는다

**발행** Cowork · 2026-08-20 · **담당** Claude Code · **작음 · 지금**
**T-39가 고치지 못한 절반. 밤에는 이쪽이 훨씬 흔하다.** APK 필요 · 마이그레이션 없음

---

## 무엇이 어긋났나

**`flush()`가 네트워크 왕복 내내 낡은 목록을 들고 있다가 그것으로 큐를 통째로 덮는다.**

```kotlin
val list = read(ctx)                  // :179  스냅샷
val item = list.first()
val code = post(base, token, item)    // :183  ~1.8초
write(ctx, list.drop(1))              // :186  ★ 낡은 list 로 덮는다
```

`read`·`write`는 각각 `@Synchronized`지만 **read-modify-write 쌍이 아니다.**
그 1.8초 사이에 다른 스레드가 쓴 것은 전부 사라진다.

**실측이 원인을 짚었다** (2026-08-20, 발동 넷을 반응 시점만 바꿔 걸었다):

| 발동 | 반응 | 결과 |
|---|---|---|
| 08:27:48 | +1.31초 | `deny` · 사유 실림 |
| 08:30:04 | **+0.48초** | **유실** (`ai_verdict = null`) |
| 08:32:53 | ~30초 | `deny` · 사유 실림 |
| 08:33:53 | **+0.57초** | **유실** |

**경계가 판정 도착 시각(캐시 적중 ~0.8초)과 정확히 맞는다.** 반응이 그보다 빠르면
`flush`가 판정 없는 스냅샷을 들고 나가고, 뒤늦게 `amendFire`가 쓴 것을 `write`가 지운다.

## T-39가 고친 자리가 아니다

T-39의 fallback은 *"`amendFire` 시점에 큐가 **이미** 비었을 때"*를 막는다.
실제로 일어난 것은 *"`flush`가 **아직 도는 중**"*이고, **그때는 큐에 행이 있어 fallback이 안 탄다.**

⚠️ **그리고 밤에는 이쪽이 사실상 전부다.**

```
캐시 적중 판정  ~0.8초   <   POST 왕복 ~1.8초        → fallback 도달 불가
```

Level 4는 **30분마다 재발동**하고 그 밤 첫 판정 이후는 **전부 캐시**다(ADR-024 ②).
즉 **둘째~여섯째 발동이 전부 이 구멍**이고, T-39는 모델을 실제로 부르는
**첫 판정(~3.3초)에서만** 일한다.

## 사라지는 것이 판정만이 아니다

`write(ctx, list.drop(1))`은 **목록 전체를 덮는다.** 그 창에서 생긴 것은 무엇이든 사라진다:

```
amendFire 가 쓴 판정                    ← 실측으로 확인된 것
T-39 가 새로 넣은 fallback 항목          ← 이 티켓이 없으면 T-39도 같은 창에서 지워진다
recordReaction 이 새로 넣은 반응 항목
그 사이에 들어온 새 발동 행              ← 개입 기록 자체가 사라진다
```

**마지막이 제일 무겁다.** 30분 간격 발동 중 하나가 앞 발동의 flush 창에 걸리면
**그 발동이 있었다는 사실이 없어진다.** 9~11월 전례의 분모가 조용히 줄어든다.

## 할 일 — 성질로 정한다

**보낸 뒤의 제거는 "내가 보낸 그것이 그대로일 때만" 한다.**

```
① POST 성공 후 큐를 다시 읽는다        — 스냅샷을 재사용하지 않는다
② 보낸 항목만 제거한다                  — 위치(drop(1))가 아니라 client_id 로 찾는다
③ 그 사이 바뀌었으면 남긴다             — 다음 flush 가 보낸다. 서버의 dup 경로가
                                          NULL → 값으로 채운다 (T-39가 이미 만든 자리다)
```

⚠️ **③이 루프를 무한히 돌리지 않게 한다.** 남긴 항목이 다시 `first()`가 되므로,
**한 flush 안에서 같은 `client_id`를 두 번 보내지 않는다**(보낸 것을 기억하고 건너뛴다).

**락으로 감싸지 않는다.** `flush`가 네트워크 왕복 동안 락을 쥐면 `amendFire`·`recordReaction`이
그만큼 멈춘다 — 개입 경로에 네트워크 대기를 들이는 것과 같은 모양이고 ADR-021이 막는 자리다.

## 범위

```
android/.../guard/GuardEventQueue.kt   flush 의 read-modify-write
test/smoke.ts                          스캐너 (아래)
```

**서버 무변경 · 마이그레이션 없음.** T-39가 만든 서버 dup 경로를 그대로 쓴다.

## 금지

| 하지 말 것 | 왜 |
|---|---|
| `flush` 전체를 락으로 감싸기 | 네트워크 왕복 동안 다른 스레드가 멈춘다. ADR-021 |
| `drop(1)`을 유지한 채 재읽기만 | **위치가 그대로라는 보장이 없다.** 새 항목이 앞에 들어오면 엉뚱한 것을 지운다 |
| `amendFire` 쪽을 고쳐 우회하기 | 원인은 `flush`다. 쓰는 쪽을 다 고치는 것은 같은 실수를 n곳에 심는다 |
| 판정 도착까지 flush를 미루기 | 반응 기록이 최악 16초 늦어진다(T-39 §금지와 같다) |
| T-39의 fallback 제거 | 여전히 필요하다 — 첫 판정(모델 호출 ~3.3초)에서는 그쪽이 일한다 |

## 완료 조건

```
typecheck 통과 · smoke 321(변화 없음 또는 +스캐너) · front 291(변화 없음) · 실패 0
Kotlin: assembleRelease BUILD SUCCESSFUL
```

**검사** — 이 결함은 서버 POST 검사가 못 본다(T-38·T-39가 배운 것). 소스를 직접 본다:

```
1  flush 가 POST 뒤에 큐를 다시 읽는가            ← 양성 매치 (스냅샷 재사용이면 거짓)
2  제거가 위치가 아니라 client_id 기준인가
3  ★ 1·2의 스캐너가 살아 있는가 (주석 걷어내고)
```

⚠️ **스캐너로는 부족하다는 것을 알고 낸다.** 경쟁 조건은 정적 검사가 증명하지 못한다 —
**아래 실측이 이 티켓의 진짜 판정이다.**

## 확인 절차 — 실측이 판정이다

**T-39 실증에서 쓴 그 방법 그대로. 자연 실험이 이미 설계돼 있다.**

```
발동 넷을 걸고 반응 시점을 바꾼다:   +0.5초 · +0.5초 · +1.5초 · +30초
20초 뒤 네 행의 ai_verdict 를 본다
```

```
넷 다 판정이 실린다        → 통과
빠른 둘만 비어 있다        → 안 고쳐졌다 (이 티켓 이전과 같다)
```

⚠️ **캐시 적중 상태에서 재야 한다** — 그 밤 첫 판정은 모델을 부르느라 3.3초라 창을 벗어난다.
**같은 `event_id`로 두 번째 이후를 걸어야 0.8초가 나온다.**

⚠️ **AI 예산**: 캐시 적중은 `ai_used=0`이라 상한을 안 쓴다. 첫 발동 하나만 예산을 쓴다.
