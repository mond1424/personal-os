# T-25 — 캘린더 탭에서 탭 전환을 할 수 있게 (가장자리를 내준다)

**발행** Cowork · 2026-08-06 · **담당** Codex CLI · **상태** ⬜ 대기

---

## 증상

**캘린더 탭에 갇힌다.** 화면이 캘린더로 가득 차서 탭 전환 스와이프를 시작할 자리가 없다.
nav 버튼으로만 나갈 수 있다.

## 원인 — 이미 코드에 있다

```js
const noSwipe = (el) => !!(el.closest && el.closest("#cal-rows, .bchart, …"));
bindCarousel(scr, { blocked: (e) => noSwipe(e.target) || !!S.pick, … });
```

`#cal-rows` 위에서 시작한 포인터는 **탭 캐러셀이 통째로 무시한다.** 의도된 것이었다 —
그러지 않으면 달 넘기기와 탭 전환이 서로 잡아채기 때문이다.

캘린더가 화면 대부분을 덮으면서 그 대가가 커졌다.

## 방향 — 가장자리만 탭에 준다

```
캘린더 가운데   달 넘기기      (지금 그대로)
좌우 가장자리   탭 전환        ← 새로
```

**`bindCarousel`의 `opt.blocked` 훅을 쓴다.** 이미 있는 자리다 —
캘린더가 `blocked`로 빠지면 `setPointerCapture`도 안 걸리고, 바깥 탭 캐러셀이 정상적으로 축을 잡는다.

**`AXIS_LOCK`·`FLICK_V`·`dragBlockUntil`·`VEL_*`를 건드리지 않는다.** 판정은 그대로고
**"누가 받을 것인가"만 바꾼다.** 함정 2·4.

### 양쪽을 함께 고친다 — **이 티켓의 덫**

두 `blocked`가 **짝**이다. 한쪽만 고치면 죽은 구역이 생긴다:

| 고친 것 | 가장자리에서 벌어지는 일 |
|---|---|
| `noSwipe`만 | 탭도 캘린더도 반응 — **둘이 서로 잡아챈다** |
| 캘린더 `blocked`만 | 캘린더는 빠졌는데 탭은 `noSwipe`에 막혀 **아무것도 안 된다** |
| 둘 다 | 탭만 받는다 ✓ |

**"고쳤는데 아무 반응이 없다"가 두 번째 줄이다.** 그리고 그건 폰에서만 드러난다.

### 캘린더만 예외다

`noSwipe`는 `#cal-rows` 말고도 `.bchart`·`.seg`·`input`·`.sheet` 등을 막는다.
**그것들은 가장자리에서도 그대로 막는다** — 입력칸은 화면 끝에 있어도 입력칸이다.

```
✓  캘린더 위 + 가장자리      → 탭이 받는다
✗  input 위 + 가장자리       → 지금처럼 아무것도 스와이프하지 않는다
```

## 가장자리 폭

**화면 폭의 10%**로 시작한다. 좌우 각각이므로 합쳐 20%.

- `scr.clientWidth || 380` 폴백을 쓴다 — **jsdom은 `clientWidth`가 0이다**(함정 2)
- px 리터럴로 박지 않는다. 화면 크기가 다르면 비율이 무너진다
- 실사용에서 조정할 값이다 — 좁으면 못 잡고, 넓으면 달 넘기기가 답답해진다

## 검사가 거짓 통과하는 자리 — **두 번째 덫**

**jsdom에서 `clientWidth`가 0**이면 가장자리 판정이 항상 참이거나 항상 거짓이 된다.
그러면 "가장자리에서 탭이 바뀐다"가 **아무것도 확인하지 않고 초록이 된다.**

함정 3이 같은 종류다 — 좌표를 나중에 붙여 `dx=NaN`이 되고 '세로'로 오판했는데 검사는 통과했다.

**폭을 주입하거나 폴백이 실제로 걸리는지 확인한다.** 검사가 `380`을 실제로 쓰는지 보이게 한다.

## 범위

```
public/app.js       noSwipe · 캘린더 blocked · 가장자리 판정
test/front.mjs      검사
```

**서버·CSS를 건드리지 않는다.**

## 금지

| 하지 말 것 | 왜 |
|---|---|
| `AXIS_LOCK`·`FLICK_V`·`VEL_*`·`dragBlockUntil` 수정 | 판정은 옳다. 바뀌는 것은 "누가 받는가"뿐 — 함정 2·4 |
| 한쪽 `blocked`만 고치기 | 죽은 구역이 생긴다. 폰에서만 드러난다 |
| `noSwipe`의 다른 대상까지 가장자리 예외로 | `input`은 화면 끝에서도 입력칸이다 |
| 가장자리 폭을 px 리터럴로 | 화면 크기가 다르면 무너진다 |
| `clientWidth` 폴백 제거 | jsdom은 0이다 — 함정 2 |
| `setPointerCapture` 순서·위치 변경 | 캡처가 걸리면 바깥이 못 받는다. `blocked`에서 빠지는 것이 핵심이다 |
| `booted` 가드 제거 · `scrollIntoView` | 함정 4 · 1 |

검사:

2. 캘린더 **왼쪽 가장자리**에서 끌면 탭이 바뀐다
3. 캘린더 **오른쪽 가장자리**에서 끌면 탭이 바뀐다
4. 가장자리에서 **세로**로 끌면 아무것도 가로채지 않는다
5. `input` 위 가장자리에서는 여전히 아무 스와이프도 안 걸린다
6. **폭이 0인 환경에서 폴백(380)이 실제로 쓰인다**

**2·3이 짝이고 6이 그 둘을 지킨다.** 6이 없으면 2·3은 `clientWidth=0` 때문에
**아무것도 확인하지 않고 초록이 된다.**

좌우를 각각 태우는 이유는 T-21과 같다 — 한쪽만 검사하면 반대쪽이 우연히 맞는 것과 구별되지 않는다.

## 검토 (검토 세션이 채운다 · HANDOFF-0731 §2)

**검사 2·3이 한쪽만 고친 구현에서 빨간불이 되는가: 양쪽 다 그렇다. 실제로 태웠다.**

| 변이 | 결과 | 빨간불이 말한 것 |
|---|---|---|
| **A — `noSwipe`만 고침** (캘린더 `blocked`에서 `isSwipeEdge` 제거) | **256 → 254/2** · 2·3만 | `today / 2026-8`, `works / 2026-9` — **탭도 달도 움직였다.** 표 1행 "둘이 서로 잡아챈다" 그대로 |
| **B — 캘린더 `blocked`만 고침** (`noSwipe`가 `#cal-rows`를 무조건 막음) | **256 → 254/2** · 2·3만 | `cal / 2026-9` 둘 다 — **아무것도 안 일어났다.** 표 2행 "죽은 구역" 그대로 |

**두 변이가 서로 다른 이유로 같은 두 줄을 빨갛게 한다** — 이게 이 티켓의 핵심이었다.
A를 잡아내는 것은 탭이 아니라 **달 조건**이다(A에서 탭은 기대대로 바뀐다). 검사 2·3이
`tab()`과 `S.cal.y/m`을 **함께** 보기 때문에 잡혔다 — 탭만 봤으면 A가 초록으로 샜다.

**검사 6이 폭 0에서 거짓 통과를 막는가: 막는다. 그리고 6이 없으면 실제로 샌다.**

폴백(`|| 380`)을 지우고 태웠다 → **256 → 253/3**: 검사 6 · 검사 1(가운데) · 검사 2가 빨간불.
폭이 0이면 `x <= 0 || x >= 0`이 **항상 참**이라 화면 전체가 가장자리가 된다. 그때:

```
검사 3(오른쪽 가장자리)  →  초록  ← 거짓 통과. '전부가 가장자리'라 우연히 맞는다
검사 1(가운데)           →  빨강  ← 증상은 여기서만 보인다
검사 6                   →  빨강  ← 원인을 이름으로 말한다 (clientWidth=0)
```

**6이 없었으면 "가운데 검사 하나가 왜 이상하지"로 끝나고 오른쪽 가장자리는 초록인 채였다.**
검사 6은 폴백 유무만 보는 게 아니라 경계값 넷(37/39/341/343)을 양쪽에서 눌러
"항상 참"·"항상 거짓" 어느 쪽으로 무너져도 걸린다. 함정 3이 다시 나지 않게 짜였다.

**제스처 상수 무변경: 그렇다.** `git diff -U0`의 **바뀐 줄**에 `AXIS_LOCK`·`FLICK_V`·`VEL_MIN_DT`·
`VEL_WIN`·`VEL_STALE`·`dragBlockUntil`·`setPointerCapture`가 하나도 없다(잡히는 것은 hunk 헤더의
문맥뿐). `bindCarousel` 본문은 손대지 않았고 추가는 `SWIPE_EDGE_RATIO`·`isSwipeEdge` 둘뿐이다.
바뀐 것은 **"누가 받는가"**(`blocked` 두 개)뿐 — 티켓이 요구한 그대로다.

**`noSwipe`의 다른 대상이 가장자리 예외가 되지 않았는가: 안 됐다.**
`.bchart, .wsegs, .seg, .seg-mini, .likert, .dcol, .sheet, .board, .modal, .tut, input, textarea`를
**먼저** 검사해 `true`로 즉시 빠지고, 가장자리 판정은 그 뒤 `#cal-rows` 줄에만 붙는다.
목록은 HEAD와 글자까지 같고 `#cal-rows` 하나만 빠졌다. 검사 5가 캘린더 화면 가장자리의
`input`에서 아무 스와이프도 안 걸리는 것을 확인한다.

**한 가지 짚어 둘 것 — 두 `blocked`가 같은 자를 쓴다.** 양쪽 다 `isSwipeEdge(e, $(".screens"))`로
**같은 host**를 잰다. 한쪽이 `#cal-rows`를 기준으로 쟀다면 두 사각형의 좌표가 어긋나는 폭만큼
"둘 다 막힌" 실틈이 생겼을 것이다 — 폰에서만 드러나고 재현이 어려운 종류다. 지금은 그 위험이 없다.

**설계 위반 · 함정 재발: 없다.** 서버·CSS 무변경 · 폭은 비율(`SWIPE_EDGE_RATIO = 0.1`)이고
px 리터럴이 아니다 · `clientWidth || 380` 폴백 유지(함정 2) · 검사가 좌표를 `MouseEvent`
생성자로 넘긴다(함정 3) · `setPointerCapture` 순서·위치 무변경 · `scrollIntoView` 없음(함정 1) ·
`booted` 가드 그대로(함정 4). 검사는 날짜 셀(`.c`)에서 이벤트를 시작해 `#cal-rows` → `.screens`
**버블 경로를 실제로 태운다** — 훅을 직접 부르지 않는다.

**판정: 통과.** front 249 → 256 · smoke 272(무변경) · 실패 0.
남은 것은 **가장자리 폭 10%의 실측**뿐이다(확인 절차 4번) — 손가락으로만 정해지는 값이라
검사가 대신할 수 없다.
