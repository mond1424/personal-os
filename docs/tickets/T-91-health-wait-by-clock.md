## 목표

`e2e.mjs`의 헬스 대기가 실제로 30초 남짓에 끝나고, 실패 문구가 실제로 기다린 시간을 말하게 한다.
왜: 지금 루프는 120회 × (요청 상한 2초 + 쉼 0.25초)라, 서버가 연결만 받고 응답하지 않으면 최대 약 270초를 기다리면서
"30초 안에 응답하지 않았다"고 말한다. T-06이 `fetch`마다 상한을 붙였지만 루프 전체는 여전히 반복 횟수로 잰다 —
**반복 횟수로 감싼 상한은 상한이 아니다**(T-06 2차). 진단 문구가 대기 시간을 틀리게 말하면 hang을 가르는 단서가 흐려진다(함정 8).

### 구현과 실행 근거

- 코드 변경은 3번 절의 헬스 루프·주석·실패 문구뿐이다. `performance.now()`로
  전체 30초 마감을 정하고, 각 요청은 `min(2000ms, 남은 시간)`, 쉼은
  `min(250ms, 남은 시간)`으로 제한한다. 마감 이후 응답은 성공으로 세지 않는다.
  반복 횟수만 제한하는 안은 응답 없는 요청의 소요를 전체 대기에 반영하지 못하므로 쓰지 않았다.
- 30초 값과 마이그레이션 120초·시드 60초·front 안전망 420초는 그대로다.
  `test/front.mjs`와 검사 본문은 바꾸지 않았다. API 구조·스키마가 같아 지도 재생성·덤프는 없다.
- 정상 대조: 2026-10-07 19:01 KST에 전체 verify가 끝났다. 마이그레이션 17.6초·front 본문
  158.8초·smoke 537/0·front 526/0·schema 일치·exit 0. 간헐 hang은 이번 실행에서 관측하지 않았다.
  원출력은 OS 임시 폴더의 `personal-os-t91-verify.log`에 있다.
- 실패 대조: `e2e.probe.mjs` 사본에는 대상 주소 변경과 헬스 시작 출력만 넣었다.
  원본과 같은 마이그레이션·dev 기동·헬스 루프·실패 정리를 실행했다.
  별도 부모 프로세스의 단조 시계로 시작 출력부터 헬스 오류 출력까지 재어 문구와 대조했다.
  아래 숫자는 헬스 구간이며 마이그레이션·기동·정리 시간은 포함하지 않는다.

| 대상 | 실제 헬스 대기 | 오류 문구의 경과 초 | 사본 종료 | 경로 확인 |
|---|---:|---:|---:|---|
| HTTP 요청을 받고 응답하지 않는 서버 | 30.012초 | 30.0초 | 1 | 서버가 요청 14건 수신 |
| 닫힌 포트 | 30.014초 | 30.0초 | 1 | 실행 직전 실제 fetch의 ECONNREFUSED 확인 |

두 오류 모두 `상한 30초`와 대상 URL을 함께 출력했다. 원출력은 OS 임시 폴더의
`personal-os-t91-no-response.log`·`personal-os-t91-closed-port.log`에 있다.
검증 도구는 두 경로의 시간·문구·exit 검증 후 exit 0으로 끝났다. 사본과 일회용 검증 도구는
삭제했고, 실행 전후 원본 `test/e2e.mjs` SHA256 동일을 확인했다.

실행 명령(Windows PowerShell, `login: false`, 추가 권한 환경):

## 검토 (설계층 · 2026-10-07)

```text
층 · 도구: 설계층 · Codex (GPT)

검증 수치의 출처: 감독층 §보고와 보존된 정상·실패 실행 로그.
설계층은 verify·사본 실패 대조를 재실행하지 않았다.
```

- **전체 상한:** `performance.now()`로 한 번 정한 마감을 모든 반복이 공유한다. 요청은 2초와 남은 시간 중
  작은 값으로 끊고, 요청이 끝난 뒤 남은 시간을 다시 계산해 쉼도 제한한다. 따라서 느린 요청 120회를
  쌓던 경로가 사라졌다. 요청 상한에 쓰는 올림은 정수 밀리초를 만들기 위한 것이며, 실측의 작은 초과와 함께
  티켓의 **30초 남짓** 조건에 부합한다. 정확히 30.000초에 프로세스가 종료된다는 판정은 아니다.
- **성공·실패 의미:** 성공 응답도 마감 전에 받은 것만 인정한다. 실패 문구의 경과 초는 시작 때와 같은
  단조 시계로 계산하며, 상한과 대상 URL을 따로 표시한다. 기존 dev 조기 종료 감지·출력 보존·실패 정리 경로는
  유지됐다. 마이그레이션 120초·시드 60초·front 안전망 420초와 검사 본문은 diff에 없다.
- **실패 대조:** 두 사본 로그에서 헬스 시작 표시, `30.0초`·상한 30초인 오류, 진단 폴더 보존까지 확인했다.
  외부 측정 **30.012초 / 30.014초**, 응답 없는 서버의 요청 14건, 닫힌 포트의 ECONNREFUSED 및 각 exit 1은
  감독층 보고에서 받았다. 측정 구간은 헬스 시작부터 오류 출력까지이며 전체 러너 소요로 읽지 않는다.
  사본과 일회용 도구가 현재 없는 것도 확인했다. 정상 실행과 실패 경로 둘을 함께 제시해,
  즉시 포기하거나 요청별 상한만 둔 구현과 구별된다.
- **기준선:** 정상 로그에서 smoke **537**, front **526**, 각각 실패 0, schema **26개 마이그레이션·71개 객체 일치**를
  확인했다. typecheck 통과·전체 exit 0은 감독층 보고와 같다. 발행 당시 smoke 534와의 차이 +3은 이미 검토한
  T-92의 전제 검사다. T-91의 증감은 **smoke 537 → 537 · front 526 → 526**으로 인정한다.
  이번 통과를 기존 front 간헐 hang의 해결로 해석하지 않는다.

**채택:** 단조 시계로 전체 마감을 정하고 요청·쉼을 남은 시간에 맞춘다.
**기각:** 횟수 제한 유지·30초 값 확대 — 전자는 요청 시간의 누적을 막지 못하고, 후자는 잘못 재는 방식을 남긴다.

감독층 후속은 티켓 머리의 `⬜ 대기`를 `✅ 닫힘`으로 바꾸고, `STATE.md`의 검토 대기를 정리한 뒤
이 검토와 함께 커밋하는 것이다(`설계층 발행분` 명시). 추가 코드 수정·검사 재실행·배포·APK·폰 확인은
판정의 조건이 아니다. push는 별도 사용자 허락을 따른다.
