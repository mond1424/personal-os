# T-97 — pOS의 새 과제 수락을 종료하고 기존 기록을 보존한다

**발행** 설계층 · 2026-10-08 · **담당** 감독층 · **상태** ⬜ 대기
**근거** 사용자 결정 2026-10-08 · ADR-050 추가 개정 · T-96 취소 후 발행
**착수 조건:** T-95 코드 커밋·설계 검토·종료 후 (T-94 → T-95 → T-97).
**서버 + 웹 · 마이그레이션 없음 · APK 변경 없음 · 구현 후 사용자 배포 필요**

---

## 목표

과제는 Tasks.org가 맡는다. pOS의 수집 제안·수락 화면과 서버 수락 경로를 종료해 새 과제가 일정·할 일로
들어오지 않게 한다. 기존 원장·일정·할 일·예정·완료 기록은 보존한다. 화면만 숨기면 옛 화면에서 계속
수락할 수 있으므로 서버에서도 막는다. T-96의 마감 차이 표시는 구현하지 않는다.

**경계:** 현재 수집 수락 경로 전체를 닫는다. `source='uclass'` 안에는 개인 일정도 섞이고 과제 여부를
확정하는 필드는 없다. 제목·categories로 과제를 추정해 일부를 통과시키지 않는다. 이 경로의 개인 일정 수락도
종료하는 대가를 ADR-050에 기록했다. 일반 할 일·손 일정 생성, 폰 캘린더 미러, 시간표는 유지한다.
자유 입력 제목에 「과제」가 있다는 이유로 일반 생성 API를 막지 않는다.

## 범위 — 이 파일들만 고친다

```
src/services/collected.ts    pending/list 빈 배열, accept/dismiss 종료, 낡은 생성 코드 제거
src/index.ts                collected 라우트의 종료 계약·주석 정리 (인증 유지)
public/app.js               Today/Works 입구·공유 수락 시트 처리 제거, Me 안내
public/index.html           td-coll·coll-entry·sh-coll 전용 마크업 제거
public/api.js               새 웹에서 사용하지 않는 수집 제안/수락/거절 래퍼 제거
test/smoke.ts               서버 종료·무변경·기존 기록 회귀 검사와 옛 픽스처 전환
test/front.mjs              입구 종료·기존 기록·일반 생성·Me 안내 검사
docs/api-surface.md         서버 종료 계약 반영
```

감독층의 STATE·APP-BUILD·보고·커밋은 통상 종료 절차다. 범위 밖 수정이 필요하면 멈추고 보고한다.
사용하지 않는 CSS·DB 헬퍼 전체 청소까지 넓히지 않는다. 원장 수집기·스키마·마이그레이션·secret은 건드리지 않는다.

## 할 일

1. **서버가 먼저 닫는다.** 인증된 `POST /api/collected/:id/accept`와 `.../dismiss`는 **410** 및
   `과제는 Tasks.org에서 관리해요. pOS는 새 과제를 받지 않으며 기존 기록은 남아요.`를 반환한다.
   서비스 함수도 같은 종료 결과를 내며 생성/상태 변경 코드는 제거한다. 라우트에만 가드를 붙이고 내부 생성 경로를 남기지 않는다.
   new·dismissed·accepted, 과거·현재·미래·시각 없음 모두 동일하다. 이미 accepted인 재시도도 성공 응답 대신 410이다.
   없는 id도 이 종료 API에서는 410으로 답한다. 기존 인증과 공통 요청 파싱의 오류 처리는 유지한다.
   유효한 JSON의 choice 누락·done·todo·skip·임의 문자열이 종료를 우회하지 못한다. `needs_choice`도 더 이상 반환하지 않는다.
   어떤 요청도 event·task·entry를 만들거나 `collected_items.state/event_id/task_id`를 바꾸지 않는다.
2. `GET /api/collected/pending`와 `GET /api/collected/list`는 **200 + 빈 배열**을 반환한다. 옛 클라이언트가
   배열을 순회하던 계약을 유지하되 수락 후보는 제공하지 않는다. 이미 캐시한 후보로 POST해도 1의 서버 종료가 막는다.
   빈 배열을 만들기 위해 기존 new를 dismissed로 바꾸거나 원장을 삭제하지 않는다.
3. `GET /api/collected/status`의 실제 수집 상태·원장 건수·관측 시각은 유지한다. Me의 수집 상태 행도 유지하고
   1의 안내를 함께 표시한다. **원장 수집 건수와 새로 수락할 과제 수를 구분**해 표기한다.
   과제 관리 이관 안내는 상태 조회가 실패해도 보인다. 실패·미설정·수집 성공을 이관 완료나 0건 성공으로 위장하지 않는다.
   외부 앱이 설치됐는지 감지하거나 새 연결 버튼·설정·자동 이동을 만들지 않는다.
4. Today의 `loadCollected`/`#td-coll`, Works의 `loadCollectedEntry`/`#coll-entry`와 호출부,
   `renderCollected`/`#sh-coll`, 과거 선택지·후처리·전용 API 래퍼를 제거한다. `collectedStatus`는 남긴다.
   새 웹은 옛 서버가 후보 배열을 돌려줘도 수락 화면을 다시 만들지 않는다. Today·Works·Me가 정상 렌더되고
   제거된 DOM을 읽는 예외가 없어야 한다. 매번 뜨는 경고 카드 대신 Me의 한 자리에서 종료 이유를 알린다.
5. **기존 기록은 이관 과정에서 그대로 둔다.** new·accepted·dismissed 원문, event/task FK(과거의 task_id NULL 포함),
   일정 시각·제목·보호, 예정·완료·취소·분석 입력을 수정하지 않는다. 기존 과제는 Today·Works·달력·날짜 상세에서
   계속 조회되며 기존 규칙 안의 완료·취소·되돌리기·미루기를 유지한다. T-95의 삭제 안내와 참조 보호도 유지한다.
   밤 Guard·직접 건 보호 일정·wake 계산은 바꾸지 않는다. 옛 과제 마감이 기존 약속 후보로 남는 것도 자동 해제하지 않는다.
6. `uclass.collect`의 원장 수집·관측 갱신은 유지한다. 새 원문 저장과 pOS 수락은 별개다.
   수집 후에도 원장 상태·FK는 저절로 수락으로 바뀌지 않고 task/event는 생기지 않아야 한다.
   `courseOf`·`titleOf` 같은 순수 이름 함수는 이 티켓에서 굳이 제거하지 않는다. 저장된 제목과 적용된 마이그레이션은 이력이다.
7. T-42·T-75·T-78·T-80 등의 **종료된 수락 동작 검사**는 새 계약으로 교체한다. T-94·T-95·T-84 등의
   살아 있는 검사에서 수락 API를 픽스처 생성에 쓰면 **격리된 검사 DB에 기존 수락 기록을 직접 준비하는 방식**으로 옮긴다.
   새 런타임 우회 플래그·관리자용 수락 API는 만들지 않는다. 기존 과제 관리·달력 합침·FK 보호·원장 수집 검사는 보존한다.
   순수 이름 함수 검사를 수락 성공과 분리하고, 삭제·교체·추가한 검사 이름과 수를 보고한다.
8. `docs/api-surface.md`를 갱신하고 STATE에 T-96 취소와 신규 수락 종료의 구현/배포 상태를 구분해 기록한다.
   과거 수락 기능의 구현·배포·검사 보고를 지우지 않는다. 이 티켓 구현 완료를 라이브 수락 종료로 단정하지 않는다.

## 금지

| 하지 말 것 | 왜 |
|---|---|
| 기존 원장·task·event·예정·완료·보호 기록 삭제 또는 일괄 완료/취소/거절 | 사용자 결정은 기존 기록 보존이다 |
| FK를 NULL로 비우거나 과거 task_id NULL에 task 소급 생성 | 원장의 의미와 T-95 참조 보호를 깨뜨린다 |
| 신규 수락을 다시 여는 설정·과제 제목 판별·옛 화면 전용 우회 | 종료 결정을 우회한다 |
| T-96 source_deadlines·차이 표시·자동 마감 추종 구현 | 사용자가 접은 기능이다 |
| 수집기·cron·secret 제거, Tasks.org 연동·데이터 복사 | 수락 종료 범위 밖이다 |
| 일반 할 일/일정 생성 차단, 캘린더 미러·시간표·Guard 변경 | 과제 수락 경로와 별개다 |

## 완료 조건

```
typecheck 통과 · smoke A → B · front C → D · 실패 0 · schema 일치 · verify exit 0
```

착수 기준선은 STATE와 T-95 종료 보고에서 받는다. 검사 수 감소를 숨기지 말고 폐기/교체/추가 내역으로 설명한다.

- 실제 API에 new·dismissed·accepted(연결 task 있음/NULL), 없는 id를 주고 두 POST가 410인지 본다.
  과거/미래·시각 없음, choice 누락/각 선택/임의 값·반복 요청을 포함한다. 단순 응답 검사로 끝내지 않고
  원장·task·event·entry·보호의 행 수와 관련 값이 호출 전후 동일함을 확인한다. 읽기 전용 GET도 상태를 바꾸지 않는다.
- 원장에 후보를 실제로 넣어도 두 GET은 빈 배열이고 status의 실제 건수는 남는다. 인증 없는 요청은 기존대로 거절된다.
- 격리된 수집 입력에서 새 UID 저장·기존 UID 관측 갱신은 되지만 event/task 생성과 기존 상태·FK 변경은 없다.
- 기존 수락 기록으로 달력 합침·날짜 상세·Today/Works 노출·완료/취소/되돌리기·미루기와 T-95 삭제 안내를 검사한다.
  과거 task_id NULL도 유지한다. 보존 검사에서 새 수락 API 성공을 전제로 하지 않는다.
- front는 후보를 주는 옛 API 모형에서도 Today/Works에 입구·수락 버튼이 없음을 확인한다. Me는
  수집 성공·미설정·실패 각각에서 종료 안내와 실제 상태를 구분한다. 일반 할 일·일정 생성은 계속 작동한다.
- 서버 410의 실제 오류 모양을 확인해 옛 웹의 공통 오류 표시가 종료 문구를 읽을 수 있음을 보고한다.
  감독층이 격리 검사에서 옛 클라이언트 요청을 재현한다. 실사용 원장을 바꿔 시험하지 않는다.
- 호출부 잔여를 조사하고 제거된 DOM/함수 때문에 새 화면이 실패하지 않는지 확인한다.
  배포 전후 웹 캐시가 섞여도 **새 서버의 수락 차단**은 유지되어야 한다.

## 확인 절차 (사용자)

1. 배포 후 폰에서 Today·Works·Me를 연다. 새 수집 제안·「들어온 것」·수락 시트가 없고 Me의 이관 안내가 읽혀야 한다.
2. 기존 과제와 마감 일정을 조회한다. 제목·날짜·완료 기록이 남고, T-95의 삭제 안내가 유지되는지 확인한다.
   과거 일정은 최신 마감으로 자동 갱신되지 않는다. 현재 과제 마감·알림·완료는 Tasks.org에서 확인한다.
3. 일반 할 일·손 일정 입력과 시간표·폰 캘린더·밤 Guard 화면이 평소처럼 동작하는지 확인한다.
   실제 밤 알림 수신과 화면 확인을 구분해 기록한다. API 차단은 감독층의 격리 검사로 보고받는다.
