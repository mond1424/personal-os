# T-37 — 기기가 서버보다 먼저 포기하지 않는다

**발행** Cowork · 2026-08-19 · **담당** Claude Code · **작음 · 지금**
**근거** [ADR-038](../../APP-ADR.md#adr-038) · **APK 필요** (Kotlin 상수)

---

## 무엇이 어긋났나

**두 상수가 서로를 모른 채 겹쳐 있고, 바깥이 안보다 먼저 끊는다.**

```
기기  android/.../guard/GuardVerify.kt:29    TIMEOUT_MS    = 6_000   (connect·read 각각)
서버  src/services/guard.ts:507              AI_TIMEOUT_MS = 8_000   (model_high race)
```

**그래서 `server_timeout`은 관측될 수 없다.** 서버가 그 값을 주려면 8초 뒤에 답해야 하는데
기기는 6초에 끊는다. T-31이 만든 구별 — `timeout`(기기가 못 닿음) vs `server_timeout`(모델이 늦음) —
의 **한쪽이 도달 불가능한 값**이고, 그 둘은 대응이 다르다.

⚠️ **이것이 격상 0회의 원인은 아니다.** 판정 전수를 세면 그렇지 않다:

```
deny 11 · unavailable/timeout 3 · unavailable/(이유없음) 6 · unavailable/cap 2 · approve 0
```

`deny` 열한 번은 **왕복이 6초 안에 끝났다는 뜻**이고 그중 둘은 `ai_used=1`로 기록됐다.
**`ai_used` 기록 경로는 정상이고 일일 상한도 작동한다.** 이 티켓은 성능이 아니라
**관측 하나를 되살리는 것**이다 — 범위를 그렇게 좁게 잡는다.

## 왜 지금

**9~11월이 §6.5의 전례를 쌓는 기간이고, 그때 `approve`가 왜 안 나오는지를 읽어야 한다.**
지금 `unavailable`이 오면 *"Doze가 끊었나 · 모델이 늦었나"*를 가를 수 없다 —
8/18 밤의 `timeout` 셋이 정확히 그 상태였다. **경계가 흐린 채로 세 달을 쌓으면
12월에 그 세 달이 못 읽는 데이터가 된다.**

작고, APK 한 번에 묶이면 끝난다.

## 할 일

### ① 순서를 바로잡는다

**바깥이 안보다 길다.** 어느 값을 옮길지는 담당이 정하되, 근거를 보고에 적는다.

권고: **기기 쪽을 늘린다.** 개입 화면은 이미 떠 있고 검증은 백그라운드 스레드라
(`GuardNotifications.kt:233` `Thread { … }`) **사용자가 기다리는 시간이 아니다.**

⚠️ **`connectTimeout`과 `readTimeout`을 같은 값으로 두지 않는다.**

```
connectTimeout   짧게 — 연결이 안 되는 것은 진짜 네트워크 부재다. 빨리 알수록 낫다
readTimeout      길게 — 서버가 생각 중인 시간이다. 여기가 서버 예산보다 커야 한다
```

지금은 둘이 같은 상수를 쓴다. **뜻이 다른 둘을 한 이름으로 두면 한쪽을 고칠 때 다른 쪽이 딸려 간다.**

### ② 두 값이 갈라지는 것을 검사가 막는다

**이게 이 티켓의 본체다.** 지금은 **한쪽만 고쳐도 아무 검사가 빨간불이 되지 않는다** —
서로 다른 언어·다른 파일에 있고 서로를 모른다.

`test/smoke.ts`가 두 파일을 읽어 비교한다:

```
① 기기 readTimeout > 서버 AI_TIMEOUT_MS 인가
② ★ 스캐너가 살아 있는가        ← 합성 값으로 실제로 잡는지 확인 (T-36 ②의 자리)
③ 두 상수를 각각 찾았는가        ← 정규식이 못 찾으면 ①이 조용히 통과한다
```

**②·③이 ①의 짝이다.** *"부등호가 참이다"*를 세는 검사는 **둘 다 못 찾아도 참**이 될 수 있다
(`undefined > undefined`는 false지만, 파싱 실패를 0으로 채우면 참이 된다) — AGENT-CHAIN §5.

### ③ `server_timeout`이 관측 가능해진 것을 확인한다

고친 뒤 **서버 타임아웃을 일부러 짧게(예: 100ms) 만들어 한 번 발동**시키면
`ai_unavailable_reason`이 `server_timeout`으로 와야 한다. **와야 T-31의 구별이 살아난다.**
확인 후 되돌린다. (이건 변이 검사이지 커밋할 변경이 아니다.)

## 범위

```
android/.../guard/GuardVerify.kt    TIMEOUT_MS 분리 · 값 조정
test/smoke.ts                       스캐너 3건
```

**서버 무변경이 기본이다** — 서버 값을 옮기는 쪽을 고르면 그 근거를 보고에 적는다.
**마이그레이션 없다.** `ai_used`·`ai_verdict`·`ai_unavailable_reason` 칼럼은 그대로다
(0016의 CHECK에 `server_timeout`이 이미 있다 — 확인하고 쓴다).

## 금지

| 하지 말 것 | 왜 |
|---|---|
| fail-closed를 뒤집기 | ADR-024다. **원인이 진단 오류였는데 원칙을 바꾸는 것은 순서가 틀렸다** |
| 재시도 붙이기 | 새벽에 두 배 깨운다. 마찰은 Guard의 도구이지 버그 회피 수단이 아니다 |
| 사전 판정 캐시 | ADR-038 §기각한 대안 3행. 판정 재료가 발동 시점의 것이 아니게 된다 |
| 숫자를 ADR·CLAUDE.md에 적기 | 코드와 두 벌이 된다(§기준선 보고 규칙) |
| `connect`와 `read`를 한 상수로 두기 | 뜻이 다르다. 한쪽을 고칠 때 다른 쪽이 딸려 간다 |
| `ai_used` 기록 경로 손대기 | **그 값은 정상이다** — 8/11의 `deny` 둘이 `ai_used=1`로 남아 있다. 판정을 못 받았을 때의 0은 맞는 기록이다 |
| `approve`가 0인 것을 여기서 다루기 | 별건이다(T-38). **원인이 다르고 고치는 자리도 다르다** |

**변이 — 이 티켓의 짝**

| 변이 | 기대 |
|---|---|
| 기기 값을 서버보다 작게 되돌린다 | ①이 죽는다 |
| 스캐너를 눈멀게 한다 | **①은 초록으로 남고 ★만 죽는다** ← 이게 핵심이다 |
| 서버 상수 이름을 바꾼다 | ③이 "못 찾았다"로 죽는다 |

## 확인 절차 (사용자) — APK 설치 후, 밤에

```
□ 낮에 testNotify({level:4}) 로 한 번   → ai_verdict 가 approve 인가
□ ai_used 가 1로 기록되는가             ← 상한이 이제 오른다
□ 두 번 더 불러 상한이 실제로 걸리는가   ← coach 의 cap 은 5
```

⚠️ **밤 실측 전날 낮에는 하지 않는다** — 상한이 이제 진짜로 오르므로 그 밤의 예산을 태운다.
귀속일 경계가 06:00이라 **01:30~05:00은 전날 낮과 같은 날**이다.
