# T-52 — 캘린더가 보낼 곳을 만든다

**발행** Cowork · 2026-08-28 · **담당** Claude Code · **보통**
**근거** [ADR-029](../../APP-ADR.md#adr-029) · `APP-PLAN` §Phase 7 · **마이그레이션 하나 · 서버 · APK 무관**

---

## 무엇을 만드나

**기기가 읽어 보낼 자리.** 화면에는 아직 아무것도 안 보인다 — **그건 T-53이다.**

```
POST /api/cal/sync   →  멱등 upsert. 기기가 창 범위를 통째로 보낸다
```

⚠️ **이 티켓만으로는 사용자가 아무것도 못 본다.** 둘을 연달아 돌린다.

## 왜 이것부터인가

**"앱을 열어도 볼 게 없다"가 지금의 병목이다.** 8/19~22 나흘 연속 `daily` 없음·`logs 0`,
오늘 할 일 하나. **위젯 셋으로 도착은 쉬워졌는데 도착지가 비어 있다.**

**넣지 않아도 채워지는 유일한 길이 외부 일정이고**, ADR-028이 *"입력의 무게중심을 시스템으로"*라
적은 자리가 여기다.

## 할 일

### ① 마이그레이션 — ADR-029가 이미 적어 둔 그대로

```sql
ALTER TABLE events ADD COLUMN ext_src TEXT;      -- 'devcal' | NULL(앱 생성)
ALTER TABLE events ADD COLUMN ext_uid TEXT;      -- 반복은 '<id>:<날짜>'
ALTER TABLE events ADD COLUMN ext_updated TEXT;  -- LWW 기준
CREATE UNIQUE INDEX idx_events_ext
  ON events(ext_src, ext_uid) WHERE ext_src IS NOT NULL;
```

⚠️ **`test/smoke.ts`의 스키마 목록에 파일명을 넣는다.**

### ② `POST /api/cal/sync` — 멱등 upsert

기기가 **창 범위의 일정 전부**를 한 번에 보낸다. 서버는 그것을 `events`에 맞춘다.

```
입력   { items: [{ ext_uid, title, date, time?, all_day?, ext_updated }], window: { from, to } }
출력   { upserted, skipped_closed, skipped_stale, deleted, protected_kept }
```

⚠️ **응답이 "무엇을 안 했는지"를 세어 돌려준다.** T-43이 `last_seen_count`로 세운 자리와 같다 —
**0건과 실패가 구별되지 않으면 다음에 조용히 깨진다.**

### ③ ★ 마감된 날은 건너뛴다 — 실패가 아니라 결정이다

**마감된 날에는 `events` 추가가 막히지 않는다**(함정 6 — `events`엔 `_ins` 트리거가 없다).
**하지만 ADR-029는 마감된 날을 동기화에서 영구 이탈시킨다:**

> 열린 날은 캘린더와 공유하는 현재, 마감된 날은 personal-os만의 과거

```
마감된 날의 항목  →  건너뛴다 · skipped_closed 를 센다
```

⚠️ **트리거에 걸려서 건너뛰는 게 아니라, 서버가 먼저 판단해서 건너뛴다.**
DB가 안 막아 주므로 **여기가 유일한 방어선**이다 — 안 막으면 지난 날이 캘린더로 덮인다.

### ④ ★ 삭제 — 유령을 남기지 않되 이력은 지킨다

캘린더에서 지운 일정이 앱에 남으면 **화면이 거짓말을 한다.**

```
창 안 · devcal 소스 · 이번에 안 온 것  →  지운다
그 중 guard 이력이 참조하는 것         →  지우지 않고 protect 해제 + 보존
```

⚠️ **`ext_src IS NULL`(앱이 만든 일정)은 절대 안 지운다.** 창 범위 안이어도 마찬가지다 —
**동기화가 사용자의 것을 지우면 신뢰가 끝난다.**

### ⑤ LWW — 구갱신은 무시

`ext_updated`가 저장된 것보다 **오래됐으면** 무시하고 `skipped_stale`을 센다.
해소 UI는 없다(ADR-029).

5  창 안에서 안 온 devcal 일정은 지워진다

**5와 7이 짝이다.** 5만 보면 *"창 안의 것을 전부 지우는 구현"*이 통과하고,
**그것은 사용자가 앱에서 만든 일정을 동기화가 삭제하는 모양이다.**
T-33·T-38·T-39·T-41·T-43·T-44·T-45·T-46·T-47·T-49에서 **열 번** 물린 자리의 가장 비싼 판이다.

**2와 3도 짝이다.** 2만 보면 *"조용히 건너뛰는 구현"*이 통과한다 — 그러면
**동기화가 절반만 도는 밤에 아무도 모른다.**

**변이**
- 마감 판정을 뺀다 → **2만** 죽는다
- `skipped_closed` 를 안 센다 → **3만** 죽는다
- 삭제에서 `ext_src` 조건을 뺀다 → **7만** 죽는다
- LWW 비교를 뒤집는다 → **4만** 죽는다
- guard 참조 확인을 뺀다 → **6만** 죽는다
- 반복 인스턴스를 id 로만 키잉한다 → **8만** 죽는다

### 마감된 날을 어디서 막았나 — DB 가 아니라 서버라는 것을 어떻게 보장했나

**`services/calsync.ts`가 요청 시작에 그 창의 마감된 날 집합을 한 번 읽고, 항목마다 먼저 판단한다.**

```ts
const closed = new Set((await db.closedDaysIn(env, from, to)).results.map(r => r.date));
...
if (closed.has(it.date)) { skippedClosed++; continue; }   // 새 항목
if (closed.has(cur.date)) { skippedClosed++; continue; }  // 옛 자리가 마감된 날 — 옮겨 오지 않는다
if (closed.has(row.date)) { skippedClosed++; continue; }  // 삭제 후보
```

**보장은 검사가 진다.** ②는 **행 수로만** 판정한다 — `WHERE date = D` 인 devcal 행이 0인가.
트리거가 막아 준다면 이 검사는 트리거를 지우는 순간 함께 죽었을 텐데, `events`엔 `_ins` 트리거가
**애초에 없다**(함정 6). 그래서 변이 A(마감 판정 제거)가 곧바로 ②를 죽인다 — **서버가 유일한
방어선이라는 것이 그 한 줄로 증명된다.**

⚠️ **세 자리 중 뒤의 둘은 트리거와 겹친다.** `trg_events_frozen_upd`·`_del`이 UPDATE·DELETE는
막는다 — 다만 그건 **409로 배치를 통째로 깨는 모양**이라, 서버가 먼저 걸러야 동기화가
*"절반만 돌고 나머지를 잃는"* 밤이 안 생긴다. 트리거는 마지막 방벽으로 그대로 둔다.

### 삭제의 `ext_src` 조건을 어디에 뒀나 — ★ `if` 가 아니라 **후보를 고르는 SQL**

```sql
-- db.extEventsInWindow
SELECT id, ext_uid, date, protect_from FROM events
WHERE ext_src = ? AND date BETWEEN ? AND ?
```

**앱이 만든 일정은 후보 집합에 아예 안 들어온다.** 서비스 쪽 `if`로 뒀으면 그 한 줄을 지우는
순간 사용자의 일정이 지워진다 — **동기화가 사용자의 것을 삭제하면 신뢰가 끝난다.**

**검사 ⑦은 진짜 앱 일정을 만든다**: `POST /api/events`로 `N1`(창 안, 열린 날)에 하나 만들고,
그 날짜를 포함한 동기화를 **그 일정 없이** 돌린 뒤 `ext_src IS NULL`인 채 살아 있는지 본다.
(가짜 행을 raw로 넣지 않는다 — 실제 생성 경로가 `ext_src`를 안 채우는지까지 함께 세야 한다.)

### 응답의 `skipped_*` 가 실제 수와 맞는 것을 어떻게 쟀나

**②와 ③을 행위와 보고로 갈랐다.**

```
②  행 수만 본다        마감된 날의 devcal 행이 0인가
③  보고만 본다        skipped_closed == (보낸 것 중 마감된 날이면서 실제로 안 들어간 수)
```

③을 *"skipped_closed === 2"* 로 쓰면 **마감 판정이 사라졌을 때 ②와 함께 죽는다** — 두 결함이
같은 한 줄을 죽여 어느 쪽인지 못 읽는다. **양변이 함께 0으로 내려가는 형태**로 쓰면
판정이 사라져도 ③은 성립한 채 ②만 죽고, 세는 것만 빠지면 ③만 죽는다. 변이 A·B가 그것을 보였다.

### 변이 여섯 — 다섯은 하나씩, **C 하나가 일곱을 죽였다**

**기준선 385.**

| 변이 | 통과 | 죽은 검사 |
|---|---|---|
| A 마감 판정을 뺀다 | 384 | ② |
| B `skipped_closed`를 안 센다 | 384 | ③ |
| **C 삭제 후보에서 `ext_src` 조건을 뺀다** | **378** | **①②③④⑥⑦⑧ (일곱)** |
| D LWW 비교를 뒤집는다 | 384 | ④ |
| E guard 참조 확인을 뺀다 | 384 | ⑥ |
| F 반복 인스턴스를 id 로만 키잉한다 | 384 | ⑧ |

**★ C가 일곱을 죽인 것은 검사가 약해서가 아니라 방벽이 SQL에 있어서다.**
조건을 빼면 삭제 후보가 **창 안의 모든 일정**이 되고, 그 중에는 앞 절들이 만들어 둔
**`guard_events`가 참조하는 일정**이 있다. FK 때문에 그 DELETE가 터져 `/api/cal/sync`가
**첫 왕복부터 500**이 되고, 그 뒤 검사가 줄줄이 넘어간다.

**티켓은 *"⑦만 죽는다"* 를 예상했지만, 그것은 조건이 서비스의 `if`에 있을 때의 모양이다.**
지금 구조에서는 그 결함이 **조용할 수 없다** — 첫 동기화에서 터진다. ⑦은 물론 죽었고,
**"사용자의 일정이 조용히 지워지는" 경로가 애초에 없다**는 것이 이 배치의 결론이다.
검사를 그 모양에 맞춰 약하게 고치지 않았다.

### ⚠️ 함정 12의 스캐너가 나를 잡았다

처음에 LWW 기준으로 `ext_updated: "2026-08-28T01:00:00Z"` 같은 **고정 문자열**을 썼고,
smoke의 *"fixture에 고정 날짜가 없다"* 검사가 그것을 잡았다(385가 아니라 384·실패 1).

`ext_updated`는 서버 시계와 만나지 않고 자기들끼리만 비교되므로 **뜻으로는 위험하지 않다.**
그래도 **스캐너를 고치지 않고 값을 상대로 바꿨다**(`${D}T01:00:00Z` · `${addDays(D,-30)}…`).
*"언젠가 반드시 현재가 된다"* 에 예외를 만들기 시작하면, 다음 사람이 그 예외를 근거로
진짜 위험한 고정 날짜를 넣는다. **예외를 안 만드는 것이 그 규칙의 값이다.**
