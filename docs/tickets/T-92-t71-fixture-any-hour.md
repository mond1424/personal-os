## 목표

smoke의 T-71 검사 2 · 7이 **돌리는 시각과 상관없이** 같은 판정을 낸다.
왜: `t71Slot`은 그날 가장 이른 일정보다 한 시간 이르게 잡되 01:00 밑으로 내려가지 않는다. 귀속일 경계 전 00시대에 돌리면
T-71 일정의 날짜(`D + 21`)가 T-80 마감(`now + 20일`)과 같은 날이 되고, 마감이 00시대라 T-71 일정이 그날 가장 이른 약속이 못 된다.
그러면 `wakePoints`는 맞게 마감을 고르고, 검사는 `간격=NaN`으로 실패한다 — **구현이 아니라 픽스처의 전제가 깨진 것이다.**

### 구현과 범위

- `t71Slot`은 요청한 날의 수업·일정을 `GET /api/days/:date`로 읽는다. 01:00보다 이르게 만들지 않는
  기존 시각 규칙으로 가장 이른 약속이 될 수 없으면 다음 날을 다시 읽는다. 탐색은 귀속일 `D + 29`에서
  끝나며, 기본 schedule 조회 창 밖으로 조용히 밀리지 않도록 전제 검사도 날짜 상한을 확인한다.
- 값이 붙은 보호 일정 → 선언만 한 보호 일정 → 일반 일정을 **실제로 선택된 날짜의 다음 날부터** 만든다.
  날짜가 이동해도 세 일정이 같은 날에 섞이지 않는다. T-80 픽스처는 그대로다.
- 새 검사는 세 일정에 하나씩, **+3**이다. 생성 후 날짜 응답을 다시 읽어 자기 `id`의 존재·시각과
  다른 일정·수업의 `HH:MM`을 직접 견준다. 선택 함수의 분 계산이나 `wake` 결과를 정답으로 쓰지 않는다.
  먼저 또는 같은 시각의 약속이 있거나 조회 창을 벗어나면 날짜·시각과 함께 **`전제 깨짐`**을 출력한다.
- API 구조·마이그레이션은 바뀌지 않아 api-surface 재생성과 schema 재덤프는 해당하지 않는다.
  `src/`·`public/`·`android/`·`migrations/`·`package.json`의 diff가 없음을 확인했다.

### 주입 시각 대조 — 시스템 시계 변경 없음

일회용 확인 스크립트는 `test/smoke.ts`에서 T-71 절의 시작 주석부터 T-84 시작 주석 앞까지를
CR을 걷어 추출했다. **픽스처와 기존 검사 1~7(2b 포함)을 복제해 다시 짜지 않고, 그 절 자체를 실행했다.**
각 시각마다 26개 마이그레이션을 적용한 별도 인메모리 D1을 만들고
`loadTime(env, Date.parse('2026-10-07T<시각>:00+09:00'))`의 컨텍스트를 주입했다.

입력은 `now + 20일`의 T-80 마감 일정과 매일 09:00 수업이다. 확인용 `api`는 실제
`events.create/setProtect`, `daily.assembleDay`, `guard.schedule`을 같은 주입 컨텍스트로 호출했다.
HTTP 미들웨어까지 태우는 전체 smoke 결과와 이 최소 재현의 숫자는 따로 센다.

| 상태 / 주입 시각(KST) | 귀속일 D | T-80 마감 | T-71의 세 날짜 | 선택 / 간격 | 통과 · 실패 / exit |
|---|---|---|---|---|---|
| 수정 전 00:30 | 10-06 | 10-27 00:30 | 10-27 · 10-28 · 10-29 | T-80 / leaveBy 없음 | 6 · 2 / 1 |
| 수정 후 00:30 | 10-06 | 10-27 00:30 | 10-28 · 10-29 · 10-30 | T-71 / 95분 | 11 · 0 / 0 |
| 수정 후 02:30 | 10-06 | 10-27 02:30 | 10-27 · 10-28 · 10-29 | T-71 / 95분 | 11 · 0 / 0 |
| 수정 후 05:59 | 10-07 | 10-27 05:59 | 10-28 · 10-29 · 10-30 | T-71 / 95분 | 11 · 0 / 0 |
| 수정 후 12:30 | 10-07 | 10-27 12:30 | 10-28 · 10-29 · 10-30 | T-71 / 95분 | 11 · 0 / 0 |

수정 전 실패 원출력은 T-90과 같았다.

```text
2 ★ protect_prep_min 이 붙은 칸에도 실린다 — 간격=NaN(기대 95) 설정합=60
7 ★ 예약이 전제하는 기상과 문구가 말할 기상이 같다 — 선언만=true 값붙음=false 갈린칸=없음
```

**전제 검사의 빨간불 대조:** 추출본의 `Math.max(60, first - 60)` 한 곳을 `first + 60`으로 바꿨다.
앵커가 정확히 한 곳임을 먼저 단언했고, 원본 파일은 바꾸지 않았다. 00:30에서
**총계 11 유지 · 통과 3 · 실패 8 · exit 1**이었다. 예상한 새 전제 검사 셋과 기존 검사 2·2b·3·4·7이
실패했고, 전제 셋 모두 `전제 깨짐`을 출력했다. 탐색 종료와 조회 창 상한의 실패도 요약을 잃지 않았다.
일회용 스크립트는 확인 후 제거했다.


- **범위와 설계:** 커밋의 코드 변경은 `test/smoke.ts` T-71 픽스처뿐이다. T-80과 기존 검사 1~7(2b 포함)의
  판정식은 그대로다. ADR-047의 일정값 → 설정 → 상수 순서와 보호 선언에 따른 기상 시각 제공 규칙을
  바꾸지 않고, 그 규칙을 검사할 표본의 전제만 복구했다.
- **날짜 선택:** 하루 조회는 `assembleDay`의 일정·수업을 모두 읽으며, `wakePoints`도 같은 일정 원장과
  수업 전개를 사용한다. 01:00 이상에서 앞설 수 없는 날은 건너뛰고, 다음 픽스처는 실제 선택일의 다음 날부터
  찾으므로 세 종류가 한 날에 섞이지 않는다. `D + 29`는 기본 schedule 조회 범위 안이다. 끝에서 자리를
  못 찾거나 후속 픽스처가 범위를 넘으면 전제 검사가 실패하므로, 탐색이 무한히 돌거나 창 밖을 성공으로 세지 않는다.
- **새 검사 +3의 의미:** 각 일정의 생성 후 자기 id·시각을 확인하고, 다른 일정·수업과 `HH:MM`을 직접 비교한다.
  선택 함수의 분 계산이나 `wake`의 선택 결과를 정답으로 재사용하지 않는다. 같은 시각도 실패시켜 단독으로
  가장 이른 약속이라는 전제를 지킨다. 감독층의 `first + 60` 변이 보고는 전제 셋과 그 전제를 잃은 기존 검사
  다섯이 함께 실패하고 총계 11을 유지했다. 이는 서로 다른 기능의 혼동이 아니라 표본 전제 파괴의 결과다.
- **완료 조건:** 감독층 보고에서 수정 전 00:30은 기존 8건 중 6 통과·2 실패, 수정 후 네 시각은 각각
  11 통과·0 실패다. 실제 시계의 전체 verify는 typecheck 통과·smoke **534 → 537**·front **526 → 526**·
  실패 0·exit 0이다. 주입 대조는 T-71 절을 추출한 최소 재현이며, 네 시각에 전체 smoke를 돌렸다는 뜻으로 읽지 않는다.

**채택:** 기존 01:00 하한과 엄격한 기대값을 유지하면서 가능한 날짜를 고르는 구현.
**기각:** 서버 선택 규칙 변경·T-80 이동·검사 2·7 완화 — 올바른 제품 동작이나 다른 검사의 전제를 건드려 원인을 숨긴다.

감독층 후속은 이 검토와 상태 변경의 커밋, `STATE.md`의 T-92 검토 대기 표시 정리다.
