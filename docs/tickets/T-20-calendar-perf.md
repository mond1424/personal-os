# T-20 — 캘린더 전환이 끊긴다

**발행** Cowork · 2026-08-05 · **담당** Codex CLI · **상태** ⬜ 대기

---

## 실측

기기에서 잰 값(하네스):

```
Api.calendar 3달치 왕복   990ms  (콜드)
renderCalendar 전체       526ms  (웜 왕복 + DOM 조립)
```

**대부분이 네트워크다.** DOM 조립은 그 나머지다.

## 무엇이 낭비인가

`renderCalendar()`는 달을 넘길 때마다 **가진 데이터를 다시 받는다.**

```
8월 보는 중 → 7·8·9월 요청
9월로 넘김  → 8·9·10월 요청     ← 8·9는 손에 있다
```

3-pane 프리렌더 자체는 옳다(주석: *"다음 달이 이미 거기 있어야 끊기지 않기 때문"*).
문제는 **넘긴 뒤 새 3-pane을 조립할 때 범위를 통째로 다시 요청**하는 것이다.

**범위만 넓히면 더 느려진다.** 5달로 늘려도 매번 5달치를 다시 받으면 응답만 커진다.
**캐시가 먼저고, 범위 확장은 그 위에서만 의미가 있다.**

---

## 1부 — 달 단위 캐시

```
받은 달을 메모리에 쌓는다 → 없는 달만 요청한다
```

- 캐시 키는 **달**(`2026-08`)이다. 날짜 범위가 아니다 —
  범위로 잡으면 겹침 계산이 붙고 그 계산이 새 버그 자리가 된다
- 요청은 **빠진 구간만**. 전부 있으면 요청이 나가지 않는다
- 서버·API를 건드리지 않는다. `Api.calendar`는 이미 범위 쿼리다

### 캐시를 언제 버리나 — **이 티켓의 덫**

**쓰기가 일어나면 캐시 전체를 버린다.**

일정 추가·수정·삭제, 할 일 미루기, 마감 — 무엇이든 쓰기 뒤에는 비운다.
"바뀐 달만 골라 버리기"는 하지 않는다. 한 곳이라도 빠뜨리면 **화면이 조용히 옛 데이터를 보여주고,
그 실패는 아무 오류도 내지 않는다.** 쓰기는 자주 없으므로 전체를 버려도 비용이 없다.

기간(`periods`)도 같이 버린다 — 같은 응답 묶음에서 온다.

---

## 2부 — 범위를 5달로

캐시가 선 뒤에 넓힌다.

```
지금  이전 · 현재 · 다음        3달
바꿈  ±2달                      5달
```

한 번 받아두면 **좌우로 두 번씩은 요청 없이 넘어간다.**
`WEEKS_IN_GRID`(6주 고정)는 건드리지 않는다 — 캐러셀 높이의 전제다(함정 11).

**DOM을 5개 유지하지 않는다.** 이번엔 데이터만 넓힌다.
조립 시간이 여전히 문제인지는 **캐시 뒤에 다시 재서** 판단한다.

## 3부 — 스와이프 직후 터치 차단

```
dragBlockUntil = Date.now() + 200    →    + 60
```

`app.js:2463`. A-4에서 "터치 씹힘 완화"로 넣은 값이고, 실사용에서 과하다는 판단이다.

**지우지 않는다.** 0으로 만들면 A-4가 막으려던 증상이 돌아온다.
`AXIS_LOCK`·`FLICK_V`는 건드리지 않는다 — 함정 2·4.


**서버를 건드리지 않는다.** `Api.calendar`는 그대로다.

## 금지

| 하지 말 것 | 왜 |
|---|---|
| 캐시를 달이 아니라 날짜 범위로 | 겹침 계산이 붙고 그것이 새 버그 자리가 된다 |
| 쓰기 뒤 "바뀐 달만" 무효화 | 하나 빠뜨리면 조용히 옛 데이터를 보여준다 |
| 캐시를 `localStorage`·`sessionStorage`에 | 메모리만. 앱을 다시 열면 새로 받는 편이 안전하다 |
| 캐시 없이 범위만 5달로 | 매번 더 큰 응답을 다시 받는다. 더 느려진다 |
| `WEEKS_IN_GRID` 변경 | 6주 고정이 캐러셀 높이의 전제다 — 함정 11 |
| `dragBlockUntil`을 0으로 | A-4가 막던 터치 씹힘이 돌아온다 |
| `AXIS_LOCK`·`FLICK_V` 수정 | 함정 2·4. 이 티켓은 데이터와 값 하나다 |
| `calGen` 세대 관리 제거 | 연속 스와이프 경합을 막는다. 캐시가 있어도 필요하다 |

- `public/app.js` 2419·2463·2538 — `dragBlockUntil`
- `CLAUDE.md` 함정 2·4·11

## 완료 조건

```
typecheck 통과 · smoke 268(변화 없음) · front 229 → 234 이상 · 실패 0
```

검사:

1. 같은 달을 다시 그리면 **요청이 나가지 않는다**
2. 옆 달로 넘기면 **캐시에 있는 만큼은 요청이 줄어든다**
3. **일정을 추가하면 캐시가 비워지고 다음 렌더가 새로 받는다**
4. 할 일을 미루면 캐시가 비워진다
5. `dragBlockUntil`이 60이다

**3·4번이 이 티켓의 덫이다.** 캐시만 넣고 무효화를 빠뜨리면 1·2·5는 통과하고,
**화면이 옛 데이터를 보여주는 것은 검사에 안 잡힌다.**
쓰기 경로를 하나씩 태워서 캐시가 실제로 비는지 본다.

## 확인 절차 (사용자)

deploy 후. APK 재빌드 불필요.

```
□ 달을 좌우로 넘길 때 끊김이 줄었다
□ 두 번째로 같은 달에 가면 즉시 나온다
□ 일정을 추가하고 옆 달 갔다 오면 그 일정이 보인다   ← 캐시 무효화
□ 스와이프 직후 탭이 덜 씹힌다
```

세 번째가 실측의 핵심이다. **여기서 안 보이면 캐시가 오래된 것이다.**

## 재측정 (완료 후)

캐시가 선 뒤에 같은 자리를 다시 잰다:

```cmd
node test/device.mjs "(async()=>{const b=performance.now();await renderCalendar();return Math.round(performance.now()-b)})()"
```

**요청이 안 나가는 상태의 값이 DOM 조립 시간이다.** 그 값이 여전히 크면
DOM 프리렌더를 다음 티켓으로 낸다. 작으면 이 항목은 닫는다.
