# T-35 — 세 번 밀린 일에 출구를 준다

**발행** Cowork · 2026-08-11 · **담당** Claude Code · **웹 중심 — APK와 무관하다**
**상태** 🔴 **멈춤 — 갈림길에서 보고 (2026-08-14)** · **경로가 없다** ·
**한 라우트가 아니라 "대기"의 정의가 걸린다 → ADR급, Cowork 판단 대기**
코드는 한 줄도 안 썼다. §보고 ★를 먼저 읽는다.

---

## 무엇이 문제인가

`BACKLOG-0806` 6번. **같은 일이 계속 미뤄지는데 앱이 아무 말도 안 한다.**

`defer_count`는 이미 조회 시 계산되어 Today 목록에 실려 온다(`db/index.ts:40`) —
**데이터는 있고 쓰는 곳이 없다.**

## 알림이 목적이 아니다 — 출구가 목적이다

*"이거 세 번 미뤘어요"*만 말하면 소용없다. **사용자가 이미 안다.**
그건 잔소리이고, §6.3이 경고한 도구 이탈로 가는 길이다.

**세 번 미뤘다는 것은 "날짜를 정할 준비가 안 됐다"는 뜻이다.**
그리고 이 앱에는 그 상태의 정확한 이름이 이미 있다 — **대기**다.

```
계속 날짜를 붙였다 미뤘다 한다     ← 지금
날짜를 떼고 대기로 돌린다          ← 그 상태의 정확한 이름
```

ADR-035가 *"적어두고 자자"*를 정당한 형태로 인정한 것과 **같은 논리**다.
막힌 것을 억지로 오늘에 붙여 두는 것보다, **날짜가 없다고 인정하는 편이 정직하다.**

## ★ 먼저 확인한다 — 대기로 되돌리는 경로가 있는가

**`api.js`에 날짜를 붙이는 `schedule`은 있는데 떼는 것이 안 보인다.**
있으면 그대로 쓰고, **없으면 그 사실 자체가 이 티켓의 첫 발견이다** —
*"세 번 미룬 일을 대기로 돌릴 방법이 없다"*는 것이고, 그러면 이 티켓은 **둘로 갈린다**:

```
경로가 있다   → 팝업만. 웹뿐이고 작다
경로가 없다   → 서버 라우트가 먼저다. 여기서 멈추고 보고한다
```

**추측해서 만들지 않는다.** 확인하고 갈림길에서 보고한다.

## 조건 — 셋 다 필요하다

```
① defer_count ≥ N        상수 하나. 실사용으로 조정한다
② 하루 한 번             귀속일 기준. 오늘 이미 보여줬으면 안 띄운다
③ 가장 많이 밀린 하나만  동점이면 id가 이른 것
```

**셋이 다 없으면 잔소리가 된다.** outcome 카드가 *"여러 개를 늘어놓으면 대충 눌러 치우게
되고, 그렇게 들어온 것은 없는 것보다 나쁘다"*(`app.js:452`)고 적어 둔 그 병이다.

**N은 실측이 정한다.** `SWIPE_EDGE_RATIO`처럼 **한 자리에 상수로** 둔다 —
한 번은 흔하고 두 번도 있을 수 있으니 3에서 시작하되, 잦으면 올리고 안 뜨면 내린다.

**②를 어디에 남기나**: `localStorage`에 귀속일 하나. 기기가 바뀌면 초기화되지만
**하루짜리 상태라 그것이 맞다.** 서버에 두면 마이그레이션이 생기고, 그건 이 값에 과하다.
`api_token`이 이미 거기 있으므로 새 저장소가 아니다.

## 선택지는 셋

```
오늘 한다      아무것도 안 바꾼다. 닫기만
대기로 보낸다  날짜를 뗀다 — 이 티켓의 요점
나중에         닫는다. 오늘은 다시 안 뜬다
```

**넷째를 만들지 않는다.** 취소는 이미 다른 경로에 있고, 여기에 넣으면 선택지가 넷이 되어
"대충 치우기"가 시작된다.

## 범위

```
public/app.js      조건 판정 · 팝업 · 선택지 셋
public/index.html  팝업 자리 (기존 시트 패턴 재사용)
public/style.css   필요하면 — 색은 CSS 변수만, 다크 짝 필수 (함정 5)
test/front.mjs     검사
```

**서버는 확인 결과에 따른다** — 경로가 있으면 무변경, 없으면 멈추고 보고.
**마이그레이션 없다** — 확인하고 적는다(§5).

## 금지

| 하지 말 것 | 왜 |
|---|---|
| 조건 셋 중 하나라도 빼기 | 잔소리가 된다. 셋이 함께 좁힌다 |
| 선택지를 넷 이상 | "대충 치우기"가 시작된다 — `app.js:452` |
| `defer_count`를 저장 | 조회 시 계산이다. 파생을 물화하지 않는다(원칙 1) |
| 여러 개를 한 번에 보이기 | 가장 많이 밀린 **하나**다 |
| N을 여러 곳에 흩기 | 실사용으로 조정할 값이다. 한 자리 |
| 대기 경로를 추측해서 만들기 | 확인하고 갈림길에서 보고한다 |
| 색 리터럴 | CSS 변수만 · 다크 짝 — 함정 5 |
| `scrollIntoView` | 함정 1 |

## 완료 조건

```
typecheck 통과 · smoke 303(변화 없음, 서버 무변경일 때) · front 283 → 288 이상 · 실패 0
```

검사:

1. `defer_count`가 N 미만이면 **안 뜬다**
2. N 이상이면 **뜬다** ← 1과 짝
3. 오늘 이미 봤으면 **안 뜬다** · 날짜가 바뀌면 다시 뜬다 ← 짝
4. 둘 이상이 조건을 넘으면 **가장 많이 밀린 하나만**
5. "대기로 보낸다"가 실제로 날짜를 뗀다 — 목록에서 사라지고 대기에 나타난다

**1·2가 짝이고 3도 짝이다.** 한쪽만 보면 *"항상 안 뜬다"*가 통과한다 —
그리고 이 기능은 **안 뜨는 것이 기본 상태**라 그 실수가 특히 조용하다.

### ★ 대기로 되돌리는 경로가 있었나 (확인 결과)

**없다. 그리고 라우트 하나를 더하면 되는 문제가 아니다** — 세 겹이다.

#### ① 라우트가 없다 (전수)

`src/index.ts:122~153`의 task 라우트 **열둘을 다 봤다.** 날짜를 **붙이는** 것은 있고 **떼는** 것은 없다.

```
POST /tasks/:id/schedule   date 하나를 붙인다        (:136)
POST /tasks/:id/defer      날짜→날짜로 옮긴다        (:132)
POST /tasks/:id/cancel     열린 예정을 비우고 취소    (:144)
DELETE /tasks/:id          task 자체를 지운다        (:150)
```

`public/api.js`도 같다(`:47` defer · `:48` schedule). 예정을 지우는 SQL은 둘뿐이고
(`db/index.ts:444` `stDeleteEntries` · `:451` `stDeleteOpenEntries`) **호출부가 둘뿐이다** —
`services/tasks.ts:230`(삭제) · `:175`(취소). **어느 쪽도 "대기로 되돌리기"가 아니다.**

**`scheduleTask`가 이 비대칭을 글자로 적어 뒀다**(`services/tasks.ts:117`):

```ts
if (!stats.is_waiting)
  throw new ApiError(409, "이미 예정이 있는 task예요 — 이동은 미루기(defer)로");
```

상태 그래프에 **되돌아오는 간선이 없다**: 대기→예정은 `schedule`, 예정→예정은 `defer`,
예정→끝은 `complete`·`cancel`·`delete`. **예정→대기는 아무 데도 없다.**

#### ② "대기"의 정의가 **예정이 하나도 없음**이다 — 세 번 미룬 일은 정의상 될 수 없다

`v_task_stats`(`migrations/0008_cancel_task.sql:37`):

```sql
CASE WHEN t.status = 'not_finished' AND t.cancelled_at IS NULL
      AND NOT EXISTS (SELECT 1 FROM schedule_entries e WHERE e.task_id = t.id)
     THEN 1 ELSE 0 END AS is_waiting
```

`NOT EXISTS` — **열린 것만이 아니라 하나도 없어야 한다.** 그런데 같은 뷰에서

```sql
MAX((SELECT COUNT(*) FROM schedule_entries e WHERE e.task_id = t.id) - 1, 0) AS defer_count
```

**`defer_count`가 바로 그 항목들의 개수다.** ⇒ `defer_count ≥ 3`은 항목이 **넷 이상**이라는 뜻이고,
대기로 만들려면 **그 넷을 다 지워야** 한다. 지우면 `defer_count`가 **0이 된다** —
**팝업을 띄운 조건 자체가 증발한다.** 되돌린 일은 *"세 번 미뤘던 일"*이 아니라
*"한 번도 안 잡힌 일"*로 남는다. 9~11월이 읽을 신호를 지우면서 출구를 주는 셈이다.

그 항목들은 **Missed 기록 그 자체다** — `services/tasks.ts:132`가 적어 둔 대로
*"deferred_to 없는 채로 남는 것이 곧 Missed 기록의 보존이다(1.2)"*.

#### ③ 게다가 대부분 **지울 수 없다** — 트리거가 막는다

`migrations/0001_init.sql:304`:

```sql
CREATE TRIGGER trg_entries_frozen_del BEFORE DELETE ON schedule_entries
WHEN (SELECT status FROM daily WHERE date = OLD.date) = 'closed'
BEGIN SELECT RAISE(ABORT, '마감된 날의 schedule 항목은 삭제할 수 없음'); END;
```

**세 번 미뤘다는 것은 그 날들이 지나 마감됐다는 뜻이다** — 즉 지워야 할 항목이 정확히
**얼어 있는 항목**이다(함정 6). 열린 것만 지우면(`stDeleteOpenEntries`) 과거 항목이 남아
**`is_waiting`은 여전히 0** — 목록에서 사라지지도, 대기에 나타나지도 않는다.
**티켓 §완료 조건 5번이 통과할 수 있는 구현이 지금 스키마에 없다.**

#### ④ 되돌린다면 21일 시계를 어디에 두나 — 이것도 결정이다

`wait_anchor_at`은 **생성 시각**이고 바뀌는 것은 연장뿐이다(`0001_init.sql:81`).

| 선택 | 대가 |
|---|---|
| 앵커를 그대로 둔다 | 7월에 만든 일이 **"대기 45일째"**로 들어간다. `WAIT_LIMIT = 21`(`app.js:29`)을 즉시 넘어 경고색이고, 대기 목록 정렬(`wait_anchor_at` ASC)에서 맨 위다 |
| 앵커를 되돌린 시점으로 옮긴다 | `trg_wait_ext_log`(`:102`)가 `wait_extensions`에 행을 남긴다 — **연장한 적이 없는데 연장 이력이 생긴다** |

**둘 다 공짜가 아니다.** 이 선택은 §6.4 대기 시계의 뜻을 정하는 일이라 여기서 정하지 않는다.

### 왜 여기서 멈추는가

티켓은 *"경로가 없다 → 서버 라우트가 먼저다. 여기서 멈추고 보고한다"*라고 했다.
**확인해 보니 서버 라우트보다 앞이다** — `is_waiting`의 정의를 건드리거나, 대기를 셋째 상태로
새로 만들어야 한다. **기각한 대안이 남아야 하는 결정**이고, `AGENT-CHAIN.md` §7의
*"ADR급 결정이 필요하다"*에 정확히 해당한다. **추측해서 만들지 않는다**(§금지 여섯째).

### 갈래 셋 — 고르는 것은 Cowork다

```
A  is_waiting 정의를 "열린 예정이 없다"로 바꾼다   뷰만. 마이그레이션 하나
B  대기를 셋째 상태로 명시한다 (tasks에 칼럼)      마이그레이션 + 서비스
C  팝업의 셋째 선택지를 '대기로'가 아닌 것으로     서버 무변경. 티켓의 요점이 바뀐다
```

- **A** — 값이 싸지만 **뜻이 조용히 바뀐다.** 과거 데이터의 `is_waiting`이 소급해서 달라지고
  (한 번이라도 잡혔다 끝난 일이 대기로 보이기 시작한다) `waitingList`·21일 시계·`analysis`의
  대기 나이가 전부 그 뷰를 읽는다. **파생의 뜻을 바꾸는 것이 가장 넓게 샌다.**
- **B** — `defer_count`도 항목도 **그대로 살고**, 대기가 *"예정이 없음"*이 아니라
  *"날짜를 안 정하기로 했음"*이라는 **의도**가 된다. 티켓 §무엇이 문제인가가 말한
  *"날짜를 정할 준비가 안 됐다"*와 이름이 맞는다. 대가는 마이그레이션 하나와
  `is_waiting`을 읽는 자리를 전수로 훑는 일이다.
- **C** — 이 티켓이 *"알림이 목적이 아니라 출구가 목적"*이라고 못 박았으므로 출구가 사라지면 남는 게 없다.

**이 층의 견해는 B다** — 원장(§②)도 트리거(§③)도 건드리지 않고, 파생을 물화하지도 않는다.
다만 **정하는 것은 위층이다.**

### 조건 셋을 어디에 뒀나 · N은 한 자리인가

해당 없음 — ★에서 멈췄다. **`defer_count`가 이미 Today 목록에 실려 온다**는 티켓의 전제는
맞다(`db/index.ts:40` 계열의 `v_task_stats`. 조회 시 계산이고 저장하지 않는다).
**팝업 쪽(①②③·N 한 자리)은 갈래가 정해지면 그대로 갈 수 있다** — 막힌 것은 선택지 하나뿐이다.

### 변이 — "항상 안 뜬다"가 잡히는가

해당 없음 — 검사를 쓰지 않았다.

### 설계와 어긋난 점

**티켓 §범위의 *"서버는 확인 결과에 따른다"*가 이 경우를 열어 뒀다** — 어긋남이 아니다.
다만 §완료 조건 5번(*"목록에서 사라지고 대기에 나타난다"*)은 **지금 스키마에서 통과 불가능**하다.
`AGENT-CHAIN.md` §5의 *"§금지를 다 지키면서 §완료 조건을 다 통과하는 경로가 실제로 있는가"*가
**여기서 없다** — 그것을 티켓 스스로 ★로 예상해 뒀고, 그 장치가 일했다.

### 막힌 것

**Cowork의 갈래 결정.** 그 전에는 코드를 쓰지 않는다.
